Task: Give a blocked run a forward path.

Requirements:
1. Replace the H1.2 refusal `aidw/workflows/prompt.py:_refuse_blocked_resume` (and its early exit-3 call in `run`, currently *before* the worktree locate and lock) with a continuation route, scoped to **review-loop** blocks: a blocked run whose `state.gates` holds a `denied` `approve-task-prompt` gate with `mechanism == "review-loop"` (the marker `_record_review_outcome` sets for the terminal `Request changes`, the `Blocked` verdict, and the M2 approve-with-blocking-findings shapes). An author-`blocked:` run (no recorded review) and a human-gate-denied run (review already approved) keep the existing exit-3 refusal (`blocked_resume_reason`), because there is no terminal review whose findings drive a fix batch — `--from-prompt` is their path. (prompt-fixed: the roadmap's continuation is "a fix batch for the terminal review's findings", which presumes a recorded review; branch on the gate `mechanism`, not `status == BLOCKED` alone. Design §8.1's terminal paragraph still says "no gate is recorded" — stale phase-02 wording echoed in §17 G2; the adjacent H7 bullet ("Every verdict-bearing exit records the gate") governs and matches the code, so a terminal-`Request changes` blocked run *does* hold the denied review-loop gate this route keys on — amend the §8.1 clause as a deliverable so the gate-presence precondition is unambiguous.)
2. The continuation is the **existing loop re-run under an extended budget**, not a new stage list. Compute `effective_max_revisions = <recorded task-review-N count> + 1` from the run's stage records, use it as the loop's `max_revisions`, and record it in `state.task["effective_max_revisions"]` (additive in the free-form `task` dict; a pre-H1.3 `state.json` still loads). With that value, the loop's own skip/rebuild machinery (H1.2 req 4: re-read each recorded review's `.out.txt`, re-parse with `parse_review_findings`/`partition_findings`) naturally appends the terminal review's `FixBatch`, and `_prompt_plan(rounds=…)` expands `task-review-fixes-{N}-*` + `task-review-reconcile-{N}` + `task-review-{N+1}` (the terminal review's findings were never batched in the original run — the `terminal_last` break skipped them). Record each round's findings/parses as today. The H1.2 resume budget guard (`_confirm_resume`'s `recorded_fix_rounds > max_revisions - 1` check at the confirmation point, before locate/lock) must consult the budget the loop will actually run under: the *resolved* value for failed-run resumes, the *effective* value for continuation resumes (derivable from the same loaded stage records at that point), and no recorded round for `--from-prompt` continuations — that loop rebuilds none and runs under the resolved value (Requirement 4). Left on the resolved value it refuses the second `--resume` on a re-blocked run (3 recorded fix rounds, resolved `max_revisions=3` allows 2) with exit 2 before the effective budget is ever computed.
3. L4.1 holds in the continuation: the added review `task-review-{N+1}` is **terminal** — never a fix without a following review. Its verdict decides exactly as the original terminal review does: `Approve` → normal success (commit via `_commit_reviewed_prompt`, clear `resume`); a residual `Request changes` or `Blocked` → `_mark_blocked`, exit 3, fail closed. "Normal success" means the same post-loop `approve-task-prompt` gate block the fresh path runs (`already_approved` → `require_approval`/`decide` → optional auto-approve, then `_record_review_outcome`, then commit): a review-loop block's recorded gate is `denied`, so `already_approved` is false and under `--require-approval` the human gate is consulted **exactly once** after the added review — a re-decide of a *denied* gate, which design §9.4 allows (only an **approved** gate is never re-asked), with `--yes`/`--skip-gates`/`--deny-gates`/`--gate-default` and the non-interactive fail-closed short-circuiting exactly as in a fresh run; without `--require-approval` the optional auto-approval stands. A denial there records the continuation's own denied gate via `_record_review_outcome` (mechanism from `decide`, never `review-loop`), `_mark_blocked`, exit 3, no commit — and a later `--resume` on that run then meets Requirement 1's human-gate-denied refusal. (prompt-fixed: "one further cycle" grants exactly one added review round per `--resume` invocation; a second `--resume` on the re-blocked run may grant one more — each is an explicit operator decision, never a default budget.)
4. Add `--from-prompt <path>` to `aidw/cli.py:prompt` and thread it into `run`. On a blocked run it is a continuation (same takeover/locate/lock as `--resume`: same run id, no `create_run`, never re-author), but instead of the fix cycle it re-runs the review loop from `task-review-1` with the operator-supplied file: copy the supplied content into the canonical `docs/task-prompts/<phase>-<task>-prompt.md` in the task worktree (so `rel`, the evidence bundle and `_commit_reviewed_prompt` keep working — the supplied file *is* the prompt being reviewed) — but never over uncommitted edits on that path: a blocked run may itself have left them (exactly what `_report_blocked_leftovers` reports and never repairs, design §13), so when the canonical prompt path is dirty in the task worktree refuse exit 4 before copying, naming the run, the path left untouched and the operator's way forward (the `worktree_clear_commands` the fresh-path dirty-tree refusal prints); a clean path destroys nothing — the committed version stays in git history. Record `state.task["from_prompt"] = {"path": <supplied path>, "hash": "sha256:<hex>"}` over the file bytes (the §9.2 `config_hash` convention), apply the control-tree preflights (base branch checked out, clean tree) and skip the run-scoped preflights — the L1.1 base-branch fetch check and the L1.2 predecessor check — exactly as a resume does. The re-run is a fresh loop over new content, forced past the skip machinery by an internal position bound at `task-review-1` — the `forced_position` rule `--from` applies on encounter, set by the route itself, since the flag is refused here — never by skipping the old reviews, whose `succeeded` records would otherwise re-parse as stale findings; `task-prompt` (position 0) sorts before the bound, so the author record is still reused and the run never re-authors. The prior review/fix/reconcile records are kept, never truncated: a re-run stage supersedes its record by name (`record_stage`'s replace, design §9.4's forced-re-run semantics — the `--from` precedent), and records of rounds the new loop never reaches stay as history. The new loop runs under the resolved config `max_revisions` — the content is new, so a fresh review budget, not Requirement 2's `effective_max_revisions` — and the confirmation-point budget guard counts no recorded round for this shape (the loop rebuilds none; Requirement 2), so a re-blocked run — whose recorded fix rounds exceed the resolved allowance, the shape the unscoped guard refuses — is not refused exit 2 before the route can run. (prompt-fixed: `--from-prompt` is blocked-run-only — on a missing or non-blocked run it is a usage error exit 2; `--from-prompt` **alone** is a takeover — locate/lock/run-id reuse happen with or without `--resume`, widening the H1.2 gate to `(resume or from_prompt) and not dry_run`; when both flags are given, `--from-prompt` takes precedence over the `--resume` fix cycle; and `--from` combined with `--from-prompt` is a usage error exit 2, validated with the missing-file check before any side effect — the route fixes its own start stage `task-review-1`, so a `--from` stage name there is contradictory, never an ordering.)
5. A blocked continuation whose task worktree no longer exists refuses exit 4 naming the run id, the missing worktree path, and the command to re-author (`aidw prompt <phase> <epic> <task>`), never silently re-authoring. Reuse the H1.2 locate (`git.worktree_for_branch`) and its missing-worktree branch, adjusting the message for the blocked case.
6. The gate history preserves the original decision: the blocked run's `denied` `approve-task-prompt` gate stays in `state.gates`; the continuation appends its **own** gate via `_record_review_outcome`. The two are distinguishable because the continuation's `detail` (from `_loop_summary`) reports the budget and the round count the loop actually ran under. That rule is scoped per route: a **`--resume` fix-cycle** continuation passes the **effective** budget into `_record_review_outcome`, never the resolved config value, so the extension is visible rather than inferred (`rounds=` counts the continuation round); a **`--from-prompt`** continuation rebuilds none of the recorded rounds and runs under the **resolved** config `max_revisions` (Requirement 4), so it passes exactly that value — the budget it did run under — with `rounds=` counting the reviews the re-run performed, and never the stale `state.task["effective_max_revisions"]` an earlier fix-cycle continuation may have recorded on the same run. Each shape reports the budget it actually ran under; neither reports one it did not, and a `--from-prompt` gate must never claim an extension that did not happen. Do not add a new gate-decision vocabulary (keep `decision` ∈ `approved`/`denied`). The continuation's `mechanism` splits per gate shape, exactly as the fresh path already does, so no new marker and no §17 marker row is owed: the continuation's **verdict-bearing** exits keep `"review-loop"` — the three `_record_review_outcome` sites at the M2 approve-with-blocking-findings re-block, the `Blocked` verdict, and the added terminal review's residual `Request changes` — while its **post-loop** `approve-task-prompt` gate goes through the shared post-loop block and records `decide`'s own mechanism (`"already approved"`, `"optional (default)"`, or the human answer; Requirement 3), because the review loop did not produce that decision. That per-shape split — never a blanket `"review-loop"`, which would misattribute an approval the loop never gave — is what keeps the original `denied` record distinguishable from the continuation's.
7. The one-run-per-worktree lock (`aidw.lock`, keyed on the reused worktree path) is held across the continuation and released on every exit path, as H1.2 req 7 does. `--dry-run` composes with the new routes exactly as H1.2 req 8 layers it: a dry run never takes over any run — the continuation and the `--from-prompt` route are both takeover-gated (`(resume or from_prompt) and not dry_run`, the H1.2 gate widened per Requirement 4) — so `--dry-run --resume` (or `--dry-run --from-prompt`) over a review-loop blocked run plans the fresh author + `task-review-1` baseline and mints one fresh run record, never continuing the blocked run's id and copying nothing. Not dry-run-gated, as in H1.2: the still-running guard (exit 4), the scoped-out blocked refusals of Requirement 1 on the fix-cycle route — an author-`blocked:` or human-gate-denied run with `--resume` and no `--from-prompt` still refuses exit 3 naming the recorded reason, mutating nothing (the `--resume` fix cycle is no forward path for these shapes, so a dry run must not plan an author over them through it) — and `--from-prompt`'s missing-file check (exit 2, validated like `--from` before any side effect). `--from-prompt`'s missing/non-blocked-run usage error is suppressed under `--dry-run` exactly as the no-run `--resume` refusal is (H1.2 req 8: no matching run plans fresh, exit 0). The missing-worktree refusal (Requirement 5) and the dirty-canonical-path copy guard (Requirement 4) are unreachable under `--dry-run` — locate and copy are takeover-gated — so a dry run over such a run plans fresh. Re-baseline the existing `test_dry_run_with_resume_over_a_blocked_run_still_refuses` per the dry-run bullet in Tests.

Traps / prior review findings:
- The obvious edit keeps `_refuse_blocked_resume` at its early pre-locate position. The continuation must reach the confirmation, locate and lock (like a failed-run resume), so the refusal *moves* to the scoped-out shapes and the missing-worktree refusal (exit 4) is a new branch at the locate — an early blanket refusal re-introduces the exact "no forward path" this task removes.
- Do not bump `max_revisions` in `resolve_config`/CLI. The effective budget is a per-run value derived from the run's recorded reviews; the `--from` grammar (`is_from_stage`) still consults the *resolved* value, and leaking the effective value into it breaks its bounds. The `_confirm_resume` budget check consults the resolved value only for failed-run resumes — a continuation resume is checked against the *effective* budget instead (Requirement 2); leaving that guard on the resolved value refuses the second `--resume` on a re-blocked run as exit 2 before the continuation is ever routed.
- The terminal review's findings are not in a `FixBatch` — the original loop never appended one at the terminal break. Re-parsing them on the skip path is what produces the continuation batch; a `rounds=[]` re-expansion re-runs the author and review-1 (the H1.2 loop-state trap).
- Branch on the gate `mechanism` (and the presence of a recorded review), never on `status == BLOCKED` alone: routing a human-gate-denied run (review already approved) into the fix cycle re-commits an approved prompt, and an author-`blocked:` run has no findings to fix — both are silently wrong continuations.
- `--from-prompt` that reviews the supplied path in place breaks `_commit_reviewed_prompt(target.root, rel, …)` and the evidence bundle, which key off the worktree-relative task-prompts path; copy the content in and record the *supplied* path + hash separately.
- A `--from-prompt` route left on the skip machinery alone no-ops: `should_run` skips the blocked run's `succeeded` reviews and the skip path re-parses their stale `.out.txt` into `FixBatch`es instead of reviewing the supplied content — and the confirmation-point guard counts `_recorded_fix_rounds(existing)`, refusing exit 2 on the re-blocked runs whose recorded fix rounds exceed the resolved allowance (a fresh blocked run records only `max_revisions - 1` and passes). The internal position bound lets the route run at all; the count-nothing guard scoping (Requirement 4) is what lets it run on a re-blocked run.
- The copy is a §13 discard when it runs over the blocked run's own uncommitted prompt edits (what `_report_blocked_leftovers` warns about). Refuse exit 4 on a dirty canonical path instead of overwriting; a silent copy is the operator-work discard AIDT never does.
- `_record_review_outcome`'s `max_revisions` argument is threaded from the resolved config at its four call sites (`_loop_summary` itself has one call site, inside that helper — edit the callers, not the helper); passing the resolved value to the continuation's gate hides the extension — the entire "visible not inferred" contract — behind a summary that reads `max_revisions=3` for a run that ran four reviews. Pass the effective budget for the `--resume` fix cycle and the resolved budget for `--from-prompt` (Requirement 6).
- `state.task` is already a free-form dict (design §9.2); record the new keys there additively — do not add a top-level `RunState` dataclass field or move `SCHEMA_VERSION`.
