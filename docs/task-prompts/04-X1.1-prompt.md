Task: Add a `recorder`-owned `summarize-implementation-results` stage (`I8`) to the `implement`
chain immediately after `record-implementation-results` (`I5`), which reads the build results
`I5` just wrote and produces a human-readable narrative `summary.md` beside it.

Requirements:
1. **The prompt** (`prompts/summarize-implementation-results.md`, new). Same front-matter shape
   as `record-implementation-results.md` (a `description:` and an `argument-hint: [branch]`).
   Variables: `("{branch}",)`. Its **only owned artifact** is
   `<implementation_results_dir>/<branch>/summary.md` (read the resolved value from
   `aidw config show`, exactly as the record prompt references `paths.implementation_results_dir`).
   It must:
   - Read, in full, `<implementation_results_dir>/<branch>/build-results.md` (written by `I5` in
     the same run), plus the task prompt (`paths.task_prompts_dir`/`<branch>-prompt.md`) and the
     cited spec/design headings, for context. The build results are the **single source of truth
     for every fact it states** — the task prompt supplies purpose/scope/non-goals only.
   - Write `summary.md` in a **fixed narrative structure** with exactly these five sections, in
     order: (a) "The problem it was solving", (b) "The core idea", (c) "What was built, piece by
     piece", (d) "What it deliberately did not do", (e) "Verification, honestly". The voice is
     descriptive, not mechanical: it explains *why* and *what changed*, never re-tables the
     Files-Changed list or the gate rows (it may cite file paths inline).
   - **Never run a command that is a verification gate, and never run any command twice.**
     `I5` already ran the gates and recorded real numbers; the summary cites those numbers from
     `build-results.md`. It may run read-only, non-gate commands to orient itself (e.g.
     `git branch --show-current`, reading files), but it must not re-run lint/build/test.
   - **Preserve the build results' honesty.** A recorded failure or `unverified` row stays a
     failure or "unverified with the reason" in the summary — never smoothed over, never rounded
     to a pass, never omitted because it is awkward. If `build-results.md` records a failing gate,
     the summary says so in section (e) and does not invent a fix or a "later resolved" claim.
   - Not modify implementation code, tests, specs, the roadmap, or architecture docs; not commit,
     push, or open a PR (the `I6` stage owns that).
   - Be self-contained under `aidw prompts check` (the existing self-containment sentinels):
     reference config paths by their `paths.*` name, never a hardcoded target-owned directory.
2. **The stage** (`aidw/stage_registry.py`). A module-level
   `StageDefinition("I8", "summarize-implementation-results", "recorder",
   "summarize-implementation-results.md", ("{branch}",))`, referenced from `_IMPLEMENT.stages`
   **immediately after** the `record-implementation-results` (`I5`) `StageDefinition` and
   **before** `_ROADMAP_TICK_STAGE` (`I7`). Add `"I8"` to `STAGE_IDS`; `REPO_OPTIONAL_IDS` stays
   `{I3, I4}` — `I8` is **core** (it writes a generic artifact like `I5`, unlike `I3`/`I4` which
   are repo-specific). The id is retained forever per R6; the position is load-bearing for
   `validate_stage_list`'s reorder rule, exactly as `I7`'s is.
3. **Recorder agent** (`agents/recorder/AGENTS.md`). Add a `## Stage
   /summarize-implementation-results` section (the Y1 precedent for the second section) stating:
   read-only, one owned artifact `summary.md`, do not change code/tests/specs/roadmap, do not
   re-run gates, do not commit/push/PR. Keep it non-overlapping with the `record` and
   `update-roadmap` sections.
4. **Inventory** (`aidw/inventory.py`). Add `prompts/summarize-implementation-results.md` to
   `REQUIRED_PROMPTS` so a rename fails loudly and `aidw prompts check` covers it.
5. **design.md updates.** (a) §1.3: replace the "optional summary prompts … not as a workflow
   stage" non-goal with a note that a single summary (the `implement` results summary) is now a
   workflow stage, scoped to X1.1. (b) §2: stage vocabulary `I1`…`I8`. (c) §5.4 role table: add
   `I8 summarize-implementation-results | recorder | cheap/mechanical`. (d) §8.2 chain diagram:
   add `→ I8 summarize-implementation-results  (agent recorder, fresh)` after the `I5` line and
   before the `I7` line, plus one bullet explaining that `I8` is a read-only summary of `I5`'s
   output that runs no gates and owns no commit. (e) §17: a new decision row `Z3` recording the
   reversal of the §1.3 non-goal, the `I8` id choice, and that the stage is core with the prompt
   owning the narrative structure (no new config path or template).
6. **Gate impact.** `validate_stage_list` now treats `I8` as core, so a repo-declared
   `workflows.implement.stages` list must include `I8` or the run refuses (removal rule), and a
   reorder against the registry's `I5 → I8 → I7` subsequence is refused — the same rule `I7`
   already carries. Re-baseline any test fixture that enumerates the implement chain. `I8` writes
   only `<branch>/summary.md`, which is inside the already-ignored `implementation_results_dir`
   in the `record`/`pr` gate scope, so **no gate-scope change is needed** and `I7`'s
   `WHEN_EVIDENCE_GREEN` evidence is unaffected.

Traps / prior review findings:
- **Do not fold the summary into `I5`.** It must be a separate stage and a separate prompt, run
  after `I5` has finished writing `build-results.md`. `I5`'s prompt and owned artifact stay
  byte-identical in scope.
- **The summary never re-runs a gate.** `I5` is the only stage that buys the whole-repo gate;
  a summary stage that re-runs `pytest` doubles the most expensive step and produces no new
  evidence. Cite `I5`'s recorded numbers, never re-derive them.
- **No invented results.** Everything the summary states about verification comes from
  `build-results.md`. A "later resolved" or "now passes" claim the build results do not contain is
  a fabrication. If `build-results.md` says a gate failed, section (e) says it failed.
- **`I8` is core, not repo-optional.** `I3`/`I4` are repo-optional because they write
  repo-specific artifacts (traceability catalog, architecture). The summary is generic, like
  `record`/`tick`/`pr`; making it disableable would let a repo silently drop the narrative
  artifact the task exists to produce.
- **The `recorder` agent now has three stages.** Each `agents/recorder/AGENTS.md` section must be
  self-contained and non-overlapping; do not blend the "run the gates" rules of `record` into the
  "read-only summary" section.
- **§1.3's non-goal is being reversed.** This is a design-decision change, not copy-editing:
  record it in §17 (`Z3`) and amend §1.3 in the same change; do not leave a stale non-goal that
  contradicts §8.2.
- **No config path or template.** The narrative structure lives in the prompt, prompt-fixed. Do
  not add `paths.summary_template` or a `summary_template` config key — that is out of scope and
  would make a one-stage feature config-driven for no caller.
- **`I8` runs between `I5` and `I7`, serially.** It depends on `I5`'s file and must never be
  added to `_IMPLEMENT.parallel_groups` (only `I2`/`I4` are grouped); it stays a static stage so
  it runs after `I5` by registry order alone.

Explicit non-goals — do NOT do these in this task:
- No new agent id — reuse `recorder` (it already runs the two other cheap/mechanical record
  stages).
- No new config path, template, or `paths.*` key.
- No change to `I5` (gates, scope, owned artifact), `I7` (tick), or `I6` (commit/PR).
- No backfill: AIDW writes summaries only for tasks that run after this change; do not generate
  summaries for already-completed tasks.
- No change to the `prompt`/`review`/`fix`/`approve` workflows — the summary is `implement`-only.
- No re-running of any verification gate or command, and no commit/push/PR (the `I6` stage owns
  delivery).
