Task: Add a `recorder`-owned `summarize-implementation-results` stage (`I8`) to the `implement`
chain immediately after `record-implementation-results` (`I5`), which reads the build results
`I5` just wrote and writes a human-readable narrative `summary.md` beside it.

Requirements:
1. **The prompt** (`prompts/summarize-implementation-results.md`, new). Same front-matter shape as
   `record-implementation-results.md` (`description:` + `argument-hint: [branch]`); variables
   `("{branch}",)`. Its only owned artifact is `<implementation_results_dir>/<branch>/summary.md`.
   It must:
   - Read `<implementation_results_dir>/<branch>/build-results.md` in full — the single source of
     truth for every fact it states — plus the task prompt (`paths.task_prompts_dir`/`<branch>-prompt.md`)
     and cited spec headings for context (purpose/scope/non-goals only).
   - Write `summary.md` in a fixed five-section structure, in order: (a) the problem it was
     solving, (b) the core idea, (c) what was built piece by piece, (d) what it deliberately did
     not do, (e) verification, honestly. Descriptive voice: explain *why* and what changed; never
     re-table the Files-Changed list or the gate rows.
   - Never run a verification gate, and never re-run any command. Cite the gate numbers
     `build-results.md` already records; read-only orienting commands (e.g. `git branch
     --show-current`, reading files) are fine.
   - Preserve honesty: a recorded failure or `unverified` row stays a failure / "unverified with
     the reason" — never smoothed, rounded to a pass, or omitted; never invent a fix.
   - Not modify code, tests, specs, the roadmap, or architecture docs; not commit/push/PR.
   - Stay self-contained for `aidw prompts check`: reference config paths by their `paths.*` name,
     never a hardcoded target-owned directory.
2. **The stage** (`aidw/stage_registry.py`). A `StageDefinition("I8",
   "summarize-implementation-results", "recorder", "summarize-implementation-results.md",
   ("{branch}",))` in `_IMPLEMENT.stages` immediately after the `I5` `StageDefinition` and before
   `_ROADMAP_TICK_STAGE`. Add `"I8"` to `STAGE_IDS`; `REPO_OPTIONAL_IDS` stays `{I3, I4}` — `I8`
   is core (a generic artifact like `I5`, unlike repo-specific `I3`/`I4`). The id is retained
   forever per R6; the position is load-bearing for `validate_stage_list`'s reorder rule, like
   `I7`'s.
3. **Recorder agent** (`agents/recorder/AGENTS.md`). Add a third `## Stage` section for
   `/summarize-implementation-results` — a bare `## Stage` heading with the stage path on its own
   line, mirroring the shape of the two existing sections — stating: read-only, one owned artifact
   `summary.md`, no code/test/spec/roadmap edits, no gate re-runs, no commit/push/PR. Keep it
   non-overlapping with the `record` and `update-roadmap` sections.
4. **Inventory** (`aidw/inventory.py`). Add `summarize-implementation-results.md` to
   `REQUIRED_PROMPTS`.
5. **design.md updates.** §1.3 (reverse the "optional summary prompts … not as a workflow stage"
   non-goal, scoped to this one summary); §2 (`I1`…`I8`); §5.4 (add
   `I8 summarize-implementation-results | recorder | cheap/mechanical`); §8.2 (chain diagram: `I8`
   after `I5`, before `I7`, plus one bullet — `I8` is a read-only summary of `I5`'s output, runs no

   wording implementer freedom — and no new config path or template).
   Gate impact: `validate_stage_list` now treats `I8` as core, so a repo-declared
   `workflows.implement.stages` list must include `I8` (removal rule) and a reorder against the
   registry's `I5 → I8 → I7` subsequence is refused — the same rule `I7` already carries.
   Re-baseline any test fixture enumerating the implement chain. `I8` writes only
   `<branch>/summary.md`, inside the already-ignored `implementation_results_dir`, so no
   gate-scope change is needed and `I7`'s `WHEN_EVIDENCE_GREEN` evidence is unaffected.

Traps / prior review findings:
- **Do not fold the summary into `I5`.** It must be a separate stage and prompt, after `I5`
  finishes writing `build-results.md`; `I5`'s prompt and owned artifact stay unchanged.
- **Never re-run a gate.** `I5` is the only stage that buys the whole-repo gate; re-running
  `pytest` doubles the most expensive step for no new evidence. Cite `I5`'s recorded numbers.
- **No invented results.** Every verification fact comes from `build-results.md`; a "now passes" or
  "later resolved" claim it does not contain is a fabrication.
- **`I8` is core, not repo-optional.** The summary is generic like `record`/`tick`/`pr`; making it
  disableable lets a repo silently drop the artifact this task exists to produce.
- **`recorder` now has three stages.** Each `agents/recorder/AGENTS.md` section must be
  self-contained; do not blend `record`'s gate-running rules into the read-only summary section.
- **§1.3 is being reversed — record it.** This is a design-decision change: amend §1.3 and add §17
  `Z3` in the same change; do not leave a stale non-goal contradicting §8.2.
- **No config path or template.** The narrative structure lives in the prompt; do not add
  `paths.summary_template`. `I8` runs serially between `I5` and `I7` — never add it to
  `_IMPLEMENT.parallel_groups`.
