Task: Branch setup becomes a Python stage, not a prompt — remove the `git checkout -b` instructions from `prompts/impliment-task.md`; AIDT creates the branch and its worktree before the first agent stage runs, using `repo.base_branch` and `repo.branch_pattern`.

Requirements:
1. Add `branch_pattern: str = "{phase}-{task}"` to `TargetRepo` (`aidw/paths.py`), mirroring the existing `base_branch: str = "main"` field. §3.4 fixes the field name and default; *where* the value lives before E3 config lands is prompt-fixed — the hardcoded-default-on-`TargetRepo` pattern `base_branch` already uses. Derive the branch/worktree name from `repo.branch_pattern.format(phase=…, task=…)` instead of the hardcoded `f"{phase}-{task}"` in `parse_task_id`/`run`; under the §3.4 default the names stay byte-identical (`00-E2.4`, `02.5-B`). The seam is prompt-fixed: `parse_task_id` stays a pure one-argument filename parser (unchanged signature and return — its third tuple element is the task id `f"{phase}-{task}"`, no longer the branch name), and `run()` derives the branch/worktree name in one place via the pattern. A malformed pattern is a usage error (exit 2, design §14), never an escaping exception: refuse — actionable message, no worktree, no stages, before the dry-run plan as well — when `.format` raises `KeyError` (unknown placeholder) or when the pattern does not reference both `phase` and `task` (a constant/partial name collides across tasks; §3.4 "name from task ids", §3.2 one-branch-one-worktree).
2. Add a `branch-setup` Python stage to `aidw/workflows/implement.py` that runs before I1 and creates the branch+worktree via `git.add_worktree(repo.root, branch, base_branch=repo.base_branch)` (the §3.2 per-task command; the primitive already derives `<workspace_root>/<branch>`). On `None` — branch already checked out (one-branch-one-worktree) or any git refusal — fail closed: print an actionable refusal and return `EXIT_REFUSED` (4), running no stages. Reusing/locating an existing worktree is E2.6, not here — and §3.2's Consequences sentence that `aidw implement`/`fix` locate the worktree via `git worktree list --porcelain` and print the exact `worktree add` command when absent is likewise E2.6's end state, not this task's contract (§6 assigns E2.4 *create*, E2.6 *locate*): this task is create-only with the fail-closed refusal above, which E2.6 will supersede with locate/reuse. In `--dry-run` the step is planned, not executed: print the intended `worktree add` action (branch, target path, base branch) and create nothing — design §14: a dry run performs no writes and prints the planned actions, matching the dry-run block's existing "no Pi, no git/GitHub writes" promise. It is inline Python in `run()`, not a `PlanStage`: `build_plan` and the `I1..I6` ids are unchanged (§3.5 keeps them as the default ids for continuity in run artifacts and `state.json` — `test_build_plan_order_and_agents` and `test_dry_run_plans_all_six_stages` pin exactly six), and branch-setup never flows through `run_stage` or a stage record.
3. Replace the old preflight (`aidw implement` must not run on `main`; `branch != branch_name` mismatch) with the branch-setup step: `aidw implement` no longer requires being on the task branch. The preflight's third guard is **retained**, not replaced: another implement run for the branch still marked `running` refuses with `EXIT_REFUSED` unless `--resume`, checked before branch-setup so the refusal creates neither worktree nor state. Sequence branch-setup before any run-state write (`create_run`; the resume path reuses existing state) so a refusal leaves no partial run state — the fail-closed test asserts this. After the worktree is created, re-resolve the target *and* the agents so I1..I6 run in the new worktree: `load_all`/`load_agent` resolves `agent.cwd` against the `repo_root` it is given (`aidw/config.py`, `cwd = _resolve(cwd_raw, repo_root)`), so either call `load_all` again with the worktree root after the switch or move the single `load_all` call after branch-setup — keeping the pre-switch agents is the stale-`cwd` trap below. The worktree must exist before the first `run_stage` (I1) call. The task prompt must reach the new worktree too: `prompt_rel` is resolved against the control root before creation, and a worktree born at the base commit does not contain a prompt file that is uncommitted in the control worktree — the standard authoring layout. Branch-setup copies the prompt file from the control worktree to `<new-worktree>/<prompt_rel>` (creating parent dirs as needed) when it is not already present there, so I1's `$1` variable and I5's relative `docs/task-prompts/<branch>-prompt.md` reference (`prompts/record-implementation-results.md` step 3) both resolve. In `--dry-run` nothing is copied (design §14: a dry run performs no writes).
4. Remove the whole "### Branch setup (do this first, before any code)" section from `prompts/impliment-task.md` (the `git branch --list` / `git ls-remote` / `git checkout -b` / `git branch --show-current` steps). Leave a one-line pointer that AIDT owns branch setup (§3.2). Touch nothing else in that prompt: its `pnpm`/`@mythical-forge`/`srd:*` content is E7.2's, and removing it now would break the D5 freeze before MF.2 lands overrides.
5. Thread the branch name derived from `branch_pattern` consistently: `create_run` label/branch, `_latest_implement_run`, `_gate_summary`, and `_write_artifacts` all receive the same value (they currently consume `branch_name` from `parse_task_id`). No divergence between the git branch, the worktree dir, and the state label. The diff/PR base follows `repo.base_branch` at every other base reference, not just worktree creation: `_gate_summary` and `_record_pr` measure `git.changed_files` against `repo.base_branch` (both currently hardcode `"main"`; the primitive already takes the ref), and I4's `variables` list becomes `[branch, repo.base_branch]` (its second element is passed as `$2` → `base_ref`, `prompts/update-architecture.md`). §3.4 makes `base_branch` the "PR base and branch point" and R4 keeps `main` out of the code for repos whose base branch differs. `_gate_summary`/`_record_pr` currently receive `repo.root` (a `Path`), so thread the base in as a value or pass the `TargetRepo`.

Traps / prior review findings:
- `agent.cwd` is resolved once against `repo.root` in `load_agent` (`cwd = _resolve(cwd_raw, repo_root)`). Create the worktree but forget to re-resolve agents/target and I1..I6 silently run in the control worktree — the exact §3.2 failure this task exists to remove.
- `TargetRepo` is `@dataclass(frozen=True)` — you cannot assign `repo.root = new_worktree`. Re-resolve `TargetRepo.resolve(new_worktree)` (or thread a separate worktree path into `run_stage`) instead of mutating.
- `git.add_worktree` returns `None` on refusal and discards git's stderr — don't parse a reason it doesn't return. Pre-check `git.worktree_for_branch` only if you must distinguish "already checked out" from other failures; otherwise fail closed with a generic-but-actionable message.
- The current `_make_inputs` harness builds plain `git init` repos with no commits — `main` doesn't resolve there, so real `add_worktree` returns `None` and every non-dry-run `run()` exits 4. Tests that reach branch-setup must use the bare+control layout (Tests section); do not mock `add_worktree` — the Done-when forbids faked git output.
- The `branch_pattern` default must reproduce the existing names byte-for-byte — `("02.5", "B")` → `"02.5-B"` — and `parse_task_id`'s filename variants must keep parsing (`test_parse_task_id_variants`, `tests/test_implement_workflow.py`; the bare `02.5-B-prompt.md` form included). Don't drop the dotted-phase form.
- `impliment-task.md` is bucket (ii) (§4.2): the "Branch setup" section is the only removal. Neutralising `pnpm`/`srd:*` is E7.2; the `agents/task-author/AGENTS.md` "branch the prompt creates" line is E7.4 (R5 names both, the roadmap assigns only `impliment-task.md` here).
- `prompt_rel` is computed against the control root before the worktree exists (`run()`, `prompt_path.relative_to(repo.root)`), and `build_plan` hands it to I1 as its `$1` variable — a worktree created at the base commit lacks a prompt file that is uncommitted in the control worktree. Without the Requirement-3 copy, the mocked-`run_stage` tests stay green while the first real agent run fails on a dangling path. An absolute path instead of the copy breaks I5's relative `docs/task-prompts/<branch>-prompt.md` reference; refusing unless committed breaks the control-worktree authoring layout — hence the copy.
