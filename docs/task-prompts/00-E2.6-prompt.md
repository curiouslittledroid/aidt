Task: `implement`/`fix` resolve their worktree

Requirements:
1. implement — locate, don't create. Replace the `# --- branch setup: create the task worktree` block in `aidw/workflows/implement.py:run` (the `git.add_worktree` call plus the copy-prompt step) with `git.worktree_for_branch(repo.root, branch_name)` (which wraps `git.worktrees()`). Found → re-resolve exactly as E2.5 does: `TargetRepo.resolve(worktree)` + `replace(base_branch=…, branch_pattern=…)` + `load_all`; the copy-prompt step is deleted (the prompt is committed on the branch by E2.5). Absent → print the command from requirement 4 and return 4, no `run_stage`, no run state — real runs; `--dry-run` plans the same command and exits 0 (req 6). `--repo`/`AIDW_REPO` already select `repo.root` (`cli.py:_roots`), so the lookup follows it — from an unrelated cwd, `--repo` is what makes the lookup possible.
2. implement — resolve the prompt inside the worktree. The task prompt lives in the task worktree, not the control root (E2.5 commits it there). Reorder `run()`, pinning the sequence: parse the task id from `Path(task_prompt_path).name` (`parse_task_id`), derive the branch (malformed `branch_pattern` → exit 2), `load_all` config validation (errors → exit 2; it stays in the preflight, before the locate, so a combined bad-config-plus-missing-worktree run exits 2, not 4 — design §14 usage/config), then the still-running guard, `--from` validation and resume confirmation, all before any side effect; locate the worktree (absent → exit 4, req 1); then resolve `prompt_path`/`prompt_rel` against `target.root` (the worktree) and check `is_file()` there (missing → exit 2). prompt-fixed, every argument shape resolves inside the worktree: a relative `task_prompt_path` is a repo-relative subpath — resolve it against the worktree root, never the control root or the cwd; an absolute control-root path re-bases via its repo-relative subpath; an absolute worktree path (what req 5's chain hands over) resolves as-is. The `is_file` refusal is real-runs-only in one case: it needs the located worktree, so dry-run applies it only when the locate succeeded — a located worktree still missing the prompt exits 2 even in dry-run, but with the worktree absent (dry-run creates nothing) the re-based `prompt_rel` is planned unchecked and the run proceeds per req 6; only the existence check is suspended — the argument-shape rules above still exit 2 in dry-run.
3. fix — resolve the PR-head worktree. In `aidw/workflows/fix.py:run`, replace `branch = git.current_branch(repo.root)` and the `branch != headRefName` refusal with: `branch = pr_info["headRefName"]`, then `git.worktree_for_branch(repo.root, branch)`; absent → print the command (req 4) and return 4 — real runs; `--dry-run` plans it and exits 0 (req 6); found → re-resolve `TargetRepo`+`load_all` against the worktree and use it for every `run_stage`, every `github.*` call that reads the tree, and the `create_run(…, repo.root, …)` call — state.json's `repo_root` must record the worktree, as `implement`'s run state already does (its `create_run` passes `target.root`). Keep the `gh`-available, PR-exists and `baseRefName` preflight checks and their order (the `baseRefName != "main"` check is pre-existing — leave it). The `pr_view` read that populates `pr_info` runs in dry-run too (req 6); only the refusals stay behind `not dry_run` — so `headRefName` resolves in both modes and `current_branch` is gone entirely.
4. The missing-worktree message is copy-pasteable. Print exactly the §3.2 per-task command, with all paths absolute: `git -C <workspace.workspace_root>/<base_branch> worktree add -b <branch_name> <workspace.workspace_root>/<branch_name> <base_branch>` (prompt-fixed: `base_branch` substitutes for the literal `main`, so `-C` points at the base-branch worktree). A test asserts the full command string, `-C` prefix included.
5. Keep the chain working. After E2.5 the chain's `repo` is the control root on the base branch, so two `aidw/workflows/run.py` reads are stale: `_resolved_task_prompt`/`find_task_prompt` scan `repo.root`, where the prompt no longer lives; and `prompt_to_fix`'s `branch = git.current_branch(repo.root)` feeds `find_pr_number` the base branch, not the task branch `implement` recorded, so PR discovery stops the chain `no PR number recorded … pass --pr` on its happy path. Derive the task branch in the chain the way `prompt`/`implement` do — `derive_branch_name(repo.branch_pattern, phase=…, task=…)`; the chain has the ids, no filename parse — locate the worktree with `git.worktree_for_branch(repo.root, branch)`, resolve the prompt path inside it (the non-dry-run `find_task_prompt` scan runs against the worktree root, not `repo.root`) so `task_to_pr`/`prompt_to_fix` hand `implement` a path that exists, and feed `find_pr_number` the same derived branch; `git.current_branch` is gone from run.py. Chain-side absence is pinned: a malformed pattern (`derive_branch_name` → `None`) is exit 2 before any lookup (req 7), and a worktree the lookup cannot find makes the chain itself print the req-4 command and return 4 without calling `implement` — the same refusal req 1 gives `implement` (a located worktree whose scan still finds no prompt keeps the existing `no task prompt found` exit 2). `--dry-run` keeps its conventional-path fallback (no lookup, no refusal) and the PR placeholder; `--pr` still overrides discovery.
6. dry-run. `implement --dry-run` prints the planned worktree path it will look up (not a `worktree add` it no longer performs), creates no worktree, refuses no locate — a missing worktree prints the req-4 command as planned output (exit 0, the same rule `fix` gets below) — and still plans I1..I6, with the re-based `prompt_rel` (req 2's argument rules, existence check suspended). Dry-run suspends neither the req-2 preflight nor the run-state write: malformed `branch_pattern` still exits 2 (req 7), unknown `--from` stage and other usage/config errors still exit 2 (design §14), the still-running guard still exits 4 (only the existing `resume and not dry_run` checks keep their dry-run exemptions), and the run is still recorded under the state root — a dry-run stage writes `state.json` (design §15), pinned by tests/test_implement_workflow.py `test_dry_run_writes_runs_under_the_state_root`; don't change that behavior (fix's dry-run records its run the same way). `fix --dry-run` plans the same way (design §14 lists it; §15: every workflow's dry-run performs no writes and prints the plan — reads are fine, it already reads `select_followups` when `gh` is available): the `pr_view` read runs in dry-run too, so `branch = pr_info["headRefName"]` and the local `worktree_for_branch` lookup still happen; print the planned worktree path, plan the F-rounds against the located worktree, exit 0. Dry-run performs no locate or PR-read refusal: a missing PR-head worktree prints the req-4 command as planned output (exit 0, not 4) and still plans the F-rounds against `repo.root` (the branch is known but there is no worktree to plan against — the same fallback the unanswerable read gets), and an unanswerable PR read (`gh` missing, or the chain dry-run's placeholder PR 0) prints a `branch: unknown (<reason>)` line — mirroring the existing `child: unknown` one — skips the lookup, plans against `repo.root`, still exit 0.
7. Fail-closed + exit codes. Missing worktree is exit 4 in real runs (preflight/safety refusal, design §14), consistent with E2.5's refusals — `--dry-run` prints the command as planned output and exits 0 (req 6). Malformed `branch_pattern` stays exit 2 before any lookup. Never `reset --hard`/`clean`/merge (design §13).
