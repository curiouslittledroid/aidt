Task: Allow per-stage `agent`/`model`/`thinking`/`timeout_seconds` and a global agent-config override, defaulting to the toolkit's `agent-configs/`.

Requirements:
1. Stage-entry schema (E3.1): extend `STAGE_KEYS` in `aidw/target_config.py` from `("id","enabled","prompt","agent")` to include `model`, `thinking`, `timeout_seconds`; `StageConfig` gains `model: str | None`, `thinking: str | None`, `timeout_seconds: int | None`. Validate on load: `thinking` ∈ `aidw/config.py:THINKING_LEVELS`, `timeout_seconds` a positive int, `model` a non-empty string; bad values fail with the dotted field path (E3.1's unknown-key/type/bad-enum contract). Round-trip via `_declared` keys so an absent override never serialises as `null`. Mirror in `docs/schema/aidw-config.schema.json` (`$defs/stage` gains the three properties, still under `additionalProperties: false`) and the `docs/target-repo-config.md` stage-entry table (replace the "`model`, `thinking` and `timeout_seconds` are **not** stage fields" sentence).
2. Global agent-config override (prompt-fixed field name + shadow semantics): add `agent_configs_dir` to `PATH_FIELDS` and `READ_PATHS` in `aidw/target_config.py`, and give `PathsConfig` the matching field `agent_configs_dir: str | None = None` — the field is load-bearing, not incidental: `_parse_target_config` constructs `PathsConfig(**{name: … for name in PATH_FIELDS})` and `resolve_config` does `getattr(defaults.paths, name)` for every `PATH_FIELDS` entry, so the key without the field is a `TypeError`/`AttributeError` at load time; and `validate_paths` checks defaults too, so seeding a value instead of leaving it `None` fails every repo without that directory. Seed **no** value for it in `TOOLKIT_DEFAULTS` (`ConfigDefaults.paths`) — it is "unset, not defaulted": the consumer falls back to the toolkit dir, so a repo with no `aidw/` folder never validates a repo-relative path it does not have. `aidw/config.py:load_all` gains an override-dir parameter (`None` → `toolkit_root/"agent-configs"`): when named, the caller resolves it target-root-relative via `_target_path` semantics (absolute value wins), and `load_all` loads its `*.yaml` and **shadows by id** over the toolkit's `agent-configs/` — the key is the file's `id` (stem==id is already enforced: `load_agent` ERRORs on a mismatch), un-overridden toolkit ids still load, and a brand-new id loads as an additional agent (a legal target for a declared `agent`); a named-but-missing dir is an ERROR issue, same shape as the toolkit dir-not-found path — `validate_paths` stays prompt-only in implement/review/fix/approve, so `load_all` is those preflights' exit-2 refusal point; an empty dir is legal and equals the toolkit defaults. `check_independence`/`check_read_only` run on the **shadowed** dict (§5.4). Thread the resolved value through the five workflow preflights **and** their worktree re-resolve `load_all` sites (`aidw/workflows/{implement,prompt,review,fix,approve}.py`), which already hold the resolved config; `aidw/cli.py` (`agents list|validate`) and `run_stage`'s defensive `agents=None` fallback keep the toolkit default (they validate the toolkit's own defaults, not a target's overrides). Mirror the key where Req 1 mirrors the stage keys: the schema's top-level `paths` object gains `agent_configs_dir`, and `docs/target-repo-config.md` gains a `paths:` inventory row (default `unset` — when named it is a read-path that must exist) and a `Full`-example declaration.
3. Per-stage `agent` override honoured: delete `_REASON_AGENT` from `aidw/runner.py` and make `_spec_from_planned` use the declared `agent` as `StageSpec.agent_id`; extend `declared_stage_issues` to existence-check a declared `agent` on **known** ids too (not only repo-added), so an unknown overridden agent is refused exit 2 in preflight, never `run_stage`'s `ValueError: unknown agent` traceback. Keep the `_REASON_REPO_ADDED` warning for `prompt`/`fix` (their name-keyed consumers never run a repo-added stage) untouched.
4. Per-stage `model`/`thinking`/`timeout_seconds` → effective agent: carry the three onto `StageSpec` (all `None`-defaulted), and in `run_stage` apply them to the resolved `AgentConfig` via `dataclasses.replace` **before** `build_argv`, `execute(timeout=…)`, `StageRecord(model=…)`, `write_meta`, `logger`/`progress` — so argv, run state and cost (§9) all see the effective model. `model` follows the agent field's `provider/model` semantics (`aidw/agents.py:model_name`/`qualified_model`): it replaces `model` only — `provider` is not a stage field (D12's surface: agent/model/timeout/thinking), so an override never switches providers (a provider change goes through `agent:` or the global override dir). `model_name` strips only a prefix matching the agent's own `provider`; any other spelling — a bare slug, or a vendor-namespace slug containing `/` (the configs' own `deepseek/deepseek-v4.1-flash`, `meta/muse-spark-1.3` under `openrouter`) — passes whole to `--model` under the base `--provider`. `StageRecord(model=…)`/`write_meta` keep reading the effective config's `qualified_model` (by construction `provider/` + the `--model` slug), never a second spelling of the override. `thinking`/`timeout_seconds` match design §5.1.
5. Precedence (prompt-fixed): per-stage override > global override-dir shadow > toolkit default, for that stage's invocation only; repo-added stages honour the same three fields uniformly (their declared `agent` is already the honoured base).

Traps / prior review findings:
- `build_argv` is one of five consumers of `agent.model` — `StageRecord(model=…)`, `write_meta`, `logger.info(model=…)`, `progress.start(model=…)` all read the base agent in `run_stage`. Patching only `build_argv` passes the Done-when's argv check while `state.json`/cost (§9) record the un-overridden model. `dataclasses.replace` once, before all of them.
- Shadow-then-validate: `load_all` must merge the override dir **before** `check_independence`/`check_read_only`, or a repo sets `implementer.model == code-reviewer.model` and the §5.4 "reviewer ≠ author" warning never fires on the value actually used.
- `model` may carry a `provider/` prefix (design §5.1) — route the override through `model_name`/`qualified_model`, never pass the raw string to `--model` (doubled prefix: `--provider openrouter` + `--model openrouter/…`) or strip unconditionally. The split rule (Req 4): only a prefix matching the agent's own `provider` is stripped; any other leading segment (`anthropic/…`) is a vendor-namespace slug riding the base `--provider`, never a provider switch. `record.model` is the *qualified* string — `qualified_model` of the effective config, `provider/` + the argv `--model` slug — never the raw override or the bare slug.
- Known-id agent existence: `declared_stage_issues` currently `continue`s past the agent check for known ids (`if definition_entry is not None: continue`) — without req 3's extension, an unknown overridden `agent` reaches `run_stage` as a traceback instead of the preflight's exit-2 refusal. Wire it in the same post-`load_all` helper as the repo-added check (E4.5b req 5).
- Removing `_REASON_AGENT` is not "drop `_warn_deferred_settings`": `_REASON_REPO_ADDED` still names `prompt`/`fix`'s name-keyed consumers. Remove only the agent reason, or repo-added stages in prompt/fix silently drop.
- `tests/test_target_config.py::test_stage_override_fields_are_not_in_this_schema` (parametrized `model`/`thinking`/`timeout_seconds`) asserts rejection — flip it to assert acceptance + per-key validation, and update the schema JSON + `docs/target-repo-config.md` in the same change, or the three disagree. Its doc-contract sibling `tests/test_target_repo_config_doc.py` pins the same agreement from the doc side (`REJECTED_STAGE_KEYS`'s two tests, `EXPECTED_DEFAULTS`, `MINIMAL_PATHS`/`FULL_PATHS`): those expectations flip with the loader in the same change — `EXPECTED_DEFAULTS` is derived from `PATH_FIELDS` at import, so skipping the file is a collection error, not one red assert.

If anything in the cited spec section is ambiguous or underspecified for this task, stop and ask rather than guessing — especially:
- the global override's field name and shadow semantics — prompt-fixed above to `paths.agent_configs_dir`, read-path, shadow-by-id: D12 fixes only "override agent config globally" and the task only "defaulting to the toolkit's `agent-configs/`"; neither names a field. Shadow-by-id (not wholesale replacement) mirrors D4/D14's missing-⇒-default so a repo overrides only the agents it differs on. The remaining edge rules follow from that fix plus existing code, so they are prompt-fixed in Req 2 rather than escalated: a relative value resolves via `_target_path` (§3.4 read-paths already do); a named-but-missing dir is an ERROR because §3.4 requires configured read-paths to exist and `validate_paths` is prompt-only outside `aidw prompt` (leaving `load_all` as the refusal point); the key is the `id` that `load_agent` already enforces against the stem; and shadow semantics make brand-new ids additive and an empty dir equal to the toolkit defaults.
- per-stage vs global precedence — prompt-fixed above to "per-stage wins for that stage only"; §3.4 fixes no interaction.
- whether per-stage `model`/`thinking` overrides are re-run through §5.4 independence — prompt-fixed above to "no": §5.4 is a load-time check on the shadowed dict; a per-stage override is an explicit operator choice recorded in the argv/state, like `--force-model`.
- whether repo-added stages honour `model`/`thinking`/`timeout_seconds` — prompt-fixed above to "yes, uniformly".
- how a per-stage `model` string maps onto `provider` — prompt-fixed above to "`model`-only replacement: `model_name` strips only a prefix matching the agent's own `provider`; any other leading segment is a vendor-namespace slug under the base `--provider`, never a provider switch; `record.model` carries `qualified_model` of the effective config": §5.1 fixes `provider` as a separate field (`model: <provider/model-slug>`), and neither D12's override surface nor the §3.4 stage entry has a `provider` key, so a prefix-split-into-provider reading has no source — a provider change is already expressible via `agent:` or the global override dir.
- anything security-sensitive, cost-committing, or hard-to-reverse (cross-account trust, schema changes, billing logic, data deletion).
