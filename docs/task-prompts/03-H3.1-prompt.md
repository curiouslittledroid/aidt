Traps / prior review findings:
- `task_id` name collision: `aidw/workflows/implement.py` already binds `task_id = f"{phase}-{task}"` (`03-H3.1`, I6's `$1`). The tick needs `entry.task` (`H3.1`), fed via the distinct `checkbox_id` field. Reusing `{task_id}` targets a non-existent id.
- D15: never write `docs/tasks` literally. Resolve `paths.roadmap_dir`/`paths.roadmap_glob` from `resolved_config` **after the locate**, joining the relative values against the worktree root — the same re-resolution `agent_configs_override(resolved_config, target.root)` already does for `paths.agent_configs_dir`; the pre-locate checks sit on the control root (cf. `prompt.py`'s `roadmap_dir = str(resolved_config["paths.roadmap_dir"].value)`); a hardcoded dir breaks repo-optional config, and the prompt itself must receive the path, not a directory.
- The byte-exact postcondition is the fail-closed check. Compare the full before/after file (bytes or the full line list) — a "line now starts with `[x]`" check would pass a reformat, a neighbour edit, or trailing whitespace. The checkbox line shape is `aidw/roadmap.py:TASK_RE`.
- Registry order is load-bearing: `validate_stage_list`'s reorder rule compares the declared core-id subsequence to `core_ids` derived from `_IMPLEMENT.stages` order. Put `I7` between `I5` and `I6` in `_IMPLEMENT.stages`, or a repo that declares the full list gets a spurious reorder ERROR. Re-baseline `tests/test_plan_stages.py`'s pinned `registry order is [I1, I2, I5, I6]` and `tests/test_implement_workflow.py:DEFAULT_ORDER`.
- `tests/test_stage_registry.py` uses `registry.stage("implement", "I7")` as its *unknown-stage* example — once `I7` exists that assertion fails; re-point it at a still-unknown id (e.g. `I8`).
- The post-stage re-parse must read the file the stage actually edited — the located worktree's copy, not the control root's. In a `--dry-run` with no worktree, resolve/plan against the same `plan_root` `implement.py` already uses.
- `skipped` is H3.2's word: its Done when records a tick withheld behind red gates as stage `skipped` naming the failing gate(s). The already-`[x]` no-op stays `succeeded` with its own `artifacts` marker (req 7); a record that cannot tell "already done" from "withheld" breaks H3.2's acceptance replay on this same stage.
- The tick is a write to a committed file: a wrong flip advances `aidw tasks --next` past open work. Requirement 7 is what makes the edit honest; do not weaken it to "the agent reported success".
