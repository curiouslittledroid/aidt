Requirements:

   path a repo-added stage writes; never source, tests, config or lockfiles.
2. State the line-up rule in the edited prompt (mirroring `pr.md`): every stage of a run that asks
   for a gate must pass the same key, command and `--ignore` scope, or the outcomes cannot line up
   and the gate re-runs. Reuse is same-run only (R16): the fix workflow is its own run, so a
   `reused:` there can only cite an outcome an earlier stage of the *same fix run* (F1) recorded —
   the fix-chain `test` stage (F2, `test.md`) is the citing consumer.
3. Keep §6's existing semantics intact: narrowest checks first, `git diff --check`, and
   "pre-existing failures are reproduced on the unmodified tip and reported separately". Do NOT wrap
   §5's deliberate "test fails before the fix" proof in `aidw gate run` — that invocation is meant to
   fail (red-before/green-after proof), and a recorded `failed` gate outcome is never cited, only noise.
4. End-to-end reuse test in `tests/test_verification.py`, following the
   `test_cli_gate_run_records_into_the_env_run` shape (`repo` fixture, `_state_base`, `create_run`,
   `cli.invoke(app, ["gate", "run", …])`, `RUN_ID_ENV_VAR`/`STAGE_ENV_VAR`). The gate command must have
   a real side effect — append a line to a counter file *outside* the repo — because a write inside the
   repo changes the tree identity and defeats the reuse the test is meant to prove. Assert, in order:
   stage `test` runs `aidw gate run suite $SCOPE -- <counter command>` → counter has 1 line; write a
   file under `docs/implementation-results/` (inside `SCOPE`) to model I5 writing after gating; stage
   `record` runs the same gate → prints `reused:`, counter still 1 line (no second run), the recorded
   outcome's `stage` is `"test"` and its `summary` carries the real count; then change a source file
   outside `SCOPE` → a third invocation re-runs (counter 2 lines, `passed:`).
5. No new schema fields, state vocabulary, or CLI surface. If the end-to-end test exposes a real
   reuse bug, fix it minimally in `aidw/verification.py`/`aidw/cli.py` and name the fix in the results
   doc; do not weaken the test to make the current behaviour pass.

Traps / prior review findings:
- A gate command that writes into the repo changes the tree identity (`tree_identity` hashes the
  change set including untracked files), so the next stage re-runs. Keep the test's counter outside the
  repo — that side effect is the proof, not an accident.
- The origin is the *first* stage that recorded the pass: `run_gate` cites `run.gate_outcome(key,
  tree)` and appends nothing on reuse. Assert `stage == "test"` and `len(gate_outcomes) == 1`; an
  assertion of `stage == "record"` proves nothing.
- Reuse is same-run and same-command only (`run_gate` requires `prior.command == command` and looks
  only at the current run's `gate_outcomes`). A different command under the same key, a different key,
  or an earlier run's outcome all re-run — do not write the test to rely on cross-run or cross-key reuse.
- `fix-next-review-followup.md` is an existing required prompt: keep its frontmatter intact and
  `uv run aidw prompts check` green; do not touch `aidw/inventory.py` or the four implement-chain prompts.
- §5's "fail before the fix" run must stay a bare command: wrapping it in `aidw gate run` records a
  `failed` outcome and muddies `aidw gate list` without ever being cited.
