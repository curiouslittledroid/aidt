Task: Implement target resolution: cwd walk-up plus an explicit-override parameter (the path that `--repo`/`AIDW_REPO` will later supply); reading `AIDW_REPO` and the CLI plumbing are E1.5. Expose `root`, `git_dir`, `common_dir`, `base_branch` (from config, E3). Roadmap context only, not this task's acceptance: the full precedence — cwd, then `--repo <path>`, then `AIDW_REPO` — is completed by E1.5.

Requirements:
1. Add a `TargetRepo` dataclass exposing exactly `root`, `git_dir`, `common_dir`, `base_branch` — `root`/`git_dir`/`common_dir` are absolute `.resolve()`d `Path`s, `base_branch` a `str`. Per §3.1 it is a distinct type from the toolkit root, never a bare `root: Path` alias. The sole construction entry point is the factory `TargetRepo.resolve(start: Path | None = None, explicit: Path | None = None) -> TargetRepo` (a classmethod on the dataclass): `start` is the default-mode walk-up origin (defaults to cwd); `explicit` is the override path. Callers never build `TargetRepo` by hand.
2. Default resolution walks up from cwd preserving `repo_root()` semantics (`aidw/paths.py:repo_root`): `git rev-parse --show-toplevel`, then the `.git`-file/dir walk-up fallback, `.resolve()`d absolute result, `RepoNotFoundError` when nothing is found.
3. An explicit override (the `explicit` param — the path `--repo`/`AIDW_REPO` will later supply) wins over cwd walk-up: when `explicit` is given, `start`/cwd is ignored entirely. Validate the override in this order: (a) `.resolve()` it to an absolute path; (b) reject a nonexistent path and a non-directory (file) with `RepoNotFoundError` naming the override path **before any walk-up** — a file override must never resolve to its parent repo, and a nonexistent path under a repo must never walk up to the enclosing repo; (c) otherwise run the Requirement 2/4/5 git semantics (`--show-toplevel`, then the `.git` walk-up fallback, `--absolute-git-dir`, `--git-common-dir`, bare check) with the override directory in place of cwd — not `repo_root()` applied verbatim, whose subprocess cwd crashes on a file path (`NotADirectoryError`, uncaught in `paths.py:27-44`) and whose fallback loop would walk a nonexistent path up to an enclosing repo. An override pointing at a subdirectory of a working tree resolves up to that tree's root; a bare override raises the bare-specific refusal (Requirement 5); a non-repo directory override raises `RepoNotFoundError` whose message names the override path. An invalid override **raises, never falls back to cwd** — a typo'd or non-repo `--repo` must not silently operate on the cwd repo. Do not read env vars or touch the CLI in this task (that is E1.5).
4. Derive `git_dir` from `git rev-parse --absolute-git-dir` and `common_dir` from `git rev-parse --path-format=absolute --git-common-dir` (prompt-fixed: plain `--git-dir` prints a relative `.git`; §3.2 pins `common_dir`).
5. Reject the bare dir with a distinct, actionable error: when `--show-toplevel` fails, check `git rev-parse --is-bare-repository` and refuse with a message naming "bare repository" and telling the user to run from a worktree. The refusal must be a distinct subclass of `RepoNotFoundError` (e.g. `BareRepositoryError(RepoNotFoundError)`) — never plain `RepoNotFoundError`, never a sibling exception type, and never let the walk-up fallback swallow it into the generic "Not inside a git repository" message — so `except RepoNotFoundError` handlers (`doctor.py:266`) keep reporting FAIL instead of crashing.
6. `base_branch` defaults to `"main"` (the §3.4 `repo.base_branch: main` value). It is a field only — no YAML/config loading here; E3.1 supplies it from config later and may change only its source, not the field.
7. This task is additive: keep `repo_root()`'s public behaviour unchanged (signature, `.resolve()`d absolute result, `RepoNotFoundError` for a non-repo path) so existing call sites (`cli.py:_roots`, `doctor.py:266`, config's `repo_root` param) keep working. Consumer porting is E1.4/E1.5.

Traps / prior review findings:
- In a linked worktree `git_dir` != `common_dir`; in a plain clone they are equal. Tests must build a real bare repo + `git worktree add` linked worktree, not `git init`, or the two fields can't be told apart. (E2.9 later shares a fixture; don't block on it.)
- `git rev-parse --show-toplevel` exits 128 in a bare repo ("this operation must be run in a work tree") and a bare dir has no `.git` entry, so the current `repo_root()` fallback would raise the generic "Not inside a git repository". Detect bareness before that path.
- `doctor.py:262` catches only `RepoNotFoundError`; if the bare-repo refusal raises a new exception type, `aidw doctor` run from a bare dir crashes instead of reporting FAIL — subclass `RepoNotFoundError` (the distinct bare subclass from Requirement 5) so the existing handler still catches it.
- `git rev-parse --git-dir` prints a relative `.git`; `--absolute-git-dir` is the field value. Mixing them yields a `git_dir` wrong relative to cwd.
- Keep `.resolve()` on every returned path: downstream (`report.rel_to`, config `_resolve`) assumes absolute resolved paths.
- "Requirements 2, 4, 5" means their git semantics, not `repo_root()` applied verbatim: its fallback loop iterates `(start, *start.parents)`, so a nonexistent path under a repo would silently resolve to the enclosing repo, and `subprocess.run(cwd=<file>)` raises `NotADirectoryError`, which the `except (CalledProcessError, FileNotFoundError)` clause (`paths.py:27-44`) does not catch. The explicit pre-walk-up validation in Requirement 3 exists precisely to make file/nonexistent overrides raise the named `RepoNotFoundError` instead.
