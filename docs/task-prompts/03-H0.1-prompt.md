Task: Keep gate outcomes across stage boundaries.

Requirements:
1. One owner for the state file. The roadmap offers two mechanisms: (a) an append-only outcome log per run that `aidw gate run` appends to and every citation reads, or (b) a merge-on-write of `gate_outcomes` under a cross-process file lock, published with `os.replace`. Choose one, implement it, and record the choice plus rationale as a new decision row in design.md §17. Either choice must satisfy items 2–4.
2. Atomic publication: no reader may ever see a half-written `state.json` — full-state writes go through the atomic-rename pattern: write the full payload to a temp file created **in the same directory as `state.json`** (`os.replace` is atomic only within one filesystem — a temp file in `/tmp` is an EXDEV failure or a non-atomic cross-device move, reopening the torn-read window), fsync it, then `os.replace` it over `state.json`; never the current `write_text` in `aidw/state.py:save`.
3. Symmetric merge — neither writer drops the other's rows: (i) a gate outcome the agent's `aidw gate run` subprocess appended must survive the workflow's next `save()` (today the in-memory `RunState` loaded at `create_run` rewrites the file — the core loss); (ii) a stage record the workflow wrote must survive a later CLI `aidw gate run` write.
4. Cross-process serialization: `aidw/runner.py:_STATE_LOCK` is a `threading.Lock` and does not serialize separate `aidw gate run` processes. The read-modify-write of gate outcomes must serialize across processes with a **per-run lock file colocated with `state.json` in the run directory** — `<run_dir>/state.json.lock` — never under `locks/` and never keyed by worktree path: the workflow process already holds that worktree lock for the whole run, so a worktree-keyed state lock would refuse every `aidw gate run` subprocess — the conflation §9.1 forbids. Reuse `aidw/lock.py`'s `fcntl.flock` LOCK_EX|LOCK_NB pattern (open fresh per acquire, never unlink) or an equivalent, and hold it around each writer's whole read-modify-write, never around a bare write — under mechanism (b) the reload/merge/write of `state.json` in the workflow's `save()` (Requirement 3) and the load/append/write of the CLI gate-write path; under mechanism (a) the CLI's append to the outcome log.
5. Citation reads merged outcomes: `verification.run_gate`'s reuse path (`RunState.gate_outcome(key, tree)`) and `aidw gate list` / `aidw runs show` must see outcomes recorded by a subprocess, including after the run process has exited. The reuse rule itself — same key + tree + command + declared scope + `passed` → cite, anything else → run — is unchanged.
6. Amend design.md §9.2's `gate_outcomes` paragraph and §14 to state who writes the file under which lock, naming the Requirement 4 lock file. Keep `aidw/state.py:GateOutcome`'s field names and the `gate_outcomes` list in `state.json` unless your chosen mechanism forces a documented change, in which case update the §9.2 schema example too.
7. Update `docs/tasks/00 - Extraction.md` E4.8's "Progress" line to name the gate-outcome survival gap that H0.1 closes, instead of leaving the box ticked with the gap buried in a trailing sentence.
8. Change neither which stages gate nor what a red gate stops.

Traps / prior review findings:
- Rejected design: "read the file at the moment of the decision" (H3.2's earlier wording) — it answers the tick but leaves every agent-side citation broken, because `pr` citations are read during the agent's own stage. Do not use it.
- Rejected design: retry the failed gate — E4.8's rule is cite-or-run, and a re-run buys the same answer for the same tree.
- The loss is symmetric: fixing only the workflow's `save()` still lets a concurrent CLI write drop a workflow stage write, and fixing only the CLI still lets the workflow's stale in-memory save drop gate outcomes. Both directions need tests.
- Dedup hazard: when merging `gate_outcomes`, do not collapse two concurrent distinct outcomes (Done-when 3 requires both survive) — "newest wins per key" is wrong here because both processes ran the command.
- `fcntl.flock` details: open the lock file fresh per acquire and never unlink it (unlinking races a second acquirer onto a new inode — see `aidw/lock.py` module docstring).
- The current suite is green for the wrong reason: `tests/test_verification.py` drives `verification.run_gate` with an in-memory `RunState` or fakes a stage via `AIDW_STAGE` alone, so the workflow `save()` round trip is never exercised. Tests (what to prove, not literal expects):
- Round trip: load the workflow's `RunState` before the gate, run `cli.invoke(app, ["gate", "run", …])` against the same run so the CLI subprocess appends an outcome, then perform the workflow's next save through that stale pre-gate handle (`run_stage` or `state.save` on that same object — no reload in between); assert the CLI-appended outcome is still present and unchanged (the stale-handle save-after-gate round trip, Requirement 3(i), not the write itself).
- Citation chain: gate `test` passes for tree `T`; `record` and `pr` cite it with the command executed once — a counter file outside the repo proves the execution count (E4.8's technique, already in `test_a_run_cites_the_suite_across_the_record_stage_and_reruns_after_a_code_edit`).
- Concurrency: a threaded pair of `cli.invoke(app, ["gate","run",…])` against one run with distinct gate keys or commands (or `--force`) — identical key + tree + command + scope reuses and records nothing (Requirement 5's unchanged rule; `test_cli_gate_run_records_into_the_env_run` pins one row after two identical runs); both distinct outcomes survive.
- Overlap integrity: a stage record already on disk, a CLI `gate run` write overlapping a workflow `save()`, and a concurrent reader that does not take the state lock (Requirement 2's atomic publication, not the lock, must keep unlocked reads whole) looping load/parse of `state.json` through the window — every observed read must parse and retain the stage record; the final both-rows-present assertion is in addition to those observed reads, never a substitute for them.
- Post-exit reporting: `aidw gate list` and `aidw runs show` report the outcomes after the run process exits.
- Purity/fail-closed: the existing fail-closed paths (unresolvable base, no run, a failed outcome never cited) stay green unchanged.
