Task: One run per worktree — move the run lock into the state root, keyed by worktree path

Requirements:
1. Lock primitive. New `aidw/lock.py`: an exclusive, non-blocking, cross-process lock living at `workspace.state_root / "locks"` (§3.10). Acquire refuses immediately when the key is already held; release returns the key to free. stdlib only — no new dependency, `uv.lock` unchanged. prompt-fixed mechanism: `fcntl.flock` with `LOCK_EX | LOCK_NB` on a lock file opened fresh per acquire — flock auto-releases on process death (no stale-lock cleanup), and `LOCK_NB` makes a held lock fail fast instead of hanging a non-interactive run (the `aidw/git.py` fail-fast convention).
2. Key = resolved worktree path, not branch. The key is the path passed to `create_run` as `repo_root`: prompt → `target.root` (the re-resolved task worktree), implement/fix → the located worktree after `TargetRepo.resolve`, review/approve → `repo.root` — constrained differently per workflow: review refuses unless the current branch equals the PR head, so its `repo.root` is reliably the task worktree; approve resolves no worktree (unlike implement/fix), so its key is the invocation worktree by design — same-cwd concurrent approves refuse, different-cwd approvals both proceed (the roadmap's "two runs in different worktrees proceed", not a "one run per worktree" violation). Derive a deterministic, filesystem-safe lock filename from that resolved absolute path (worktree paths contain `/` and can't be a flat filename — §3.10's `<branch>.lock` is shorthand, valid only under the one-branch-one-worktree fact). Two different worktrees must never share a lock file, and a detached-HEAD worktree must still get its own.
3. Acquire/release in every workflow's `run()`. Wire `prompt`, `implement`, `review`, `fix`, `approve`: acquire immediately before `create_run` (where the key is final) and release on every exit path after it — success, failure, and any post-acquire refusal — via a context manager or `try/finally`. `create_run` is the start of a run; dry-run reaches it too (a dry-run reaches `create_run`, which saves `state.json` unconditionally — `aidw/state.py::create_run`, on every workflow's dry-run path; design §15's "performs no writes" line is stale for run state — §16 Phase 2 records "a `--dry-run` stage writes `state.json`"), so dry-run acquires and releases the same way. No `state.json` schema change — the lock is a filesystem mutex, not recorded state. `aidw/workflows/run.py` acquires nothing itself: it delegates in-process to `prompt.run` then `implement.run`, each holding and releasing its own lock.
4. Refusal contract. A held lock prints a message naming the worktree path and that another run holds it, and returns exit 4 (preflight/safety refusal, design §14) — before `create_run`, leaving no run state behind (the same fail-closed contract as E2.6's missing-worktree refusal).
5. Keep the resume guard. `_latest_implement_run`/`_latest_fix_run` stay branch-keyed and unchanged: they are the `--resume` / "finish it" path for a *crashed* run left `status == RUNNING` (flock has already released). The lock closes the race where the second process's still-running check reads `state.json` before the first has written it. Don't delete or re-key them.
6. Don't conflate with `--parallel` / `_STATE_LOCK`. The run lock is one-per-run (the whole workflow), never per-stage; `_STATE_LOCK` (`aidw/runner.py`) still serializes `state.json` writes between concurrent stages *inside* one run. §3.2 says "do not conflate the two."
7. Concurrency test (the deliverable). See Tests.

Traps / prior review findings:
- Reusing `threading.Lock`/`_STATE_LOCK` for the run lock → it is in-process only, so two `aidw implement` processes both proceed. The test must prove exclusion across a process boundary (or at least two separate `open()` file descriptors).
- Caching the lock fd per key (a module-level dict) → flock is per open-file-description, so two threads in one process share the cached fd and both "acquire"; the thread-based workflow test passes while real two-process exclusion is broken. Open fresh per acquire.
- Keying by branch (mirroring `_latest_implement_run`) → a detached-HEAD worktree has no branch and bypasses the lock; §3.2 and the roadmap both say "worktree path". Use the resolved path from `TargetRepo.resolve`/`git.worktree_for_branch`, not the branch name.
- `O_CREAT|O_EXCL` + a PID marker instead of flock → a crashed run leaves a stale lock that blocks every later run until hand-deleted. flock's auto-release on process death is why the lock can be "one active run" without cleanup.
- Placing the lock under a worktree or target repo (e.g. `<repo>/.aidw/locks`) → §3.1 "nothing generated is ever written into a target repo", and `git worktree remove` deletes it mid-run. It must be `workspace.state_root / "locks"`.
- Forgetting to release on a mid-run refusal (a gate refusal or PR-publish failure after `create_run`) → the worktree stays locked until the process exits. Wrap the whole post-acquire body, not just the happy path.

Explicit non-goals — do NOT do these in this task:
- E2.8 doctor worktree/git checks — a doctor check for lock health/leftovers is separate; don't add one.
- E2.9 shared worktree fixture — separate; build local bare+worktree helpers in the tests (mirror `tests/test_worktree_cli.py::_make_bare_with_control`).
- Re-keying the resume guard to worktree path, or merging it into the lock — resume is found by branch; leave `_latest_implement_run`/`_latest_fix_run` as-is.
- A whole-repo/global lock, read-write (shared) locking, or a lock in `run.py` — §3.2 specifies "one run per worktree" and nothing more; don't invent.
- Windows/non-POSIX support — macOS/Linux only (E2.1); `fcntl` is fine.

Tests (what to prove, not the literal expects):
- Primitive, cross-process (`tests/test_lock.py`): build a real bare+worktree repo so two real worktree paths exist; a subprocess acquires the lock for worktree A and holds it (signals readiness); the parent's non-blocking acquire for A is refused; the parent acquires and releases B; after the A-holder exits, the parent re-acquires A — proving auto-release with no stale lock left behind.
- Workflow refusal, one test per key path — each workflow derives its key independently (req 2), so a wrong key in one passes an implement-only test. Hold the first run with fake `run_stage` blocking on an event (as the existing tests fake it); the refused run exits 4 before `create_run` and leaves exactly one run directory.
  - implement/fix (located-worktree key): two concurrent `implement.run` calls on the same located worktree; two on different worktrees both exit 0. Same refusal for `fix.run` on the same re-resolved PR-head worktree — a lock keyed on the pre-re-resolve control root instead must fail this test.
  - review/approve (invocation-cwd `repo.root` key): two concurrent `review.run` calls from the same repo root, and likewise two `approve.run` calls.
  - prompt (task worktree created in-run): `git.add_worktree` precedes acquisition, so a second `prompt.run` on the same branch is refused by git's one-branch-one-worktree rule before the lock could contend — the prompt lock excludes a concurrent implement/fix/review/approve started in the just-created task worktree, not a second prompt. Prove the wiring, not prompt-vs-prompt contention: while the author stage is held, the test's own non-blocking acquire of the task-worktree key is refused; after `prompt.run` exits it succeeds.
  Real bare+worktree repos, no real Pi model.
- Purity/fail-closed: acquiring and releasing writes nothing under the worktree; the only lock file is under `workspace.state_root / "locks"`; a refusal creates no run state.

If anything in the cited spec section is ambiguous or underspecified for this task, stop and ask rather than guessing — especially:
- the lock mechanism is prompt-fixed: `fcntl.flock`, non-blocking, fresh fd per acquire, auto-release on death. If a blocking (wait-for-release) lock or an `O_EXCL`+PID scheme with stale detection is wanted, say so.
- the lock filename encoding is prompt-fixed: deterministic from the resolved worktree path. If keying by branch is actually intended (accepting the detached-HEAD gap), say so.
- the refusal exit code is prompt-fixed: 4 (preflight/safety refusal), matching the existing still-running refusal and design §14; no run state on refusal. If exit 3 ("blocked, needs human") is wanted, say so.
- the lock covers dry-runs too (dry-run reaches `create_run` and writes `state.json`) — prompt-fixed; if dry-runs should never hold the lock, say so.
- applying the lock to all five workflows (prompt/implement/review/fix/approve) is the reading of "one run per worktree"; if only implement/fix should lock, say so.
- anything security-sensitive, cost-committing, or hard-to-reverse (cross-account trust, schema changes, billing logic, data deletion).
