Task: Stage registry and workflow definitions as data — turn the current hardcoded chains (`aidw/workflows/implement.py:build_plan`, `prompt.py` run loop, `review.py` R1/R2, `fix.py` iteration stages, `approve.py` STAGE) into declarative defaults keyed by workflow and stage id, keeping the existing ids (I1…I6, P1, R1, R2), reproducing today's order exactly including the post-phase-02 prompt loop (one `task-review-reconcile-N` per fix batch, review-only terminal review).

Requirements:
1. New module `aidw/stage_registry.py` holding the default stage definitions and per-workflow chains as data, keyed by workflow name and stage id. (prompt-fixed path: design.md §3 puts toolkit code under `aidw/`; a dedicated module is importable by both `target_config` and the workflows without a cycle — `target_config.py`'s docstring forbids importing workflow modules, and E4.3 will make `implement.py` import the registry, so the registry must not import back.)
2. Stage-id vocabulary (R6): registry keys are the retained ids — I1–I6, P1, P2, R1, R2, F1–F4, A1 — matching design.md §8.1–§8.5 and EXTRACTION.md §3.5. The prompt loop's fix and reconcile stages are expressed inside the loop descriptor (Requirement 6), not as flat ids. `P2a` is §8.1's diagram id only — the runtime stage names match `prompt.py`'s run loop and are never `task-prompt-fixes-*`: per-finding/combined `task-review-fixes-{revisions}-{index}`, the unparseable-review fallback `task-review-fixes-{revisions}` (no index suffix), and the per-batch `task-review-reconcile-{review_index}` keyed on the review round. Do **not** adopt §3.4's YAML-example ids (`author`/`review`/`implement`/…) — those illustrate the *schema shape* only; R6 says ids are retained, not renamed to semantic ids.
3. Every stage definition carries the §3.5 `PlanStage` fields exactly: `id`, `name`, `agent`, `prompt_file` (toolkit `prompts/<name>.md`), and `variables` (the `$1..$n` positional tokens, design.md §7.3/D2). The `implement` default must reproduce `aidw/workflows/implement.py:build_plan` **byte-for-byte**: six stages I1–I6 in order, each with identical id/name/agent/prompt filename/variables — e.g. I1 `impliment-task`/`implementer`/`impliment-task.md`/`[prompt_rel]`, I4 `update-architecture`/`implementer`/`update-architecture.md`/`[branch, base_branch]`, I6 `pr`/`pr-publisher`/`pr.md`/`[task_id]` — **including** I2's `extra` (`_TEST_CONTEXT`). Also record the default `parallel_groups` pair — `[test, update-architecture]`, the two stage *names* in today's `implement.py` `by_name` lookup (R11/E4.4) — as workflow-level data.
4. The `prompt` default reproduces the post-phase-02 loop (design.md §8.1 + decisions H6/G2/L4.1): P1 author (`task-prompt`, task-author, `[phase, epic, task]`); per review round P2 (`task-review-N`, task-reviewer, `[rel]`); fix stages `task-review-fixes-*` (task-fixer — one per blocking finding, one combined could-fix, single fallback); exactly one `task-review-reconcile-N` per fix batch (task-fixer) before the next review; final round review-only (terminal review, nothing after it). Match `aidw/workflows/prompt.py` run loop.
5. `review`/`approve`/`fix` defaults: R1 `code-review` (code-reviewer), R2 `review-findings-to-github` (review-publisher) conditional on R1 findings; A1 `approve-review-followups` (review-approver); fix loop F1 `fix-next-review-followup` (fixer), F2 `test` (tester), F3 `code-review` (code-reviewer), conditional F4 — reproducing today's `iterN-`-prefixed stage *names*. Match `review.py` R1/R2, `approve.py` STAGE/AGENT/PROMPT, `fix.py` iteration tuples.
6. Dynamic-loop representation (prompt-fixed): prompt and fix chains are bounded loops with conditional stages — a flat list cannot express them. Represent them with a minimal declarative loop/terminal/conditional shape (consistent with design.md §8's `⟳`/`if` notation) plus one pure, deterministic expand/render helper (name prompt-fixed) yielding the ordered stage list for concrete inputs (`max_revisions`, finding partition, iteration). Label the choice `prompt-fixed` in the module docstring.
7. No behaviour change: this task adds data + a pinning test only. Do not edit `aidw/workflows/*` runtime paths, `resolve_config`, `ConfigDefaults.workflows`, or any prompt/agent-config; `uv run --frozen pytest` stays green with no test deselected.

Traps / prior review findings:
- Circular import: don't import `PlanStage` from `aidw/workflows/implement.py` — E4.3 inverts the dependency (`implement.py` → registry). Define the registry's own stage type, or move `PlanStage` to a low-level module that neither workflow nor `target_config` imports upward.
- `PlanStage.id` (`"I1"`) and `PlanStage.name` (`"impliment-task"`) are different fields; key on id, reproduce both, and R6 forbids semantic ids — §3.4's example ids (`author`/`review`/`implement`) are illustrative, not the default ids.
- The `extra` text — I2's `_TEST_CONTEXT`, F2's `_TEST_EXTRA`, R2/F4's `MANIFEST_EXTRA`, prompt's `_render_delta_brief`/`_render_reconcile` — is runtime-rendered in the workflow modules and is part of "byte for byte"; if the registry drops it, the pinning test under-asserts and E4.3 would silently change rendered prompts.
- The prompt loop's stage count is data-dependent (findings count, `max_revisions`); flattening it into a fixed list silently drops the reconcile-per-batch and terminal-review semantics (H6/G2/L4.1).
- `fix.py` uses `iterN-`-prefixed stage *names* (`iter1-fix-next-review-followup`, `iter1-test`, `iter1-code-review`), not literal F1/F2/F3 — F1–F4 are logical ids; reproduce the `{prefix}-…` names, not `"F1"`/`"F2"` strings.
- Don't half-wire `ConfigDefaults.workflows`/`resolve_config`: the config `StageConfig` is `{id, enabled, prompt, agent}` (E4.6 adds model/thinking/timeout) and cannot carry `name`/`prompt_file`/`variables` — the registry and the config-merge slot are different shapes; wiring the merge is E4.3's.
