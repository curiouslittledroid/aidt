Task: Withhold the PR when the tester's in-scope verdict is `Fail` (Design 8.2)

Requirements:
1. Per roadmap Q1.1 + §8.2: `implement` must not run `I6 pr` (and must open no PR) when the
   `I2 test` stage's final message reports `Fail` for any in-scope acceptance criterion. The
   workflow parses the verdict and decides, the way §8.3 parses R1's verdict — the tester's
   stage still exits 0 and stays `SUCCEEDED`, so this is a message-content check, not a
   stage-status check.
2. Add a machine-parseable verdict block to `prompts/test.md` (its "Return"/"Final response"
   sections): a bare declaration line `Test verdict: Pass` or `Test verdict: Fail`, and on
   `Fail` a following `Failing in-scope criteria: <comma-separated criterion IDs/wording>`.
   Capitalised tokens, bare line — no heading, code span or fence (match §18 M3's
   `Verdict: Approve` rule). `Fail` iff an in-scope criterion failed; `Unverified`, out-of-scope
   and pre-existing/unrelated failures stay in the per-criterion report and never make the
   verdict `Fail` — make that separation explicit in the per-criterion block (e.g. a `Scope:`
   line) so a human can audit it; the parser reads only the verdict block.
3. The gate is an imperative check in `aidw/workflows/implement.py`, placed after the pre-pr
   loop (I1..I9, I7, on both the serial and `--parallel` paths) and before the
   `approve-implementation-pr` gate — no new stage id, no registry `when=` token, and no
   `--dry-run` evaluation (the dry-run path already returns before the gate section).
4. Reuse §8.3/§18's parse shape: a pure helper (e.g. `_parse_test_verdict(text)`) that blanks
   fenced code blocks first, reads the bare `Test verdict:` declaration line, rejects code spans,
   and returns `("Pass", [])` / `("Fail", [criteria...])`, or `None` when no declaration parses.
   The helper is pure (no I/O, no mutation) and lives in implement.py, not verdict.py.
5. Fail closed: a `Fail` verdict or an unparseable verdict (`None`) each stop the run with
   `state.status = BLOCKED` and exit 3 before the gate/I6, mirroring `review.py`'s
   `verdict is None` / `Blocked` handling. A missing/empty `out` hits that same branch: the gate
   reads the recorded `test` out.txt via `_read_out` on fresh and resumed runs alike — a fresh-run
   I2 empty final message exhausts the U1 retry and still records a SUCCEEDED stage with no
   out.txt (`runner.py` leaves the empty-final-message case to the workflow to fail, H1.1, and
   `implement.py`'s `execute()` checks only stage status — do NOT expect exit 1 there the way
   `review.py` fails an empty R1 message), and a resumed run can have a SUCCEEDED `test` record
   whose out.txt is absent. Empty text parses to `None`, so both stop BLOCKED/exit 3 naming the
   ambiguity. A `Fail` records
   `state.pr["test_verdict"] = "Fail"` and `state.pr["test_failing_criteria"] = <criteria>` and
   prints the failing criteria to stderr; an unparseable verdict names the ambiguity
   instead. Both stop messages must state the forward path: a plain `--resume` skips the
   already-SUCCEEDED I2 (`should_run`, implement.py) and re-reads the same recorded verdict, so
   it repeats this stop identically while the verdict is unchanged — that repeat-stop is
   correct, not stuck — and re-testing requires `--from test` (with `--resume` to stay in the
   same run), which overrides §9.4's completed-stages-never-rerun rule and re-runs I2 and
   everything after it.
6. A `Pass` verdict proceeds to the gate and I6 unchanged; record `state.pr["test_verdict"] = "Pass"`.
7. Update design.md §8.2 (a bullet on the I2 verdict gate, including its resume rule: a plain
   `--resume` re-reads the recorded verdict and repeats the stop; `--from test` re-tests) and
   §17 (row Z10), recording the prompt-fixed decisions named in the closing clause the way
   Z2/Z9 record "spec fixed only the shape".

Traps / prior review findings:
- The verdict is in I2's *message*, not its stage status: the tester exits 0 and reports `Fail`
  in prose, so a `record.status == SUCCEEDED` check lets a Fail through. Read the message via
  `implement.py:_read_out(record)` from `state.stage("test")`, exactly as review.py does.
- `fix`'s `F2 test` uses the same `prompts/test.md` (`stage_registry` `_FIX`, name `iter{N}-test`)
  and will now emit the verdict block; `fix.py` reads only the record *status*
  (`is_test_stage`/`tick_evidence`), never the message. Adding the block must not break fix, and
  you must not add a fix-side parse here.
- Blank fenced code blocks before matching (M1): the test prompt's own "Return" section shows the
  block as a fenced example — a naive regex reads the *example* as the verdict. The declaration
  is a bare line the tester emits; the parser must reject the fenced sample (E4.5b/M1's lesson).
- The resume path re-reads I2's recorded `out.txt` via `_read_out`; key the check off the recorded
  stage, not a live run only, or a resumed run would skip the verdict and reopen the PR. The flip
  side: a plain `--resume` also skips the SUCCEEDED I2, so it re-reads the same recorded `Fail`
  and stops again identically — that repeat-stop is the intended resume semantics (the existing
  approve-gate denial has no such problem because a human re-decides the gate), and the stop
  message must name `--from test` as the way to re-test, or the first real Fail presents as a
  dead end where every `--resume` exits 3 with no distinction between "stuck" and "working
  as intended".
- A missing `Failing in-scope criteria:` line on a `Fail` verdict is still `Fail` (stop); the
  criteria list is best-effort naming — don't turn it into "ambiguous".
- The tick runs before this gate: with green gates but an inspection/browser-only Fail, I7 can
  still flip the checkbox (uncommitted). That is acceptable — I6 is the only committer and never
  runs — but don't "helpfully" also withhold I7; the roadmap scopes the stop to I6.

Explicit non-goals — do NOT do these:
- Don't add a test-verdict gate to `fix` (F2) or change fix.py's convergence rules — Q1.1 is
  `implement` withholding the PR only.
- Don't stop earlier than "before I6" (e.g. abort before I3–I9): the roadmap scopes the stop to
  withholding I6; don't rework the serial/parallel dispatch to fail fast after I2.
- Don't touch `stage_registry.py`, `docs/workflow-stages.md`, or add a registry `when=` condition
  — S1.1's `WHEN_PATHS_CHANGED` is a separate task; this check is an imperative workflow gate.
- Don't change the tester's exit-code behaviour or add a prompt/agent (`REQUIRED_PROMPTS` unchanged).
