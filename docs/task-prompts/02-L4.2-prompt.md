Task: Record what was accepted and what it cost (Design 9.2, Design 9.3)

Requirements:
1. Accumulate per-round telemetry in the loop in `aidw/workflows/prompt.py`: for each review round record `(review_index, findings_count, fix_stage_count)`. `findings_count` is `len(findings)` from `parse_review_findings` on every round, fallback included — 0 only when nothing parsed (a partial-parse fallback keeps its count: `parse_review_findings` collects malformed blocks as findings too, so 2 clean + 1 malformed records `findings=3`); `fix_stage_count` is the number of `task-review-fixes-*` stages that round actually ran — `len(blocking) + (1 if could_fix else 0)` from `partition_findings`, or 1 on the whole-review fallback, 0 on the terminal review (L4.1 runs no round-3 fix batch).
2. Build one summary string from that telemetry at each verdict-bearing loop exit, as named `key=value` pairs continuing the existing `detail` style: `verdict=<Approve|Request changes|Blocked|ambiguous>`, `revisions=<fix batches>`, `rounds=<review rounds run>`, `findings=<per-round counts>`, `fixes=<per-round fix-stage counts>`, `approved=<yes|no>`, `fixes_after_last_review=<yes|no>`. Two renderings are fixed, not the implementer's: a `parse_verdict` `None` renders `verdict=ambiguous` (the existing `verdict or 'ambiguous'` convention, reachable at the terminal fall-through), and `approved=yes` iff the final verdict is `Approve` — the roadmap deliverable's "whether the final verdict approved" — so the human-deny exit records `approved=yes` beside `decision=denied` (the reviewer's verdict and the human's refusal each keep their own field). Factor it into one helper so the gate `detail`, run.log and stdout cannot drift.
3. Record the `approve-task-prompt` gate record on **every verdict-bearing** review-loop exit — approve, human-deny, terminal Request-changes, Blocked. The approve/human-deny path keeps `decision=approved|denied` as today but the `detail` becomes the full summary (today it is only `verdict=…; revisions=…` at `prompt.py` `detail=f"verdict={verdict}; revisions={revisions}"`). The terminal Request-changes and Blocked-verdict exits now record `approve-task-prompt` with `decision=denied` and the same summary in `detail`. *(Prompt-fixed: `denied` is existing gate-decision vocabulary and "the gate failed closed" is truthful; this reverses L4.1's "no gate record", so revise L4.1's two tests that assert gate absence.)* No new decision word — the verdict travels in `detail`. Exits with no verdict record **no** gate: the author-blocked report, a failed author/review/fix/reconcile stage, an empty review, a missing prompt file — no review outcome exists there, and a `denied` would claim one that never happened.
4. Write run.log lines on every verdict-bearing exit carrying the same summary, and add the missing `logger.error` on the terminal Request-changes branch (it currently prints to stderr only, so run.log is silent on the exact symptom L4.2 exists for). A run that ends BLOCKED must say so in run.log. The no-verdict exits write no summary line: they keep today's `status` (`FAILED`; `BLOCKED` on the author-blocked path) and today's logging (the empty-review and author-blocked `logger.error` lines included) — add no gate or summary there.
5. Print per-round counts to stdout (the stage report): a per-round line naming the round, findings count and fix-stage count, in addition to the existing `verdict: … — findings_summary` and `fix N.M/total:` lines.
6. `fixes_after_last_review` is the L4.1 invariant: it must be `no` on every path because the terminal review is review-only. Derive it from the telemetry (the last review round's fix count is 0), never hardcode a constant — recording it proves no unreviewed fix shipped.
7. Observability only, per the roadmap Notes: no new `status`/`decision`/verdict vocabulary (`decision` stays ∈ `approved`,`denied`; `status` stays `blocked`), and no cost/round-count/latency gate or threshold. `totals` already aggregates cost (§9.2) — do not add a separate cost field or acceptance check.

Traps / prior review findings:
- The terminal Request-changes branch (`if revisions >= MAX_REVISIONS - 1:` → `return 3`) has no `logger` call and no gate record — add both there, not only on the approve path, or the Done-when stays unmet for the run L4.2 targets.
- Recording only on the approve path leaves a BLOCKED run's verdict reachable only via stage `.out.txt` — the gate record must be written on the terminal and Blocked exits too, with `decision=denied` (not a new value).
- Counting fix stages from `state.stages` names after the fact instead of the in-loop counter — the fallback round runs 1 stage while a parsed 3-finding round runs 3; the counter set inside the loop is authoritative.
- Turning the new record into a success: the terminal/Blocked branches must still `return 3` with `status=BLOCKED` and the findings on stderr — add the record, do not change the exit code or the `Approve`/`Blocked` short-circuits (L4.1).
- Keying `fixes_after_last_review` off `revisions` (fix batches) rather than the terminal round's fix count — post-L4.1 the terminal round never increments `revisions`, so `revisions` understates the round count; use the per-round fix counts.
- Using a new `decision` value (e.g. `"blocked"`) to carry the verdict violates "no new gate-decision vocabulary" — verdict lives in `detail`, `decision` stays `approved`/`denied`.

Explicit non-goals — do NOT do these in this task:
- L4.3 (`--max-revisions` flag / `max_revisions` config key) — the next task; add no config surface or flag here.
- L6.1 (synthesized fixture pinning the whole loop contract) and L6.2 (consolidating §17 decisions + re-baselining E4.1/E4.3) — later; this task records data, it does not edit design.md §17 or `docs/tasks/00 - Extraction.md`.
- The author-blocked (L1.3) path is out of scope for the gate record: it has no review rounds or verdict; it already records `status=blocked` + a run.log line. Do not add an `approve-task-prompt` record there.
- Do not turn the summary into a gate, threshold, or cost/latency acceptance criterion (phase preamble "Explicit non-goals for phase 02").
