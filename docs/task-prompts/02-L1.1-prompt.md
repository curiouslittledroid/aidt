Task: `aidw prompt` must fetch before it authors anything, and refuse to run when the base branch is behind its remote. A run that starts on a stale base authors a prompt against a tree that lacks a merged prerequisite — exactly the E1.6 failure, where the prompt commit's parent was the pre-E1.5 commit while the E1.5 merge was already on `origin/main` and the local base had never been pulled.

Requirements:
1. `aidw/git.py` gains `fetch(repo, remote="origin", *, timeout=30) -> tuple[bool, str]` (whether the fetch succeeded, plus a short failure reason) and `is_ancestor(repo, ancestor, descendant) -> bool | None` (`git merge-base --is-ancestor`; `None` when git cannot answer). Reuse `_git_out`, adding a `timeout` parameter that defaults to `None` so existing callers are unchanged. The fetch updates remote-tracking refs, so correct the module docstring's "the read helpers never change git state" claim rather than leaving it false.
2. Place the check in `aidw/workflows/prompt.py:run`'s preflight block — **after** the existing current-branch and clean-tree checks, and **before** the config load and `create_run`. A refused run must leave no run directory, no `{phase}-{task}` branch and no prompt file, which is the guarantee today's two refusals already give.
3. Fetch `git fetch origin` (the whole remote, so `refs/remotes/origin/<base>` is guaranteed current — do not rely on a partial-fetch refspec), then compare `aidw/paths.py:TargetRepo.base_branch` against its remote-tracking ref with `git.rev_parse`, and use `is_ancestor` for the direction. Consume the typed `TargetRepo.base_branch`; introduce no second literal `main`, and leave the existing current-branch check exactly as it is (E2.5/E3 own base-branch configurability).
4. Pin all six outcomes, each reported on stderr:
   - equal revisions → proceed, no output;
   - local is an ancestor of `origin/<base>` (behind) → refuse with `EXIT_REFUSED` (4), naming both revisions and the corrective `git pull --ff-only` in the base worktree;
   - neither is an ancestor (diverged) → refuse with `EXIT_REFUSED` (4), naming both revisions and telling the operator to reconcile the base branch with its remote first; suggest no destructive command (design §13);
   - `origin/<base>` is an ancestor of local (ahead: unpushed commits on the base branch) → warn and proceed;
   - `origin/<base>` cannot be resolved (no `origin`, or never fetched) → warn that freshness could not be verified, and proceed;
   - the fetch itself failed → warn, naming the remote and git's failure kind, then run the comparison against the last known `origin/<base>`.
   The fetch outcome never decides the verdict on its own — only the comparison does, so an offline run still catches a provably stale base.
5. The fetch must be non-interactive and bounded: `GIT_TERMINAL_PROMPT=0` in its environment and the timeout above, whose expiry counts as a failed fetch.
6. `--no-fetch` (a `aidw/cli.py` option threaded as `no_fetch=` into `prompt_workflow.run`) skips the fetch **and** the comparison and warns that the base branch was not verified. It is the only way past the check; nothing else bypasses it.
7. `--dry-run` performs no fetch and no comparison — dry-run must stay hermetic, and the existing dry-run test stubs no git call — and prints a one-line note that a real run will fetch and verify the base branch.
8. No warning or refusal may echo a remote URL that carries credentials: redact userinfo (`user:token@`) if git's message contains the URL, and name the remote and the failure kind instead. These messages are operator-facing on stderr and get copied into issue reports and terminals, and a refusal happens before `create_run`, so there is no run log to redact after the fact.
9. Docs: add `[--no-fetch]` to the `aidw prompt` usage line in design.md §14, and one sentence to §8.1's preflight description stating the fetch-and-refuse behaviour. Do not restate the stage chain and do not open a design.md §17 entry — phase 02's L6.2 consolidates this phase's design decisions.

Traps / prior review findings:
- The existing full-run tests build a repo with **no `origin`** and patch only `git.current_branch`/`git.is_clean` (`_patch_prompt_repo`, `test_review_uses_resolved_path_and_commits`), so your check must warn and proceed there. Do not add a `fetch` patch to those tests to keep them green: a remote-less repo is a supported configuration and is precisely the case that must warn.
- A refusal placed after `create_run`, or inside the stage loop, leaves a run directory behind — and for a real run a branch too. The refusal belongs before both, next to the `main`/clean-tree refusals.
- Sha equality is not the test. A locally rebased base is *diverged* (both revisions differ, neither is an ancestor) and must refuse, while an *ahead* base (origin is the ancestor) must only warn.
- `git fetch` prompts for credentials when it needs them and will hang a non-interactive run without `GIT_TERMINAL_PROMPT=0`; the timeout is what covers a stalled connection rather than a dead one.
- `--dry-run` must not touch the network — a fetch there makes the dry-run test and CI dependent on connectivity.
- Keep the spawns down: one fetch and at most two `rev-parse`/`merge-base` calls per run, never repeated per stage, and nothing added to `_roots`.
- `--no-fetch` proves the escape hatch, not the gate: do not use it to make the refusal tests fast or quiet.

Tests (what to prove, not the literal expects):
- Build a bare origin plus a clone inline (the phase entry's approach) and drive `prompt_workflow.run` to prove all six outcomes: behind → 4; diverged → 4; equal → proceeds; ahead → proceeds with a warning; no origin → proceeds with a cannot-verify warning; unreachable origin whose cached `origin/<base>` is behind → fetch-failure warning and then the behind refusal.
- Both refusals name the local and remote revisions, and the behind refusal carries the `git pull --ff-only` corrective; no run directory exists for the refused run and no branch was created.
- `--no-fetch` on a stale clone returns successfully with the not-verified warning, proven separately from the gate.
- `--dry-run` against a clone with an unreachable origin returns 0 and prints the would-fetch note — proof that dry-run never reaches the network.
- The non-interactive environment and the timeout reach the fetch: spy on the new `git.fetch` (or on `subprocess.run`) rather than asserting on git's own behaviour.
- A remote URL carrying userinfo is redacted in the warning.
- The existing prompt-workflow tests pass unchanged (remote-less repo → warn → proceed).

Done when:
- A run whose base branch is behind its remote refuses with `EXIT_REFUSED` before anything is written; the same run on an up-to-date base proceeds; the same run in a repo with no `origin` warns and proceeds; `--no-fetch` warns and skips the check; `--dry-run` performs no fetch.
- `uv run --frozen pytest` is green from the toolkit root, including the six outcomes above and the untouched existing prompt-workflow tests.
- `uv run aidw doctor`, `uv run aidw agents validate --strict` and `uv run aidw prompts check` stay clean.
- The diff touches only the five deliverables.
