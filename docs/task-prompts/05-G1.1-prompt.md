Task: Classify prompt-review findings as `spec-gap` vs `prompt-gap` and short-circuit spec-gaps

Requirements:
1. `prompts/task-review.md` finding block gains a required `Kind:` line whose only values are `spec-gap` and `prompt-gap` (bare, no bold/backticks, like `Priority:`/`Confidence:`), plus one line defining each: a `spec-gap` is a defect only the cited spec/roadmap can close (the prompt cannot be fixed without changing its source of truth); a `prompt-gap` is fixable by editing the prompt. Extend the existing "Keep the labels plain" instruction to `Kind:`.
2. `aidw/findings.py` parses `Kind:` into `ParsedFinding.kind`, normalised to the two canonical tokens via a `KIND_MAP` beside `PRIORITY_MAP` (same `_clean_scalar` path; space vs hyphen tolerated exactly as priority is). `kind` is **optional at parse level** — code-review findings (§8.3) have no `Kind:` and must keep parsing clean — so it is **not** added to `STRING_FIELDS` or `to_manifest_entry` (the published manifest shape is unchanged). `_finding_text_block` re-emits `Kind:` when present, so the fixer stage and `stage_registry.render_delta_brief`'s shrink do not drop the classification.
3. `aidw/workflows/prompt.py` enforces classification on the prompt-review loop only (not the shared parser): after `parse_review_findings`, any finding whose `kind` is missing/empty/unrecognised fails closed — the run ends `blocked` (exit 3), the offending finding(s) surfaced on stderr, never routed to the fixer — instead of the existing whole-review `unparseable` fallback. This is a distinct check from the existing `problems`-driven fallback, which stays unchanged for unknown priority / confidence / other-field. An unclassified finding is checked first: when a review has both an unclassified and a spec-gap finding, the unclassified stop (mechanism `unclassified`) wins, because a review whose classification cannot be trusted must not be acted on even in part.
4. A `spec-gap` finding short-circuits the loop before any fix stage, reconcile, or approve path: `blocked` (exit 3), the spec-gap finding(s) printed to stderr, the prompt left uncommitted, the `approve-task-prompt` gate recorded `denied` with mechanism `spec-gap` (prompt-fixed, see ask-if-ambiguous). The unclassified stop records mechanism `unclassified`. Both are non-`review-loop`, so the existing W1 `--resume` rule refuses them (exit 3, recorded reason) rather than offering a fix cycle. Classification checks run after `partition_findings` and before the M2/`Blocked`/terminal branches and the `unparseable` whole-review fallback; a spec-gap wins over an `Approve` or `Blocked` verdict.
5. `prompt-gap` findings flow through the existing loop unchanged: `partition_findings` stays priority-keyed, blocking findings one fix stage each, could-fix batched, reconcile unchanged — no `prompt-gap` finding is short-circuited.
6. `agents/task-reviewer/AGENTS.md` mirrors the `Kind:` requirement: a finding without a valid `Kind:` is not a complete review, and the reviewer's read-only boundary is unchanged.
7. `prompts/task-review.md` forbids approving on grep-only re-reads: on any round after the first, the reviewer must re-read the cited file/section in full (the task prompt, the cited spec section, the flagged repository file) before resolving a previous finding — a grep/diff-only re-read of the previously flagged section is never sufficient to approve.
8. design.md: §8.1 gains the `Kind:` contract, the spec-gap short-circuit (exit 3, surface, no fixer), and the unclassified fail-closed rule; §17 gains one new row recording task id, spec sections, changed files, and the prompt-fixed decisions below. The roadmap says "recorded as Z13", but Z13 is already taken (05-S1.2's roadmap-ownership row) and `aidw/conventions.md` forbids reusing an id — append under the next free Z id (`Z18`), never reuse Z13.
   Gate impact: no new prompt/agent id, no new checker, no status-vocabulary or CI change. `prompts/task-review.md` and `agents/task-reviewer/AGENTS.md` are edits to existing files, so `uv run aidw prompts check` and `uv run aidw agents validate --strict` stay green; `task-reviewer` stays read-only (`READ_ONLY_AGENTS`). The new `mechanism` values are gate-detail strings, not a new `state.py` status — no schema change.
