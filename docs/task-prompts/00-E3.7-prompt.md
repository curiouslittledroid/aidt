Task: Validate configured paths (fail closed) — classify every `paths:` entry as a read-path or a write-target, validate existence, and wire the result into `aidw doctor` and the stage preflight.

Requirements:
1. Classification, as a single source of truth in `aidw/target_config.py` (it already owns the config and reserves existence validation for E3.7 — see its module docstring). Read-paths (must exist): `roadmap_dir`, `task_prompts_dir`, `implementation_results_dir`, `build_results_template`. Write-targets (created on demand): `architecture_dir`. Exhaustive over `PATH_FIELDS`: `roadmap_glob` is a *glob*, not a filesystem path — classify it as neither and never existence-check it.
2. A pure check function — `check_paths(resolved: ResolvedConfig, target_root: Path) -> list[Issue]` — that resolves each read-path's value against `target_root` (relative `paths.*` values are target-relative, §3.1/§3.4) and, when the path does not exist, returns one `ERROR` issue naming the dotted field (`paths.build_results_template`) **and** the resolved absolute path. It writes nothing and mutates nothing; write-targets produce no issue.
3. Wire into `aidw doctor` `_check_target_config`: union the path issues with the existing loader `ERROR`s and `check_compatibility` issues so a missing read-path is a `FAIL` naming field + path. Doctor stays read-only — no `mkdir` here. A config-less repo whose *default* read-paths are absent now fails (intended: §3.4 D17 — a non-Mythical-Forge repo must supply the files or override the field).
4. Wire into the `aidw prompt` preflight (in `aidw/workflows/prompt.py`, after the existing compatibility refusal): check `roadmap_dir` and `task_prompts_dir`; a missing one is an exit-2 refusal naming field + path, before any branch/worktree/run record. This is validation only — do **not** change `load_tasks` to consume the configured `roadmap_dir` (that is E5.2).
5. Wire into the record stage's preflight in `aidw/workflows/implement.py` (which today loads no target config) — **one** insertion point: after the worktree locate, immediately before I5 (`record-implementation-results`) runs or is planned, never the pre-locate startup preflight, which cannot yet see the tree I5 writes into. There, load and resolve the worktree's `<target.root>/aidw/config.yaml` (prompt.py's loader-ERROR + compatibility refusal pattern, exit 2 regardless of `--dry-run`, so a malformed config never hides behind the hardcoded paths), then check the two read-paths I5 first needs — `implementation_results_dir`, `build_results_template` — resolving against `target.root`: the re-resolved worktree root the stages record as `repo_root`, never the control `repo.root` (the base-branch control tree and the task-branch worktree tree differ). A missing one is an exit-2 refusal naming field + path. The check runs whenever I5 will run or be planned: every real run (the locate has already refused exit 4 when no worktree exists), a `--resume`/`--from` that reaches I5, and a `--dry-run` with a located worktree; a dry run planning without a worktree has no worktree root to check and plans unchecked (the task-prompt existence refusal's own contract), and a resume/`--from` that skips an already-succeeded I5 skips its preflight with it.
6. Write-target `architecture_dir` on demand: when its owning stage is enabled, ensure the directory exists (`mkdir(parents=True, exist_ok=True)`) in `aidw/workflows/implement.py`'s real path, immediately before I4 (`update-architecture`) executes — after the worktree locate, resolving against `target.root`, never the pre-locate startup and never doctor. The mkdir runs only when I4 will actually execute: never under `--dry-run` (plan-only — a dry run writes nothing into the target tree), and never when the stage-skip logic (`should_run`) skips an already-succeeded I4 under `--resume`/`--from`. A creation failure (path exists as a non-directory, or is uncreatable) fails naming the stage by its **config stage id — `architecture`** (requirement 7's ownership/enabled key). The runtime chain's label for the same stage is I4 `update-architecture`; the message names the config id, not the runtime name. When disabled, absence passes — no creation, no error.
7. Write-target ownership (prompt-fixed): `architecture_dir` ↔ the `architecture` stage (the config stage id in §3.4's `workflows.implement.stages` example). "Enabled" is read from the resolved `workflows.implement.stages` list — an entry with `id: architecture` and `enabled: false` is disabled; an absent entry (config declares no stages) is enabled (the hardcoded chain always runs it). Read the flag for path validation only — do **not** wire `enabled` into the stage chain (E4.5).
8. Gate impact: this changes the `target config` doctor check (a new failure mode in `uv run aidw doctor`). Pre-existing entries affected: `tests/test_doctor.py`'s target-config tests and `tests/test_prompt_workflow.py`'s `_make_control_repo` fixture both build repos that lack `docs/task-prompts/`, `docs/implementation-results/` and `docs/implementation-results/TEMPLATE.md` — update those fixtures to provide the read-paths (or override them in the fixture config) rather than weakening the check. This repo itself has all four read-paths present (`docs/tasks`, `docs/task-prompts`, `docs/implementation-results`, `docs/implementation-results/TEMPLATE.md`) and `docs/architecture` legitimately absent, so `uv run aidw doctor` and `uv run --frozen pytest` stay green here.

Traps / prior review findings:
- `roadmap_glob` is a glob (`[0-9]* - *.md`), not a path — existence-checking it would treat the literal pattern as a filename and fail every valid config.
- The read-path set is **four**, not §3.4's three: `implementation_results_dir` is the fourth (the E3.7 roadmap entry in `docs/tasks/00 - Extraction.md`, confirmed by `docs/target-repo-config.md` and pinned by `tests/test_target_repo_config_doc.py::test_doc_states_the_read_path_contract_and_the_write_target_exemption`). Omitting it leaves the record stage's parent directory unvalidated.
- Two roots: `paths.*` resolve against the **target** root (`TargetRepo.root`), never `toolkit_root()` or the cwd — resolving against the toolkit root would flag a healthy target repo's `docs/` as missing. `implement.run` has two `TargetRepo`s: its stage preflights resolve against the located worktree (`target.root`, requirements 5–6), not the control `repo.root`.
- Doctor is read-only (`_check_target_config`'s "Read-only: one file read, nothing written"): the `mkdir` for write-targets belongs at requirement 6's site only — immediately before I4 (`update-architecture`) executes — never in doctor and never in requirement 5's record-stage preflight.
- §3.4 requires only "exist", not dir-vs-file typing: don't add `is_dir()`/`is_file()` checks the spec doesn't fix (the template is a file and the three dirs are dirs, but the contract is existence).
- Wiring the `aidw prompt`/`aidw implement` preflights will fail existing fixture repos that lack the default read-paths (`tests/test_prompt_workflow.py::_make_control_repo`, `tests/test_doctor.py::_make_supported`) — update the fixtures, don't gate the check behind `--strict` or a config presence test.

- E5.2 driving `roadmap.py` from the configured `roadmap_dir`/`roadmap_glob` — E3.7 validates the configured path; consuming it in `load_tasks` is E5.2's.

- "Any repo-added stage's directory" as a write-target — no schema field declares one yet; that is E4.1's stage registry.
- E3.6's doc — already written and consistent; keep it true, don't rewrite it.
