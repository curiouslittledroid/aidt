Task: `aidw prompt` resumes instead of re-authoring.

Requirements:
1. Add `--resume` and `--from <stage>` to `aidw/cli.py:prompt` and thread both into `aidw/workflows/prompt.py:run`, mirroring `aidw/cli.py:implement` / `aidw/workflows/implement.py:run`. `--resume` reads the latest **prompt** run for the derived branch (a `_latest_prompt_run` filtered on `state.workflow == "prompt"` and `state.git.branch`, like `implement._latest_implement_run`), prints completed stages, and confirms before continuing (mirror `implement._confirm_resume`, asked before the worktree locate, the lock and any run-state reopen or `create_run` — implement's F2 comment — so a declined resume exits 4 leaving no side effect; `--yes` skips). No matching run is a usage error (exit 2), matching implement. The lookup runs on a fresh invocation too, and implement's one-live-run-per-branch guard mirrors with it: a latest run still marked `running` refuses a fresh run exit 4 **before branch setup** (no run dir, worktree, lock or stage) — the lock only catches a live peer, and a crashed run releases it leaving a stale `running` record a clean-tree re-run would otherwise mint a second run id for (implement's "still marked running" refusal; `fix.py` guards the same) — stderr naming the run id and the `--resume`-or-finish-it recovery. `--resume` over a still-`running` record proceeds as that run's own resume: same run id, no `create_run` (implement's `state = existing` takeover); a crash stamps no `next_stage` (Requirement 3), so re-entry follows the recorded stage records through Requirement 4's reconstruction — the in-flight stage, never succeeded, re-runs. In the same `aidw/cli.py` change, update the `runs resume` hint in the `runs` command — it currently names only `aidw implement --resume` and says `aidw fix` has no resume in v1 — to name `aidw prompt --resume` alongside implement (the hint stays per-workflow guidance; `aidw fix` still has no resume).
2. Reuse the existing task worktree instead of re-creating it. On resume, locate via `git.worktree_for_branch` and re-resolve `target` + `agents` into it (the exact block that today follows `git.add_worktree` in `run`); a missing worktree on resume is a preflight refusal (exit 4). On a fresh (non-resume) re-run, reuse an existing worktree only if its tree is clean (empty `git status --porcelain`; a truncated fixer can leave partial prompt edits — H1.1 Notes): a dirty reused worktree is a preflight refusal (exit 4) printing the same two clear commands and noting the operator may instead inspect or commit the edits (§13: the discard stays operator-owned, `--force`-explicit); fall back to `git.add_worktree` only when none exists, and when that would refuse (a leftover branch from a prior failed run), refuse exit 4 printing the two copy-pasteable commands that clear it — remove the worktree (`aidw worktree remove <branch> --force`) and delete the leftover branch (`git branch -D <branch>`) — derived from `implement.worktree_add_command` and the `aidw worktree` surface, never a hand-rolled `rm -rf` or `reset --hard`. Both of these fresh-path refusals sit at branch setup — after the L1.1/L1.2 preflights, before the lock, `create_run` and any stage (Requirement 1's still-running refusal sits earlier, mirroring implement's pre-locate guard). A resume is exempt: the failed run's own partial edits are the state it continues from (H1.1's accepted precedent), and its reconcile and next review still verify the result.
3. Write `state.resume = {"next_stage": <failed stage name>}` on **failure** stops in `run` (each `return 1` site, including H1.1's empty-final-text failure), and clear it to `{"next_stage": None}` on success. Blocked exits (`return 3`) have no failed stage — leave `resume` without a `next_stage` (the empty dict, as today; `implement.py`'s gate-denied `return 3` is the precedent), with resume branching on run status first (Requirement 6). This is the key the resume read-back keys on.
4. Resuming a **failed** run continues at `state.resume.next_stage` (unless `--from` overrides — Requirement 5) in the same worktree and appends later stages to the same `state` (one run id — reuse the `existing` object and its `run_dir` exactly as `implement.py` does, no `create_run`). Reconstruct the loop's in-memory state from persisted stage records, never by re-authoring: `review_index`/`revisions` re-derive from the recorded stage names (`task-review-N`, `task-review-reconcile-{r}`), and each prior round that ran fixes rebuilds its `FixBatch` as a real `stage_registry.FixBatch` by re-reading that round's `stages/task-review-<N>.out.txt` (`_read_out`) and re-parsing it with the loop's own parser (`parse_review_findings` + `partition_findings`, `unparseable=True` when the parse failed) — stage names carry only counts, and `_expand_prompt_loop` raises `StageFieldError` on anything but a `FixBatch`; use the recorded `task-review-fixes-{r}-{i}` names as the expected stage inventory to reconcile each rebuilt batch against (an approving or `Blocked` round has no batch). The gate detail's per-round summary is **not** written on a failed run — do not rely on it. `baseline_prompt` (the pre-fix-batch snapshot) is not persisted: pass the existing `_brief_diff(baseline=None, …)` degradation path rather than fabricating one.
5. `--from` validates against the prompt loop's stage-name grammar **before any side effect** (mirror `implement.py`'s pre-locate validation: exit 2 on an unknown name, no run dir or worktree), then re-runs from that stage onward and records the override. The two flags combine exactly as `implement.py` layers them (design §9.4: completed stages are never re-run *implicitly* — `--from` is the explicit override): `--from` **without** `--resume` is a fresh run — `create_run` gives a new run id, Requirement 1's still-running guard and Requirement 2's fresh re-run worktree rules apply, and the named review stage is absent from the fresh plan so the degradation clause below applies (`--from task-prompt` alone is just a fresh run); `--from` **with** `--resume` keeps the resumed run's single run id and takes precedence over `resume.next_stage` — the named stage and everything after it runs again even if recorded succeeded, while stages before it keep the resume skip. Prompt-fixed — the exact predicate, derived from `_expand_prompt_loop`'s bounds and the `resolve_config`-resolved `max_revisions` (already computed before any run state), not the `rounds=()` two-name expansion: the valid set is `task-prompt`, plus — for integers `r`/`i` — `task-review-{r}` with 1 ≤ r ≤ `max_revisions`; `task-review-fixes-{r}-{i}` with 1 ≤ r ≤ `max_revisions − 1` and i ≥ 1 (per-blocking-finding and could-fix stages; `i` has no upper bound — a review's finding count is not budgeted); the unparseable fallback `task-review-fixes-{r}` with 1 ≤ r ≤ `max_revisions − 1`; and `task-review-reconcile-{r}` with 1 ≤ r ≤ `max_revisions − 1` (the final round is review-only — `terminal_last` breaks before its fixes/reconcile). Every other name, including out-of-budget ones (`task-review-5` under `--max-revisions 3`), is unknown → exit 2. Validation consults only this grammar and `max_revisions`, never a run record (implement's names-only check is the precedent; every recorded stage name is grammar-valid within budget, so recorded stages add no accepted names) — a name that passes validation but is in neither the resumed run's recorded stages nor the rebuilt plan degrades exactly as `implement.py` does when a validated name is absent from the plan (no position override; each stage keeps its own skip decision), never a crash.
6. Resuming a **blocked** run refuses naming the reason and never silently re-authors (a blocked run has no failed stage — design §9.3 sets `next_stage` only on failure). Branch on `status == "blocked"` before the completed-stages print, the confirmation, the worktree locate and the lock (implement's pre-locate-refusal position) and exit **3** — design §14's "workflow blocked (needs human)": the refusal reports the run's own blocked condition, so it is neither a usage error (2) nor a preflight refusal (4; those stay reserved for the no-matching-run, still-running and worktree cases). stderr names the run id and the blocked shape's recorded reason, re-read from the run's own records: the author's `blocked:` line (`_parse_blocked` on the recorded author `.out.txt`); otherwise the last recorded review's verdict and findings summary from its `.out.txt` (the loop's own `parse_verdict`/`parse_review_findings`, the same re-read Requirement 4's rebuild makes), naming the recorded denied `approve-task-prompt` outcome's `mechanism` (`review-loop` marks the review shapes; anything else is a gate denial). Nothing is mutated — the refusal precedes every write path (no `create_run`, no locate, no lock, no `save`). The blocked-run forward path (`--from-prompt`, the extra cycle) is H1.3.
7. The one-run-per-worktree lock must hold across a resume: acquire `aidw/lock.py:acquire(workspace.state_root, target.root)` — key = the resolved worktree path, the same value the reused worktree resolves to — before re-opening the run's state and release on every exit path, exactly as the current `try/finally`. Gates already recorded are not re-asked (design §9.4); `gate_outcomes` already survive `save()` via H0.1's merge.
8. `--dry-run` composes with the new flags exactly as `implement.py` layers them: a dry run is always the **fresh-plan baseline** — the unchanged author + `task-review-1` plan (`rounds=()`), never a resumed plan. Under `--dry-run`: Requirement 1's no-run `--resume` refusal is suppressed (implement's `resume and not dry_run` guard — no matching run plans a fresh run, exit 0), and the completed-stages print, the confirmation, the `existing` takeover and the worktree locate are all skipped (the planned branch-setup print stands); a `--from` override is validated but not applied to the plan. Not dry-run-gated: Requirement 5's `--from` validation (unknown or out-of-budget still exits 2 before any side effect), Requirement 1's still-running guard (a fresh dry run over a `running` record still refuses exit 4; `--resume` over it still plans fresh), and Requirement 6's blocked refusal (it precedes the dry run's own `create_run`, so `--dry-run --resume` over a `blocked` run still refuses exit 3 naming the reason — a dry run never plans an author over a blocked run). The dry run keeps the side-effect contract both workflows already share: one fresh run record via `create_run` marked succeeded, the worktree lock held and released (implement's dry run reaches `create_run` too); the plain dry run's plan is otherwise unchanged.

Traps / prior review findings:
- The obvious change is to keep calling `git.add_worktree`; it returns `None` ("already checked out") on every re-run and resume. Locate-then-reuse is the whole point; the exit-4 two-commands refusal covers both not-reusable cases — a leftover branch with no worktree, and (fresh path only) a dirty located worktree; a resume proceeds on the failed run's own tree.
- Loop state is not persisted directly. `review_index`/`revisions`/`fix_batches`/`previous_review_text`/`baseline_prompt` are in-memory only; a resume that re-expands `_prompt_plan(rounds=[])` re-runs the author and review-1. Recover the counters from stage names and rebuild each round's `fix_batches` by re-parsing that round's review `.out.txt` back into real `FixBatch` objects (`parse_review_findings`/`partition_findings`) — names encode only counts, `_expand_prompt_loop` rejects anything but a `FixBatch`, and placeholder batches are the same forbidden fabrication as a fake baseline.
- Every **failure** stop (`return 1`) must set `state.resume` — `run` returns 1/3 on ~a dozen sites without touching it. Missing one leaves a run whose `--resume` silently re-authors; stamping it on a blocked `return 3` makes a blocked run look resumable (design §9.3).
- Run-scoped preflights (L1.1 base-branch fetch, L1.2 predecessor check) are **not** repeated on resume — they belong to the run being resumed; the worktree identity and the lock do (roadmap Notes). Skipping the wrong half either re-spends the fetch or lets two runs share one worktree.
- Blocked ≠ failed: a blocked run records no `next_stage`, so resume must branch on `status == "blocked"` and refuse with exit 3 naming the recorded reason (Requirement 6) — not fall through to the author stage.
- `--from` validation must precede the locate and `create_run` (implement.py's F1 comment is the precedent); a typo'd name leaving a run directory is the exact prior-review finding.
- The obvious change is to make a resume dry run reconstruct the loop and print the resumed stage list — `implement.py`'s precedent is the opposite: its dry run always plans the fresh full plan and skips the takeover (`resume and not dry_run`), and a prompt dry run cannot plan past review-1 without real verdicts anyway (`rounds=()` is why). Mirror implement (Requirement 8); the resumed shape is proven by the fake-stage resume tests, not the dry run.

Explicit non-goals — do NOT do these in this task:
- H1.3 (blocked-run continuation, `--from-prompt <path>`, recorded effective budget) is a separate task — H1.2 only refuses a blocked resume with a named reason.
- H2.1 (delta-brief size budget) is a separate task — resume re-sends the same prompts; it does not shrink them.
- `aidw run` chain resumability (`prompt-to-fix`/`task-to-pr`) is out of scope — `aidw/workflows/run.py` calls `prompt_workflow.run` without resume flags and stays unchanged.

Tests (what to prove, not the literal expects):
- tests/test_prompt_workflow.py (extend the existing `_fake_stages` pattern): a run that fails at `task-review-2` (fake stage returns `failed`, prior rounds' `.out.txt` files already written) resumes with `--resume` — assert the resumed stage list starts at `task-review-2`, never includes `task-prompt`/`task-review-1`, the run id is unchanged, and the new `task-review-2` record is appended to `state.stages`.
- Absence of author: assert no `task-prompt` record is added on resume and no `create_run` fired (one `state.json`/run dir).
- Fresh re-run refusal: with a leftover branch (worktree removed but the branch alive, or the worktree present but dirty), a non-resume run refuses exit 4 and the message carries both clear commands; a located worktree with a clean tree is reused by the fresh run instead (no `git.add_worktree`), while a resume over that same dirty tree proceeds.
- Still-running guard: the latest run marked `running` (stale from a crash) refuses a fresh run exit 4 naming the run id, leaving no new run dir, while `--resume` over that same record proceeds — one run id, no `create_run`, and the in-flight stage re-runs from its non-succeeded record.
- Declined resume: answering no at the confirmation exits 4 before any side effect — no worktree locate, no lock, no `create_run`, `state.json` unchanged.
- `--from` validation: an unknown stage name exits 2 before any run dir/worktree side effect; an out-of-budget name (`task-review-5` under `--max-revisions 3`) is unknown and exits 2 too; a valid `--from task-review-1` re-runs from that stage — with `--resume` that reuses the same run id and forces the named stage onward despite its succeeded records, while `--from` alone starts a fresh run id (fresh-re-run rules).
- Blocked refusal: a `status: blocked` run with `--resume` refuses exit 3 naming the reason each shape records — a terminal `Request changes` names the last review's verdict and findings from its `.out.txt`, an author `blocked:` block names its recorded line, a gate denial names the gate mechanism — and `state.json` is unchanged (no new stage records, no `create_run`).
- Fix-batch reconstruction: a run that failed after a round of fixes (e.g. at `task-review-fixes-1-2`) resumes with the prior round's `.out.txt` re-parsed into a `FixBatch` whose partition matches the recorded fix stage names (per-finding stages or the single unparseable fallback), replanning the same remaining fix stages — not `rounds=()`.
- `state.resume` lifecycle: on a failed stage, `state.resume.next_stage` names it; on success it is `None`; a blocked stop records no `next_stage`. Lock: a resume acquires the same worktree-keyed lock (monkeypatch `lock.acquire` to record the key, or reuse the existing lock test).
- Dry-run composition (Requirement 8): `--dry-run --resume` prints the same fresh plan as a plain dry run (author and `task-review-1` planned; no completed-stages print, no confirmation, no worktree locate) and mints one fresh run record — never a takeover of the existing run id; over a `blocked` run it still refuses exit 3, and over a still-`running` record it still plans fresh; `--dry-run --from <unknown>` still exits 2 with no run record.

Done when:
- A run that failed at `task-review-2` resumes at `task-review-2` in its own worktree with one run id, never re-running `task-prompt` or `task-review-1`.
- A resume past a round of fixes rebuilds each prior round's `FixBatch` from its persisted review text (re-parsed, never fabricated or inferred from names alone), so `_prompt_plan` replans the same fix stages the recorded names show.
- A `blocked` run's `--resume` refuses with exit 3 naming the recorded reason, mutating no state, and never silently re-authors (the continuation is H1.3's).
- A fresh non-resumed re-run reuses the existing worktree when its tree is clean, or refuses exit 4 printing the two clear commands (dirty reused tree, or a leftover branch); a fresh run while the latest run is still marked `running` refuses exit 4 naming that run, and `--resume` takes the same record over.
- `--from` validates against the loop's stage-name grammar bounded by `max_revisions` before any side effect (unknown or out-of-budget name → exit 2, no run state); `--from` without `--resume` creates a fresh run id, and with `--resume` it overrides the resume selection in the same run id.
- The one-run-per-worktree lock holds across a resume; `state.resume.next_stage` is set on failure stops (a blocked exit records none) and cleared on success; gates already recorded are not re-asked.
- `--dry-run` composes with `--resume`/`--from` as `implement.py` does — always the fresh author + `task-review-1` plan (no takeover, no locate, no confirmation; `--from` still validated, the still-running and blocked refusals not dry-run-gated) — leaving the plain dry-run plan unchanged as the primary integration seam.
