Task: Require the revision a finding was verified against (Design 8.1)

Requirements:
1. `Where:` reword — in `prompts/task-review.md`, the `Where:` field definition in the finding-format block (currently "Task-prompt path and line/section; include the authoritative file and section when relevant.") must require the reviewer to name the file/symbol the finding was verified against **and** the revision or command it was verified at (e.g. a git sha, or `git show <rev>:<path>`), or state explicitly that nothing could be verified. This is the roadmap's own Deliverable made exact.
2. Evidence stays inside `where` — no new finding field or label. The evidence travels inside the `where` field's value; the manifest keys are fixed at `prompts/scripts/review-followup/logic.py:_FINDING_KEYS` and the finding-block labels at `aidw/findings.py:_LABELS` (both already map `where`). Add no `Revision:`/`Evidence:` label or manifest key.
3. `Where:` label byte-stable — only the guidance text after the `Where:` colon changes. The label `Where:`, the other six labels, and the three verdict tokens (`Approve`/`Request changes`/`Blocked`) stay exactly as-is; the parser keys on them (`aidw/findings.py`).
4. Product-neutral wording — bucket (i) (EXTRACTION.md §4.2): no package-manager name, no product path, no product document, no product task-id example (no `pnpm`, no `Design 21`, no `docs/task-prompts`, no `origin/00-E1.5`-style example). Generic "base branch"/"revision or command" phrasing is fine.
5. Rendered-prompt test — add a rendered-prompt assertion to `tests/test_prompt_workflow.py` following `test_l21_rendered_reviewer_prompt_states_dependency_and_blocked_rules`: the new `Where:` requirement phrases appear in the rendered `task-review.md`; label/verdict tokens stay byte-stable; the forbidden strings are absent from the added lines.
6. Bundled suite untouched — `prompts/scripts/review-followup/` (including `logic.py`) is not a deliverable and must not be edited; its tests pass unchanged because the manifest shape is unmodified.

Traps / prior review findings:
- Don't add a new field. A `Revision:` line in the finding block would either be dropped by `aidw/findings.py:_LABELS` (only the seven known labels map) or rejected by `logic.py:_FINDING_KEYS` — evidence goes inside `where`, never a new key.
- Keep the `Where:` label byte-stable. Renaming it (e.g. `Evidence:`) breaks the `where` mapping in `aidw/findings.py:_LABELS`, so every finding parses an empty `where` and the manifest fails closed.
- Scope the neutrality assertion to the added lines, not the whole rendered prompt: the pre-existing Scope bullet already names `Design 21 — Monorepo Layout`, and bucket (i) ships as-is (EXTRACTION.md §4.2) — a whole-prompt absence assertion would fail on it.
- Include the "nothing could be verified" escape hatch. A reviewer forced to always cite a revision will fabricate one — the exact citation-free round-1 failure L2.2 exists to prevent — so the reworded line must permit the explicit "nothing could be verified" statement.
- Render with exactly one variable: `render_prompt_file(toolkit_root()/"prompts"/"task-review.md", ["docs/task-prompts/03-E4.1-prompt.md"])`; zero or extra args raise `PromptError`.
