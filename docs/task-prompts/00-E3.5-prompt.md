Task: `aidw/config.yaml` validation in doctor — report the config path found (or none), the resolved schema version, and any validation error.

Requirements:
1. Add one doctor check, `_check_target_config` → `Check("target config", …)`, in `aidw/doctor.py`, called from `collect_checks` in the resolved-target block (alongside `_check_git`/`_check_mcp`) **after** the `BareRepositoryError`/`RepoNotFoundError` early returns — the config lives in the working tree (`aidw/paths.py:101-102`), so a bare/non-repo target must still short-circuit before it. Compute the path the way the existing consumers do: `root / "aidw" / "config.yaml"` (`aidw/cli.py:1290`, `aidw/workflows/prompt.py:1317`).
2. Load with `aidw.target_config.load_target_config`. A missing file is the valid defaults case (§3.4): the loader returns an empty `TargetConfig` with `source_path=None` and no issues — the check must be `OK` then, never a FAIL or a crash.
3. Report the path: `str(declared.source_path.resolve())` when a file was read, else `none (defaults)`.
4. Report the resolved schema version: the `resolve_config(declared)["schema_version"]` leaf (value + `source`; it equals `declared.schema_version` because schema_version has no toolkit default, and is unset when no file). Render as `1 (config)` / `none (defaults)`.
5. Validation errors → `FAIL`: collect `declared.issues` at `ERROR` level and render with `format_issues` (re-exported by `aidw.target_config` from `aidw.config` — the module's stated E3.5 convention). The loader's messages already name the full field path (`unknown key `paths.foo``, `` `schema_version` is required ``) — surface them, don't paraphrase them away.
6. Compatibility errors also → `FAIL` (§3.11/D10): `check_compatibility(declared, toolkit_version=__version__)`; union its `ERROR` issues with the loader's and report all. It is safe on a partial config (None fields → no refusal), so a config that is both malformed and incompatible reports both. Import `__version__` from `aidw` (no cycle — `aidw/__init__.py` only defines the literal); import the loader/resolver/compat/`format_issues` from `aidw.target_config`, never the reverse.
7. Gate impact: this changes the `uv run aidw doctor` gate. On this toolkit repo `aidw/` is the Python package (D7), so there is no `<target>/aidw/config.yaml`; the new check reports `OK … none (defaults)` and the gate stays exit 0. The check reads one file and writes nothing (§3.1 "nothing generated is ever written into a target repo"); `run_doctor` already exits non-zero on any FAIL, so no exit-code change beyond the check.

Traps / prior review findings:
- Two config modules: `aidw/config.py` is *agent* config (`agent-configs/*.yaml`); `aidw/target_config.py` is the *target* `aidw/config.yaml`. Import the loader/resolver/compat from `aidw.target_config` and `format_issues` from the same re-export; validating agent configs (or `Path.exists()`-ing `aidw/config.yaml` before loading) is the wrong surface.
- Missing config is valid, not an error: the loader returns `source_path=None` + no issues when the file is absent. Failing on `source_path is None` turns every defaults-only repo — including this toolkit repo — red and breaks the done-when "passes with defaults".
- Decide failure from issues, not the merge: `resolve_config`'s contract is "callers refuse a config carrying ERROR issues *before* resolving". The FAIL decision comes from the loader's `ERROR` issues + `check_compatibility`, never from the merged output; report the schema version only after that gate.
- Don't hardcode the toolkit version: pass `toolkit_version=__version__` (`from aidw import __version__`), never a literal `"0.1.0"` — the same drift trap E3.3 warns against.
- Check-name uniqueness: `tests/test_doctor.py::_named` asserts exactly one check per name; "target config" is free, but place the call so the existing order assertion (`git version` before `repo root`) and the by-name `NEW_CHECKS` loop keep passing — `_make_supported` repos have no config, so the new check is `OK` there.

Explicit non-goals — do NOT do these in this task:
- E3.6 `docs/target-repo-config.md` (documenting every field/default/effect) — separate.
- E3.7 read-path existence validation / write-target classification — separate; do **not** `Path.exists()` any `paths:` field or create `docs/architecture` here. This check validates the *config file*, not the paths it names.
- `aidw config show` (`aidw/cli.py:config()`) is E3.2's and already done — do not refactor or duplicate its resolution/provenance logic into doctor beyond the path/load shape this check shares.
- E4.3 wiring config into the other workflows, and E4.2's third §3.11 refusal ("a required prompt cannot be resolved") — separate; this task changes only `aidw/doctor.py`.
- E5.2 making `roadmap.py`/`prompt.py` consume `paths.*` — separate.

Deliverables:

Tests (what to prove, not the literal expects):
- `tests/test_doctor.py`, reusing the existing git fixtures (`_init_committed_repo`/`_make_supported`, `_named`, `fake_external_clis`): a target with a valid `aidw/config.yaml` (`schema_version: 1` plus one override, e.g. `repo.base_branch: trunk`) → `target config` is `OK`, detail names the resolved absolute path and `schema version 1 (config)`.
- A target with no `aidw/` folder → `OK`, detail says `none (defaults)` and the resolved schema version is unset/none — the roadmap done-when "missing config passes with defaults".
- A malformed config — one vector each for an unknown key, a wrong type, and a missing `schema_version` → `FAIL`, and the detail contains the offending field path (assert the path substring, not an exact sentence).
- An incompatible config — `schema_version: 2` and/or `requires_toolkit: ">=99.0.0"` → `FAIL`, detail names the field (`schema_version`/`requires_toolkit`).
- Exit code: `run_doctor` (or `CliRunner` on `["doctor"]`) returns `1` for the malformed config and `0` for the missing-config repo.
- Read-only: after `collect_checks` on a config-less repo, no `aidw/` directory or `config.yaml` was created.

Done when:
- `uv run --frozen pytest tests/test_doctor.py` is green, including the `target config` cases above.
- A malformed config makes `aidw doctor` exit non-zero naming the field path, and a missing config exits 0 reporting defaults (the roadmap's Done-when).
- On this toolkit repo (no `<target>/aidw/config.yaml`), `uv run aidw doctor` still exits 0 with the new check reporting `none (defaults)` — the gate stays green.
