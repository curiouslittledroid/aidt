Task: Freeze test (the D5 guard) — a golden test asserting that the Mythical-Forge-shaped config yields byte-identical marker strings, label names, colours, descriptions and comment bodies to the `baseline-verbatim` tag.

Requirements:
1. The oracle is the tag, never the working tree: read `prompts/scripts/review-followup/constants.py` from `git show baseline-verbatim:<path>` (subprocess, repo-root cwd) and load it into a fresh module namespace (shape of `tests/test_target_config.py:_frozen_script_constants`, but a distinct module name). The current `constants.py` is the thing under test, not the oracle.
2. Markers byte-identical — rendered *and* template. For a fixed probe PR URL/finding id, the baseline `parent_marker`/`child_marker`/`summary_marker` output must equal the current render of the resolved `github.markers.*` templates. The baseline exposes markers only as f-string functions (E6.1's module-level templates don't exist there), so recover each template by self-substitution — `baseline.parent_marker("{pr_url}")` is exactly the template literal — and assert the resolved template equals it byte-for-byte. Pinning the template is what catches a pre-rendered literal that matches one probe and breaks every real PR.
3. Labels byte-identical: resolved `github.labels` == baseline `LABEL_DEFINITIONS` — enumerate all six names (`review-follow-up`, `must-fix`, `should-fix`, `could-fix`, `decision-pending`, `approve-fix`), assert the key sets are equal and each colour and description is byte-identical. Whole map, no spot-check.
4. Comment bodies and role names byte-identical (script side, §3.9 — these have no config field): current `constants.py` `STATUS_IN_PROGRESS`/`STATUS_FIXED`/`DECISION_APPROVE_FIX` and `LABEL_REVIEW_FOLLOW_UP`/`LABEL_APPROVE_FIX`/`LABEL_DECISION_PENDING`/`PRIORITY_LABELS`/`PUBLISHER_LABELS` == baseline's same names.
5. The "Mythical-Forge-shaped config" is resolved, not hand-asserted: `resolve_config(TargetConfig(schema_version=1))` (D17 — toolkit defaults ARE Mythical Forge's values) must resolve every `github.markers.*` and `github.labels.<name>.{color,description}` leaf to a value byte-identical to the baseline (read via `resolved["github.markers.parent"].value`); also assert `TOOLKIT_DEFAULTS.github` equals the baseline directly so the config-less fallback/handoff default is pinned without depending on resolution.
6. Fail loudly, never skip: if `git show baseline-verbatim:…` fails (tag absent), the test errors — never `pytest.skip`/`xfail`, because a silent skip disables the D5 guard exactly where it matters.
7. Gate reconciliation (CI — mandatory, the suite breaks otherwise): `.github/workflows/ci.yml`'s `actions/checkout` step is a shallow, tagless clone, and `baseline-verbatim` is the root commit ~258 commits behind `main`, so `git show baseline-verbatim` fails in CI. Set `fetch-depth: 0` on that step so the tag is present when CI runs `uv run --frozen pytest`. This is the only non-test change in the task.

Traps / prior review findings:
- Do not diff the two `constants.py` files' text: E6.1 legitimately rewrote the current file (module-level marker templates, updated docstrings), so baseline and current are not byte-identical *files*. Compare values (rendered markers, `LABEL_DEFINITIONS`, comment bodies, role names), never source text.
- f-string vs `.format`: baseline markers are f-string functions; current are `{pr_url}`/`{finding_id}` templates rendered by keyed `.format`. A naive "function output == template string" comparison fails — recover the template via `baseline.<fn>("{pr_url}")` and assert both rendered and template.
- Module-name collision: loading the baseline must use a fresh module name distinct from the imported `constants` and from `_frozen_script_constants`'s `review_followup_constants_for_two_home_test`, or the import silently aliases the current module and the golden compares a thing to itself.
- Don't put this under `prompts/scripts/review-followup/tests/`: that tree is stdlib-only, copied into other repos without `aidw`, and cannot import `aidw.target_config` or run `git show`. This golden is a repo-root `tests/` test.
- CI is the silent killer: locally the tag is present, so the golden passes and everything looks done; the first red CI is where the missing-tag failure surfaces. Req 7 must land in the same change as the test.

Explicit non-goals — do NOT do these in this task:
- E6.4 "Document the freeze" narrative in `docs/target-repo-config.md` (why config-with-frozen-defaults, what a rename breaks) — separate task.
- Any change to E6.1's config plumbing (`aidw/github.py` serializer, `aidw/target_config.py` defaults, the `AIDW_REVIEW_FOLLOWUP_CONFIG` handoff) or E6.2's `test_matching_semantics.py` — already delivered, leave untouched.
- No bucket-(i) prompt byte-identity coverage: §5.4 also freezes resolved prompts, but that is MF.2's (Mythical Forge override) concern, not this task's.
- No re-derivation of the frozen values from a new source, and no writing markers/labels/comment bodies into any prompt or doc beyond what already exists.

Deliverables:
- tests/test_baseline_verbatim_golden.py
- .github/workflows/ci.yml (the `fetch-depth: 0` checkout change only)

Tests (what to prove, not the literal expects):
- One byte-identity assertion per frozen surface, enumerated exhaustively so any single-character change fails: three markers (rendered + template), six labels × name/colour/description, three comment bodies, five role-name constants — all against the baseline module.
- Fail-loud: a `git show` non-zero exit or a missing tag raises (not skips); the golden's own error path is the assertion.
- Purity: resolving the config twice returns equal values and mutates nothing; the baseline namespace and current constants are read-only.

Done when:
- `uv run --frozen pytest tests/test_baseline_verbatim_golden.py` is green, and the full `uv run --frozen pytest` gate is green (AGENTS.md gates).
- Temporarily editing any one frozen value (a label colour in `aidw/target_config.py`, a marker character, or a comment body in `constants.py`) makes the golden fail, then revert — the roadmap's "changing any frozen value in Mythical Forge's config fails this test" made executable.
- `git show baseline-verbatim:prompts/scripts/review-followup/constants.py` succeeds from a fresh checkout after the CI change (the tag is now fetched).
- The diff touches only the new test file and the one-line CI checkout change — no `prompts/scripts/`, `aidw/`, or pre-existing test is modified.

If anything in the cited spec section is ambiguous or underspecified for this task, stop and ask rather than guessing — especially:

- The CI `fetch-depth: 0` reconciliation is prompt-fixed: it is the minimum change that keeps the golden's gate green in CI; if the repo prefers `fetch-tags: true` or vendoring the baseline into the tree, name it before implementing.

This task guards what a GitHub-writing script posts: a weak or silently-skipped golden masks a D5 violation — orphaned parents and duplicate issue creation are the freeze's whole point.
