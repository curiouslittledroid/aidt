Task: Move markers and labels into resolved config — populate `github.markers` and `github.labels` from config, with defaults **exactly** equal to today's literals in `prompts/scripts/review-followup/constants.py`.

Requirements:
1. Seed `TOOLKIT_DEFAULTS.github` in `aidw/target_config.py` with the D5 frozen values copied verbatim from `constants.py` (§3.4/§3.9): `github.markers` `parent`/`child`/`summary` = the three `{pr_url}`/`{finding_id}` template strings exposed as frozen literals in `constants.py` (Req 5 — the same strings today's `parent_marker`/`child_marker`/`summary_marker` render); `github.labels` = the six `name → {color, description}` entries of `constants.py:LABEL_DEFINITIONS`. `resolve_config` already walks `MARKER_FIELDS` and `LABEL_KEYS` (the `set(declared_labels) | set(defaults.github.labels)` merge), so the merge does **not** change — only the defaults structure's contents do. Keep `TOOLKIT_DEFAULTS` immutable.
2. Two-home byte-identity (prompt-fixed, mirroring E3.4's `TargetRepo` dual-home): `target_config.py` must **not** import from `prompts/scripts/` — the wheel ships only the `aidw` package and the layering forbids it. The frozen literals live in both `constants.py` (script fallback) and `TOOLKIT_DEFAULTS.github` (config defaults), pinned equal by a test in this task; E6.3 adds the authoritative baseline-verbatim golden.
3. Script handoff (prompt-fixed channel; the roadmap delegates the choice): the scripts read one env var `AIDW_REVIEW_FOLLOWUP_CONFIG` whose value is a JSON object `{"markers": {"parent": str, "child": str, "summary": str}, "labels": {str: {"color": str, "description": str}}}` carrying **fully-resolved** values (defaults merged, `source` dropped). Unset env var → frozen `constants.py` (the standalone case). Present but unparseable, missing a marker/label field the script needs, or carrying a template that fails its accessor's keyed `.format` render (a stray `{` → `ValueError`, an unknown placeholder → `KeyError`) → fail closed with a clear error; never silently fall back (a wrong-marker publish violates D5). `gh.py` owns the parsing (the module both CLI entry points already import): it resolves the effective marker templates and label definitions once — env var unset → the frozen `constants.py` values; malformed → fail closed — and, at that same resolution step, validates each resolved template renders under the keyed `.format` its accessor performs (Req 5's signatures), so a render-incapable template surfaces as the same clear fail-closed error **before** any marker renders — no publish, no half-rendered marker, no mid-publish crash — and the CLIs import the resolved markers/labels from `gh.py` (the effective accessors are named in Req 5); neither `constants.py` nor `logic.py` reads the env var. Parsing uses stdlib `json`/`os` only — no new dependency.
4. What stays frozen (spec-fixed by §3.4/§3.9/D5): the comment bodies (`STATUS_IN_PROGRESS`, `STATUS_FIXED`, `DECISION_APPROVE_FIX`) and the role label names (`LABEL_REVIEW_FOLLOW_UP`, `LABEL_APPROVE_FIX`, `LABEL_DECISION_PENDING`, `PRIORITY_LABELS`, `PUBLISHER_LABELS`) remain in `constants.py`, **not** config-driven — §3.4's schema has no comment-body or role field and D5 freezes names. `PUBLISHER_LABELS` stays the frozen 5-name tuple (the workflow's role labels, `approve-fix` excluded); it is **not** derived from config keys — a repo-added label is a definition, not a publisher obligation.
5. Markers are format templates, and the script-side seam is named (prompt-fixed, so tests assert real symbols, not invented ones): `gh.py` exposes the **effective** accessors under the same names and signatures as `constants.py`'s frozen fallbacks — `parent_marker(pr_url)`, `child_marker(pr_url, finding_id)`, `summary_marker(pr_url)`, and the `LABEL_DEFINITIONS` mapping — and the two CLI entry points (`review_followup.py`, `publish_review_followups.py`) take their marker calls and label *definitions* from `gh.py`, while the frozen role names and `PUBLISHER_LABELS` still come from `constants` (Req 4). Each effective marker accessor renders the resolved template with `.format(pr_url=…, finding_id=…)` (keyed `.format`, not `%`/`.replace`/f-string), byte-identical to today's output when the env var is unset — a template that fails this render never reaches an accessor, because `gh.py`'s resolution step (Req 3) rejects it first. `logic.py` needs **no** config — it uses only the frozen role names + comment bodies — so only `gh.py` and the two CLIs consume markers/labels. `constants.py`'s only change is exposing the three marker template strings as module-level frozen literals (today they live only inside the f-string functions, so `gh.py`'s fallback and the two-home test would otherwise have to probe the functions); everything else in it stays byte-identical and no env-var or config parsing enters it.
6. aidw sets the env var at **both** invocation seams, threading one `ResolvedConfig` end-to-end (prompt-fixed): the resolution point is each workflow `run()`'s existing `resolve_workflow_config` preflight (`aidw/target_config.py`, called once at the top of `review`/`approve`/`fix`/`implement`/`prompt`'s `run()` — a missing `aidw/config.yaml` still resolves the toolkit defaults); no seam re-loads or re-resolves it. Every new parameter below is an optional keyword `config: ResolvedConfig | None = None`; `None` leaves the env var unset (byte-identical to the default config, so callers that pass nothing keep compiling). (a) `run_stage` — when `config` is set, its env block sets the env var alongside `SCRIPTS_DIR_ENV_VAR`, serialized via `serialize_github_config` (below; `runner.py` already imports `ResolvedConfig`, and `github.py` imports stdlib only, so `runner → github` adds no cycle), so agent-invoked scripts inherit it. (b) `select_followups`/`verify_approvals` thread `config` through `run_script` to `_run`, which composes the subprocess env with the var when present, so aidw-direct runs carry it; the read-only `gh` helpers (`repo_slug`/`pr_view`) keep calling `_run` without it. `build_publish_argv`/`build_followup_argv` change nothing — argv only, no env channel; the real-run publisher inherits the var from `run_stage` (the R2 agent's subprocess). Call sites that gain `config=<the workflow's resolved config>`: every `run_stage(` in the five `aidw/workflows/` modules (each sits in `run()` or a helper/closure already holding it — `review.py`'s `run_spec`, `fix.py`'s `_approval_round`, `approve.py`'s `_planned_stage`), plus the `select_followups`/`verify_approvals` calls in `fix.py` (`_approval_round`, `run`) and `approve.py` (`_planned_stage`, `run`); `review.py` has none (its only followup-script touch is the dry-run `build_publish_argv` print). Add the serializer `serialize_github_config(resolved) -> str` in `aidw/github.py` (which owns the script seam), building the JSON from the `ResolvedConfig`'s `github.markers.*` and `github.labels.*` entries, enumerating label names from the resolved entries rather than a hardcoded list. Define the env-var name constant in `aidw/paths.py` next to `SCRIPTS_DIR_ENV_VAR`.

- Stale test pins are the whole risk surface: E3.2/E3.4 wrote `github.markers.*`/`github.labels.*` as "unset" in `test_target_config.py`, `test_cli.py` and `test_target_repo_config_doc.py`. A green new test next to a red suite fails the gate — update all of them in the same change.
- `logic.py` must not read config: it uses frozen role names + comment bodies; threading config into it breaks E6.2's "test suite passes unmodified". Only `gh.py` + the two CLIs consume markers/labels; `constants.py` must not read config either — it stays the frozen fallback, and env-var parsing lives in `gh.py`. The CLIs' marker and label-*definition* imports must switch from `constants` to `gh` — leaving them on `constants` passes the no-env case while the configured path never reaches the CLIs (`PUBLISHER_LABELS` and the role names stay on `constants`).
- Marker templating: the config value is the `{pr_url}`/`{finding_id}` template, formatted with keyed `.format`; a repo template with a stray `{` or unknown placeholder raises `KeyError`/`ValueError`, and Req 3's resolution-step validation makes that a clear fail-closed error — never a mid-publish crash, a half-rendered marker, or a silent fallback to the frozen literals — while a pre-rendered template (literal PR URL) renders cleanly but breaks E6.3's byte-identity and child lookup (E6.3's golden, not this task).

- Two-home drift: `target_config.py` must not import `prompts/scripts/review-followup/constants.py` (wheel ships only `aidw`). Pin equality with a test; don't collapse into a shared import.
- Set the env var at both seams: if only `github.py` (aidw-direct) sets it and `run_stage` (agent) doesn't, a non-default repo gets the publisher writing one marker while `select_followups` searches for another → "No review-follow-up parent issue found".
