Task: Version and compatibility refusal (D10) — refuse to run when `schema_version` is newer than understood, or `requires_toolkit` is unsatisfied.

Requirements:
1. Add `SUPPORTED_SCHEMA_VERSION = 1` and `check_compatibility(declared: TargetConfig, *, toolkit_version: str) -> list[Issue]` to `aidw/target_config.py` (the module's docstring already names E3.3 as its consumer; `load_target_config`/`resolve_config` keep their APIs). Pure: no I/O, no input mutation, returns a fresh list. Returns `[]` (compatible) or ERROR issues reusing the module's re-exported `Issue`/`ERROR` so `format_issues` renders them; the issue `source` follows the loader's `path.name` convention (`declared.source_path.name` when set). The two refusals are independent: a config that is both newer and pins an unsatisfied version reports both issues, not just the first.
2. Refusal 1 — schema_version: refuse iff `declared.schema_version is not None and declared.schema_version > SUPPORTED_SCHEMA_VERSION` (§3.11's "exceeds what it understands"; the roadmap's "newer than understood"). A missing config file (`schema_version is None`) is the valid defaults-only case and is **not** a refusal. The message names the field `schema_version`, the declared value, `SUPPORTED_SCHEMA_VERSION`, and the remedy (upgrade the toolkit, or lower the config's `schema_version`).
3. Refusal 2 — requires_toolkit: refuse iff `declared.requires_toolkit is not None` and the toolkit's own version does **not** satisfy the declared specifier. Compare with `packaging.version.Version` + `packaging.specifiers.SpecifierSet` — add `packaging` to `[project] dependencies` and re-sync `uv.lock` in the same change (AGENTS.md: a new dependency edits `pyproject.toml` *and* the lock). An unparseable specifier (`SpecifierSet(...)` raising `packaging.specifiers.InvalidSpecifier`) is a refusal with a clear message, never a traceback. The message names the field `requires_toolkit`, the declared specifier, the toolkit's own version, and the remedy (upgrade the toolkit, or relax the pin).
4. Wire the check into `aidw/workflows/prompt.py:run()` — immediately after the existing config-ERROR-issues refusal (the E3.2 block that prints `format_issues` and returns `2`): call `check_compatibility(declared, toolkit_version=__version__)` and, when it returns issues, print `format_issues` to **stderr** and return `2` — before `load_tasks`, `derive_branch_name`, any run record, branch or worktree, and regardless of `--dry-run`. Import `__version__` from `aidw` (the module already does `from aidw import git, lock`); import `check_compatibility` from `aidw.target_config` — never the reverse direction. This is the "refuse to run" behaviour; `prompt.py` is the only workflow that reads config today, so it is the only wiring this task makes.
5. `aidw/cli.py:config()` (`config show`) keeps its E3.2 display-only behaviour and gains **no** compatibility refusal here: it is the inspection aid that shows the resolved `schema_version`/`requires_toolkit` with provenance, so a user can see why a workflow refuses. (prompt-fixed — see ask-if-ambiguous.)

Traps / prior review findings:
- Lexicographic version comparison: `"0.1.0" >= "1.0.0"` is `True` as strings — use `packaging` (PEP 440/semver-compatible), never `str` comparison or a naive `tuple(int(x) for x in v.split("."))` (pre-release/build-metadata edge cases). The toolkit version is passed **in** as `toolkit_version`; never hardcode `"0.1.0"` inside the check.
- Import cycle: `target_config` must not import `aidw.workflows.prompt` (E3.2's existing rule); `prompt.py` imports the check and `__version__` from below it.
- `SpecifierSet` raises `InvalidSpecifier` on garbage (`requires_toolkit: "banana"`): an uncaught exception is a traceback, not the actionable refusal — catch it and emit an ERROR issue (Requirement 3).
- Copying `state.py:load`'s `version != SCHEMA_VERSION` guard: that *strict-equality* shape would refuse `schema_version: 0`/negative, which the spec does **not** name ("newer than understood" is `>`, not `!=`). Keep the `>` comparison.
- Placement/exit-code drift: putting the refusal after branch/worktree setup creates state before refusing, and using `EXIT_REFUSED` (`4`) instead of `2` splits the two config refusals into different codes — keep it at the E3.2 config-refusal site (stderr + `2`, the `test_l43_broken_config_*` family's contract).
- Missing-config crash: a `declared.schema_version > SUPPORTED` check that lets `None` through (`None > 1` → `TypeError`) or treats `None` as "newer" breaks every defaults-only repo — guard `is not None` first.

Explicit non-goals — do NOT do these in this task:
- E3.4 Mythical-Forge default *values* under `paths:`/`repo:` — separate; this task does not touch the defaults structure.
- E3.5 `aidw doctor` config validation and exit-code wiring — separate; do **not** touch `aidw/doctor.py`, and do not report incompatibility from doctor.
- E3.7 read-path existence validation — separate; no `Path.exists()` on `paths:` fields here.
- E4.2's third §3.11 refusal ("a required prompt cannot be resolved") — that is the prompt resolver's, not this task's.
- E4.3 wiring config into every workflow — separate; only `prompt.py` reads config today, and the other workflows will call this same check when they become config-driven.
- E8 tag-based releases / documenting how a repo pins `requires_toolkit` — separate; this task only *enforces* the pin.
- Do not touch `docs/schema/aidw-config.schema.json` (it pins `schema_version` as `type: integer`; value semantics are this task's, not the schema's).
