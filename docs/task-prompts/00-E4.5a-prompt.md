Task: Enforce core vs repo-optional — the rules and their messages (D12, D13). Split of the former E4.5; the planning consequences are E4.5b.

Requirements:
1. Pure validator in `aidw/stage_registry.py`: `validate_stage_list(workflow: str, stages: Sequence[Mapping[str, Any]]) -> list[Issue]`, mirroring `validate_parallel_groups` — no I/O, no `target_config`/workflow import, no mutation of `stages`; raise `UnknownWorkflowError` for an unknown workflow name (never a traceback). It takes plain stage dicts (the `_workflow_value` "stages" shape: `id` + optional `enabled`/`prompt`/`agent`), never `StageConfig` objects.
2. Classification, derived from the registry with no third category: repo-optional ids = a new module constant `REPO_OPTIONAL_IDS = frozenset({"I3", "I4"})` (D13's traceability→`update-traceability`, architecture→`update-architecture`); loop ids = the `stages_by_id(workflow)` keys that are **not** in `definition.stages` (catches `P2`, `P2-fix-blocking`/`-could-fix`/`-fallback`, `P2-reconcile`, `F1`–`F4`); core ids = `definition.stages` ids minus repo-optional; any other id is repo-added (accepted). Prompt-fixed: R2 (review publisher) and A1 (approve) are **core** — D13 names implement/test/code-review/record/pr + author as core and only traceability/architecture as optional, but is silent on the publisher/approver roles, which cannot be optional without making `review`/`approve`/`fix` no-ops.
3. Per-entry rejections, each one `ERROR` with `source=f"workflows.{workflow}.stages"` naming the stage id and the rule: a loop-stage id is refused, never silently ignored or double-planned — message `core stage cannot be disabled` when `enabled is False`, else `loop stages are generated by \`expand\`, not declarable`; a core stage with `enabled: false` → `core stage cannot be disabled`. Skip entries the loader already errored on (non-`Mapping`, missing/empty `id`). Accept: repo-optional `enabled: false`; repo-added stages at any `enabled`; core `enabled: true`/absent.
4. Whole-list checks, each `ERROR` with the same `source=f"workflows.{workflow}.stages"` as the per-entry rejections: removal — every core id absent from the declared list is one `ERROR` (`core stage cannot be removed`), so an explicit `stages: []` yields one per core stage (the list replaces wholesale); duplicate — each core id appearing more than once is one `ERROR` (`core stage declared more than once`); reorder — the declared list's core-id subsequence (duplicates excluded) must equal the registry's static `WorkflowDefinition.stages` core order, with repo-added/repo-optional stages free to interleave or move; a mismatch is one `ERROR` naming the workflow, both orders, and `core stage cannot be reordered` (prompt-fixed: one error per reordered list, not per stage).
5. Wire into all five preflights — `implement`, `prompt`, `review`, `fix`, `approve` — immediately after each workflow's `resolve_workflow_config` succeeds and **only** when the workflow's `stages` entry is declared (`config.get(f"workflows.{workflow}.stages").source == SOURCE_CONFIG`, the same declared-ness test as `effective_parallel_groups`); on any `ERROR` print `format_issues(...)` to stderr and return 2, before `load_all`/any run record/worktree and in `--dry-run`. `implement` validates `parallel_groups` (E4.4) then `stages`.
6. Update the stale E4.3 deferred-warning comment in `aidw/runner.py` (`_REASON_REPO_ADDED`/`_REASON_DISABLED` header) to say `enabled: false`/repo-added are now *preflight-validated* (accepted/rejected) while their *planning* stays deferred to E4.5b — do not change the warnings themselves.

Traps / prior review findings:
- Loop-id vocabulary: `STAGE_IDS` holds `P2` but **not** `P2-fix-*`/`P2-reconcile`, which `stages_by_id()` does return. Detect loop stages via `stages_by_id(workflow)` keys minus `definition.stages`, never via `STAGE_IDS` membership — else `P2-fix-blocking` etc. get misclassified as repo-added and accepted, silently double-planned later.
- Declared-ness: `resolve_config` omits an undeclared `stages` entry (absent, not `unset`) and carries `source == config` for an explicit `stages: []`. Validate only when `source == SOURCE_CONFIG`, or a config with no `stages:` falsely reports "every core stage removed".
- §3.4's illustrative YAML uses semantic ids (`author`, `traceability`); R6 makes retained ids the vocabulary — a config copied from §3.4 with `id: traceability` is a *repo-added* stage, not I3, and `id: architecture` is likewise not I4 (the E4.4 trap repeats here).
- `tests/test_implement_workflow.py::test_dry_run_renders_a_repo_declared_prompt_override` declares `stages: [{id: I3, prompt: …}]`, which the wholesale-replacement + removal rule now correctly rejects (I1/I2/I5/I6 removed). Update it to declare the full six-id list with I3's `prompt:` on it — otherwise `uv run pytest` goes red. `test_plan_stages.py`/`test_cli.py` configs are untouched: they call `plan_stages`/`config show` directly, not a workflow preflight.
- Import direction: `stage_registry` must not import `target_config` or a workflow — pass the resolved stage dicts in as an argument (as `validate_parallel_groups` takes the group list). `review.py`/`fix.py`/`approve.py` import only `resolve_workflow_config` today; the wiring adds `SOURCE_CONFIG` + `stage_registry`, which is safe (no cycle).
- Don't fold removal into reorder: an omitted core stage is a *removal* error, a present-but-misordered one is a *reorder* error — `[I2, I1]` reports removal for I5/I6 *and* one reorder error for I1/I2, never a single blended message.
