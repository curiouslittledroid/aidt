Task: Retry a stage whose final message never arrived.

Requirements:
1. Extend the attempt loop in `aidw/pi.py:execute` (surfaced through `aidw/runner.py:run_stage`) with exactly one second attempt when an invocation exits cleanly and produced no final text: exit 0, not timed out, **no provider error** (`stop_reason != "error"` and no `error_message` — `PiResult.provider_error` already encodes this), and `parse_events(stdout).final_message == ""`. The existing transient-error branch (`is_transient`) is unchanged and additive, never folded into one predicate.
2. The retry starts a **fresh session**: pass a distinct `--session-id` on the second attempt, never re-run the identical argv (Pi resumes `--session-id`, and a truncated context truncates again). The base id is `aidw/state.py:session_id`; derive the retry id deterministically from it. Prompt-fixed (spec says only "distinct"): use a `-retry` suffix on the base id — record the exact convention in the §17 decision row.
3. One attempt only, same cap as today: `max_attempts = 2 if retry_transient else 1`. `--no-retry-transient` (the `retry_transient` param already plumbed CLI → `run_stage` → `execute`) disables the new retry exactly as it disables the transient retry. A stage that answers on the first attempt is never retried; a non-zero exit keeps today's behaviour.
4. Record both attempts: the stage `.meta.json` must show both attempts — per-attempt session id, exit_code, stop_reason, and usage, alongside the existing `attempts` count. Prompt-fixed field name: `attempts_detail`, carried on the `PiResult` as an additive field of the same name — `write_meta` builds the meta from the `PiResult` (`aidw/pi.py:write_meta`), so the per-attempt records must travel there. The truncation retry itself also writes one `run.log` line — `logger.warn`/`logger.info` naming the stage and the first attempt's stop reason, mirroring the transient path's warn in `aidw/pi.py`'s `is_transient` branch — so both attempts are visible in `run.log`, not only the meta (roadmap Deliverable). The stage's recorded `usage` (the dict `run_stage` puts on `aidw/state.py:StageRecord`, which `RunState.totals` sums) must be the **sum of the attempts that actually ran**, so both costs land in the run total. The cost-ceiling check in `run_stage` then covers the summed total automatically — do not add a second check. Prompt-fixed, not an implementer choice: `generation_seconds` and `tool_seconds` sum across the same attempts — `output_tokens_per_second` is the derived `usage.output_tokens / generation_seconds` (`aidw/pi.py:88-96`) that `run_stage` copies to the `StageRecord` and `runs show` prints, so summed `usage` must pair with summed seconds.
5. Add additive fields to `aidw/state.py:StageRecord` — `stop_reason: str | None` and `attempts: int | None` (default `None`, same-schema-version additive precedent as `generation_seconds`) — populated in `run_stage` from the `PiResult`, whose single `stop_reason` is the **final attempt's** value (`execute` parses only the last attempt's stdout; per-attempt reasons live in `attempts_detail`), so the workflow failure path can name them. Reflect them in design §9.2's schema example.
6. Fail closed on double truncation: two attempts with no final text must fail the run with a message naming the stage, the stop reason — the final attempt's, per Requirement 5 — and that **both** attempts were truncated — never the bare "produced no final message". Update the three checks that currently print that string (`aidw/workflows/prompt.py`, `aidw/workflows/fix.py`, `aidw/workflows/review.py`) to read the Requirement 5 fields.
7. Amend design §10's "A review stage returns no final message" row to state the one fresh-session retry and the double-truncation failure, and record the decision in design §17 (next free decision row), naming the session-id convention, the per-attempt meta shape, and the summed usage/timing fields.

Traps / prior review findings:
- Provider-error precedence: a 402 is exit 0 + empty final text. Without the `stop_reason != "error"` guard, the retry silently converts design §10's "provider error → failed, not retried" row into a double attempt. Gate the retry on `not result.provider_error`, not just "exit 0 and empty".
- Emptiness is already whitespace-insensitive: `parse_events` strips assistant text (`_assistant_text`), so a whitespace-only final message parses to `""` — the retry trigger (`final_message == ""`), `execute`'s out-file gate (`if parsed.final_message:`), and the workflows' `not text.strip()` checks already share one notion of empty. A prior review claimed a whitespace-only attempt skips the retry; the strip makes that impossible. Do not add a second emptiness predicate.
- Fresh session is mechanical, not semantic: `session_id` is baked into `argv` by `aidw/agents.py:build_argv` before `execute` runs, so the natural "re-run argv" resumes the truncated session and truncates again. The retry must rebuild/replace the `--session-id` argument.
- Throughput invariant (§9.2/§9.3): `output_tokens_per_second` == `usage.output_tokens` / `generation_seconds`. The timing fields sum across the attempts that ran, exactly like `usage` (Requirement 4 — this is settled, not a choice): leaving `generation_seconds`/`tool_seconds` at the last attempt's value divides summed tokens by one attempt's seconds. Note `execute` currently parses only the last attempt's stdout — the retry overwrites the transcript — so capture each attempt's usage and timing inside the loop before retrying.
- The retry is unconditional on empty final text across **all** stages, not just review stages (a truncated stage is indistinguishable from a silent one — the roadmap accepts this). A stage whose prompt legitimately ends without a final message now costs one extra attempt; do not "helpfully" scope the retry to review stages and do not invent a per-stage opt-out the spec does not have.
- Gate semantics untouched: the retry fires only on the truncation/empty-text signature. A denied/blocked gate or a `Request changes`/`Blocked` verdict is never retried (design §10, roadmap non-goal); a gate command the first attempt already ran is cited — not re-run — via H0.1's cite-or-run path. No new gate machinery.

Explicit non-goals — do NOT do these in this task:
- H1.2 (`aidw prompt --resume`/`--from`, worktree reuse) and H1.3 (blocked-run continuation) are separate tasks — do not touch resumability or branch setup here.
- H2.1 (delta-brief size budget) is a separate task — the retry re-sends the prompt; it does not shrink it.
- The "truncated vs silent" ambiguity is accepted, not solved (roadmap Notes) — do not add a mechanism to distinguish the two.

Tests (what to prove, not the literal expects):
- test_pi.py: drive `execute` with a fake `pi` argv (a python `-c` script printing JSONL that echoes its own `--session-id`): first attempt emits `stop_reason: "length"` + no text, second emits a real answer — assert `attempts == 2`, the two session ids differ, `final_message` is the second answer, `usage` equals the hand-calculated sum of both attempts' token/cost counters, `generation_seconds`/`tool_seconds` equal the sum of both attempts' windows, and `output_tokens_per_second` equals summed output tokens over summed generation seconds, and the logger carries one truncation-retry line naming the stage and the first attempt's `length` stop reason. Feed the two-attempt result through `write_meta` (existing tmp-path pattern) and assert the `.meta.json` carries `attempts_detail` with one entry per attempt, each entry recording that attempt's session id, `exit_code`, `stop_reason`, and usage.
- Double truncation: both attempts empty with `stop_reason: "length"` — assert `final_message == ""`, `attempts == 2`, `stop_reason == "length"`, `out_path is None`, and that `attempts_detail` shows both attempts truncated (two entries, each with `stop_reason: "length"` and its own usage).
- First answer wins: first attempt has text — assert `attempts == 1`.
- Provider-error no-retry: exit 0 + `stop_reason: "error"` + empty text — assert `attempts == 1` and `result.provider_error`.
- Whitespace-only answer: first attempt's final text is spaces only — assert it parses to `""` and retries (`attempts == 2`), and that two whitespace-only attempts end with `out_path is None`, matching the double-truncation case.
- test_runner.py: drive `run_stage` with a fake argv (or a monkeypatched `execute` returning a two-attempt `PiResult`) — assert the `StageRecord` carries `stop_reason`/`attempts` and summed `usage`, with the recorded `stop_reason` the final attempt's (the last `attempts_detail` entry's); that the written `stages/<name>.meta.json` shows `attempts_detail` with one entry per attempt (session id, exit_code, stop_reason, usage) alongside the `attempts` count; and that `retry_transient=False` never retries.
- Purity/fail-closed: existing non-zero-exit and transient-retry behaviour stays green unchanged.

Done when:
- A stage whose first attempt ends `stop_reason: length` (or empty final text) is retried once with a distinct session id; a second attempt that answers continues the run, both attempts visible in the stage meta, one `run.log` line recording the retry, and both costs in the run total.
- Two truncated attempts fail the run naming the stage, the stop reason, and that both attempts were truncated.
- The stage's `usage`, `generation_seconds` and `tool_seconds` all sum across the attempts that ran, so `out-tok/s` stays a true rate (§9.2/§9.3) — never summed tokens over one attempt's seconds.
- A stage that answers first time is never retried; a non-zero exit keeps today's behaviour; a provider error (exit 0, `stopReason: "error"`) is not retried.
- `--no-retry-transient` disables both retries.
- design §10's row and a §17 decision row are amended/added; `state.json` and `.meta.json` keep loading at the same `schema_version`.
