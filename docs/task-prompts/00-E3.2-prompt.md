Task: Layered resolution with provenance — merge toolkit defaults → target config, recording the source of every resolved value.

Requirements:
1. Resolution API in `aidw/target_config.py` (the module's docstring already names E3.2 as its consumer — keep `load_target_config`'s API untouched). Add `resolve_config(declared: TargetConfig, *, overrides: ConfigOverrides | None = None) -> ResolvedConfig` returning, per field, a value plus a provenance `source`: exactly `default` | `config` | `override` (labels prompt-fixed from the roadmap's "default, the config file, or an override") whenever a value resolves, and `None` — with `value is None` — for a field with neither a default nor a declared value. That `None`/`None` pair is Requirement 4's `unset` state and the only other encoding the API carries: there is no fourth `source` label, and `config show` renders this state as `unset`. Precedence: override > config file > default (EXTRACTION.md §3.4 + design.md §12). Addressing and granularity are pinned so later consumers share one contract: `ResolvedConfig` is a flat mapping keyed by each §3.4 leaf's dotted path — `schema_version`, `requires_toolkit`, `max_revisions`, `repo.{base_branch,branch_pattern}`, the six `paths.<field>` leaves, `github.markers.{parent,child,summary}`, `github.labels.<name>.{color,description}`, and one whole-list entry per declared `workflows.<name>.{stages,parallel_groups}` — every entry `{value, source}`. Lists carry provenance only at the list's own path (elements and stage sub-fields get none; lists are never merged element-wise), and the open maps `workflows`/`github.labels` contribute entries only for keys the config declared, so in this task every entry inside them is `source == "config"` (Requirement 2 seeds no defaults there).
2. A defaults structure seeded with **only** `max_revisions = 3`, defined once as `DEFAULT_MAX_REVISIONS` in `aidw/target_config.py` — its single home (design.md §12/H8 pin the *value*: "the toolkit default stays 3"; §12's "lives in `aidw/workflows/prompt.py`" wording describes the pre-E3.1 interim state, and keeping the definition there would force this low-level loader to import a workflow module once Requirement 5 lands — a `target_config -> workflows.prompt -> target_config` import cycle). The `repo:`/`paths:`/`github:`/`workflows` default *values* are E3.4/E6/E4.1's — give the structure empty slots for them and emit `source == "default"` only when a default value actually exists, so those tasks add values without touching the merge.
3. Provenance reflects **declared-ness, not value equality**: a config that explicitly sets `max_revisions: 3` (equal to the default) must still resolve with `source == "config"`. Use `TargetConfig._declared` / field-non-None (E3.1 already tracks this), never `value == default`.
4. `config show` in `aidw/cli.py` must parse the target config via `load_target_config` + `resolve_config` instead of the current `is_file()` detection, and report every resolvable §3.4 field with its `{value, source}`. Keep the six E1.6 root entries (`toolkit_root`/`version`/`target_root`/`workspace_root`/`state_root`/`config_file`); `config_file` now comes from the loader, not `is_file()`, keeping its E1.6 rendering — resolved path with source `target repo` when the loader read a file, `null` with source `defaults` when it saw none. The loader's `Path.exists()` semantics replace `is_file()` and change two pinned edge outcomes: a directory at `aidw/config.yaml` is `exists()`-true and unreadable (`read_text` → `OSError`), and an unparseable YAML file is a parse ERROR — both are loader ERRORs hitting Requirement 6's fail-closed contract (no `--json` payload is emitted; human mode keeps the two E1.6 no-repo root lines before the refusal — Requirement 6); a broken symlink is invisible to `exists()` exactly as to `is_file()`, so it still resolves `null`/`defaults` with exit 0. A field with neither a default nor a declared value is reported `unset` (value null, no source) — that is exactly what E3.4 flips to `default`. The `config` JSON section is the dump of Requirement 1's mapping: one flat object keyed by the same §3.4 dotted paths, each entry `{value, source}`, an unset leaf `{"value": null}` with no `source` key. Human mode grows beyond the six root lines: one line per resolved leaf, after them, in the existing `label: value (source)` format with the dotted path as the label (e.g. `repo.base_branch: main (config)`); an unset leaf prints `unset`.
5. Wire `max_revisions` resolution in `aidw/workflows/prompt.py:run()` to `resolve_config` (replacing the `# insert it on the line below when it lands (E3.1)` placeholder), so CLI `--max-revisions` > config `max_revisions` > `DEFAULT_MAX_REVISIONS` is implemented in exactly one place (design.md §12, H8). `prompt.py` imports `resolve_config` and `DEFAULT_MAX_REVISIONS` from `aidw.target_config` — never the reverse direction. Load the config at `repo.root / "aidw" / "config.yaml"` (§3.4). A loaded config carrying ERROR issues never resolves to defaults: `run()` prints `format_issues` to **stderr** and returns `2` — the same refusal it already applies to `load_all`'s agent-config issues, not `EXIT_REFUSED` (4, git/worktree refusals) — before any run record, branch, or worktree is created, and regardless of `--dry-run`. The loader emits only ERROR issues, so there is no WARNING path to gate behind `--strict`.
6. Purity + fail-closed: `resolve_config` never mutates the input `TargetConfig` (or its nested dataclasses) and does no I/O. `config show` is fail-closed on loader ERROR issues (unparseable YAML, unreadable file — including a directory in place of the file — non-mapping root, unknown key, wrong type) rather than silently resolving a broken/partial config to defaults (`aidw prompt`'s refusal on the same issues is Requirement 5's) — exact contract: it prints `format_issues` of the loader's issues to **stderr**, exits `EXIT_STAGE_FAILURE` (the existing `aidw/cli.py` validation-failure code `agents validate`/`prompts check` already use), and emits no resolved output beyond the two E1.6 no-repo root lines (`toolkit root`/`version`, printed before target resolution): `--json` stdout stays empty (E1.6's all-or-nothing invariant), and human mode keeps the wrong-target refusal shape — those two lines precede the refusal (`test_config_show_wrong_target_refuses_human` pins them). The loader emits only ERROR issues today; no other issue level changes the exit code — resolution proceeds and the command succeeds.
7. Gate impact: `config show`'s JSON payload grows beyond the six E1.6 keys — update `tests/test_cli.py` (`CONFIG_KEYS` and the pinned source labels) to the new contract; `uv run --frozen pytest` must stay green. Beyond `CONFIG_KEYS`, the `is_file` edge-case tests change contract: `test_config_show_config_file_detection_does_not_parse_yaml` and `test_config_show_config_file_directory_is_not_a_config` currently pin exit 0 with the file detected / `none` — both flip to Requirement 6's fail-closed expectation (issues on stderr, `EXIT_STAGE_FAILURE`, empty stdout); `test_config_show_broken_config_symlink_uses_defaults` keeps its outcome (`config_file` `null`/`defaults`, exit 0) with its detection framing updated from `is_file` to the loader's `exists()`; `test_config_show_detects_the_target_config_file` keeps its expectation.

Traps / prior review findings:
- Value-equality provenance bug: implementing `source = "default" if value == DEFAULT else "config"` mislabels an explicit `max_revisions: 3` — use declared-key tracking (`TargetConfig._declared`), the mechanism E3.1 built for exactly this.
- `DEFAULT_MAX_REVISIONS` duplication / import cycle: the constant's single home is `aidw/target_config.py` (Requirement 2); `prompt.py` imports it from there. Don't hardcode `3` a second time inside the resolver or re-define the constant in `prompt.py`, or design.md §12's "default stays 3" drifts into two places — and never `import aidw.workflows.prompt` from `target_config`, which with Requirement 5's reverse import is a cycle that breaks `aidw.cli` at import time.
- Scope creep into E3.4: seeding `repo:`/`paths:` MF-layout defaults here creates a second source of truth against `paths.py:TargetRepo.base_branch`/`branch_pattern` (still hardcoded "main"/"{phase}-{task}"). Leave those slots empty; E3.4 owns the values and the per-default assertions.
- Nesting drift in the resolved shape: mirroring §3.4's YAML nesting in the `config` payload, or splitting `stages` into per-element entries, are the two shapes an implementer reaches for first; both break the flat dotted-path contract E3.4/E4.1/E6 will cite. One flat mapping, whole-list entries at the list path, open maps contributing declared keys only (Requirement 1).
- `config show` still detects the file with `is_file()` and never parses it — without the `load_target_config` call the "per value" provenance is impossible, and a broken YAML is reported as "none" instead of surfacing (see `test_config_show_config_file_detection_does_not_parse_yaml`).
- Resolver purity: a resolver that fills `None` into the `declared` dataclass (or shares default containers across calls) makes resolve-twice and the E3.1 round-trip tests fail; return fresh `ResolvedConfig` objects and never assign into `declared`.
- Don't invent new override flags: the only CLI flag that overrides a config value today is `--max-revisions` (design.md §12). `config show` itself adds no override flag.
- `prompt.py` silently defaulting `max_revisions` on a broken config: `resolve_config` alone doesn't refuse — `run()` must check the loaded config's ERROR issues and exit before resolving, so a malformed `<target>/aidw/config.yaml` cannot hide behind `DEFAULT_MAX_REVISIONS` (Requirement 5, mirroring the `load_all` refusal in the same function).

Explicit non-goals — do NOT do these in this task:
- E3.3 version/compat refusal (`schema_version` newer than understood, `requires_toolkit` unsatisfied) — separate; the resolver does not compare or refuse these fields.
- E3.4 Mythical-Forge default *values* under `paths:` and `repo:` — separate; this task provides empty default slots and `unset` provenance only.
- E3.5 `aidw doctor` config validation and exit-code wiring — separate (doctor only; `config show`'s own failure contract is Requirement 6, not E3.5's); don't touch `aidw/doctor.py`.
- E3.6 `docs/target-repo-config.md` — separate.
- E3.7 read-path existence validation — separate; no `Path.exists()` on `paths:` fields here.
- E4.1/E4.5 stage registry and id vocabulary; E4.6 stage `model`/`thinking`/`timeout_seconds` overrides; E6 `github.markers`/`labels` default values — all separate; the resolver only merges what E3.1's schema already declares.
