Requirements:
1. One shared tick stage: extract I7 into a module-level `StageDefinition` in `aidw/stage_registry.py` (the `_APPROVE_STAGE`/A1 precedent — one id `I7`, one prompt `update-roadmap.md`, one agent `recorder`, one name `update-roadmap`, variables `("{roadmap_file}", "{checkbox_id}")`, `when=WHEN_EVIDENCE_GREEN`), referenced from both `_IMPLEMENT.stages` and a new `_FIX.post_loop`. Add `post_loop: tuple[StageDefinition, ...] = ()` to `WorkflowDefinition`, emitted by `expand()` only on request — a flag such as `include_post_loop`, threaded through `plan_stages` — because `expand("fix", …)` *is* the per-iteration expansion: `fix.py:_planned_iteration` calls `plan_stages("fix", …)` once per iteration with only `pr`/`round_index`/`iteration`/`manifest_path`, and `_render` raises `StageFieldError` on a missing field, so an unconditional post-loop emission breaks every `fix` plan. A named post-loop planning call in `fix.py` — once after the loop breaks on `EXIT_NONE_AVAILABLE`, once at the end of the `--dry-run` plan — expands `post_loop` with `roadmap_file`/`checkbox_id` from req 3's resolution (recording req 3's skip when resolution yields no entry); the loop's stopped exits (`--max-iterations`, a denied gate, an ambiguous verdict, a failed stage) record the same skipped post-loop stage with the stop as its reason (req 4's non-green skip — a stopped run records why, Done when) before returning, the tick itself only ever planned and run after the break; `expand`'s documented `fix` field set gains those two fields (post-loop-only).
2. Enumerate the post-loop stage everywhere the static/loop stages are enumerated: `stage()`, `stages_by_id()`, `validate_stage_list()`, `aidw/runner.py:plan_stages`, and the two `aidw/runner.py` helpers that keep their own `definition.stages`-only sets — `declared_stage_issues` (a declared post-loop id must be treated as known, resolving by its registry prompt-file/agent like any known stage, else the `fix` preflight at `aidw/workflows/fix.py:351` refuses the canonical `[A1, I7]` as repo-added/unresolvable, exit 2 before any run record) and `_warn_deferred_settings` (`fix` is name-keyed, so a post-loop id left out of its known set would warn a correctly declared `I7` as repo-added-deferred). `validate_stage_list` must classify `fix`'s post-loop `I7` as **core** (removal/disable/reorder rules apply; it is not a loop id), and `plan_stages` must split static / loop / post-loop three ways — the current `loop_ids = stages_by_id - static_ids` formula would misclassify `I7` as a loop id for `fix`. Declared-list semantics: a repo-declared `workflows.fix.stages` list replaces static **and** post-loop together — `I7` is declared after every static core id (`[A1, I7]` today; its absence is the removal `ERROR`, req 8), the reorder check compares the declared core subsequence against the registry's static-then-post-loop core order, and the declared path renders declared static entries, then the loop unchanged, then declared post-loop entries — plan order stays static → loop → post-loop.
3. `fix` task-id resolution: from the newest `implement` run's recorded `state.task` (`{"phase","task","prompt_path"}`) for the PR-head branch — `run.py:find_pr_number`'s re-read-the-run-state trade-off, never a `gh` query and never the PR title. Fallback: reverse `repo.branch_pattern`. Resolve the roadmap entry from the located PR-head worktree (`roadmap.load_tasks` + `roadmap.tick_entry` over the resolved `paths.roadmap_dir`/`paths.roadmap_glob`, the same call `implement.py` makes); when neither yields exactly one entry, skip the stage with a reason and the run still succeeds (exit 0), because `fix` must keep working on PRs that are not AIDT tasks.
4. `fix`'s `WHEN_EVIDENCE_GREEN`, evaluated by the workflow (not the agent) before any `run_stage`, distinct from implement's gate-outcome rule: green iff (a) the loop ended because `select` returned `github.EXIT_NONE_AVAILABLE` (not `--max-iterations`, a denied gate, or an ambiguous verdict — those already return 3), (b) every `iter{N}-test` stage record is `SUCCEEDED`, and (c) `latest_verdict == Approve`. Make it a pure helper. Non-green → `aidw/runner.py:record_skipped` (status `SKIPPED`, reason in `SKIP_REASON_KEY`), no `run_stage`, roadmap byte-identical.
5. On green, run the shared tick stage and apply the byte-exact postcondition — re-read the file before/after and call `roadmap.verify_checkbox_flip`; reuse `implement._settle_roadmap_tick` (import or extract) rather than duplicating the flip rule. `tick: flipped`/`already` semantics unchanged: an already-`[x]` box is `succeeded`, never `skipped`.

The edit stays uncommitted — no stage of `fix` commits.
7. The stage appears **once per run**, never per iteration, in `state.json`, `run.log` and the `--dry-run` plan (final position, after the loop). `--dry-run` plans it and evaluates no evidence (apply implement's `withhold_tick`/`settle_tick` split to fix's loop).

Traps / prior review findings:
- Per-iteration emission: the fix loop expands one iteration at a time (`_planned_iteration`); if the post-loop stage rides that plan it is planned (and dry-run printed) per iteration. Plan and run the tick exactly once after the loop breaks on `EXIT_NONE_AVAILABLE`, never inside the loop.
- Two-way split: `plan_stages`'s `loop_ids = stages_by_id - static_ids` and `validate_stage_list`'s loop-vs-core classification both derive from the static set. A post-loop `I7` left out of the enumeration is refused as a "loop stage" when declared and mis-split when not. Update all six enumerators (req 2).
- Empty fix run: the first `select` already returning `EXIT_NONE_AVAILABLE` means `iterations == 0` and `latest_verdict is None`, so condition (c) is false → skip. Do not tick on a run that closed nothing.
- Skip vs no-op: route the skip around the postcondition, exactly as implement's `withhold_tick` returns before `settle_tick` — `_settle_roadmap_tick` runs on `exit_code in (None, 0)` and would stamp `tick: already` onto a stage that never ran.
- Reversal underdetermined: `repo.branch_pattern` is a `str.format` template; `string.Formatter().parse` yields literals and field names only — no split, no greediness. `03-H3.3` under `{phase}-{task}` has exactly one viable split (`03`/`H3.3` — one hyphen), but a task id containing the separator (`03-H3-3`) splits several ways (`03`/`H3-3`, `03-H3`/`3`), and `roadmap.tick_entry`'s count check does not catch a wrong-but-valid pair matching a different real entry. Prompt-fixed rule (req 3): match the whole branch against the pattern's structure (literals `re.escape`d, each field a non-empty capture), **enumerate every viable `(phase, task)` split** — never take a single regex match — and require exactly one viable split that resolves to exactly one roadmap entry; zero or several viable splits, or zero/several entries → skip with reason (exit 0), never a guess.
- Read the roadmap from the located PR-head worktree, not the control root (design K1); read `state.task` from the newest `implement` run matched by `git.branch`, not the PR title.
