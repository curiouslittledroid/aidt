Task: Schema, loader, validation — `aidw/config.py` (or a new `aidw/target_config.py`) defines the §3.4 schema as dataclasses, plus `docs/schema/aidw-config.schema.json`. YAML (D11). Unknown keys are an error, not ignored.

Requirements:
1. New module `aidw/target_config.py` (prompt-fixed: the roadmap lists either, but `aidw/config.py` already means *agent* config — design §5, `load_agent`/`load_all` — so a separate module avoids the collision). Define the §3.4 schema as dataclasses with field names exactly as §3.4 (final names fixed here): top-level `schema_version` (int, required when a config file exists), `requires_toolkit` (str, optional), `max_revisions` (int, optional — design.md §12, absent from §3.4's listing), `repo.{base_branch, branch_pattern}`, `paths.{roadmap_dir, roadmap_glob, task_prompts_dir, implementation_results_dir, build_results_template, architecture_dir}`, `workflows` (map of workflow-name → stage list + `parallel_groups`), `github.{markers, labels}`; each `github.labels` entry is a mapping with exactly `color` (str, required) and `description` (str, required) (prompt-fixed: §3.4's example always shows both, `prompts/scripts/review-followup/publish_review_followups.py` consumes both unconditionally, and D5/§3.9 freezes names, colours and descriptions together).
2. Stage entry schema: `id` (str, required), `enabled` (bool, optional, default true — §3.5 "disabled with `enabled: false`"), `prompt` (str, optional), `agent` (str, optional) — §3.5 "a repo-added stage must declare `id`, `agent`, and either `prompt` or a file in `aidw/prompts/`". No `model`/`thinking`/`timeout_seconds` here — those are E4.6's. Optional fields default to `None`/empty; the Mythical-Forge default *values* for `repo`/`paths` are E3.4's, not baked into the loader.
3. Loader `load_target_config(path: Path) -> TargetConfig` in `aidw/target_config.py`, mirroring `aidw/config.py:load_agent` (prompt-fixed shape: the return is the dataclass carrying `.issues: list[Issue]`, like `AgentConfig` — not `load_all`'s tuple; both conventions exist in-repo, the single-file loader matches the single-file `load_agent`). The input is the config-file path (`<target>/aidw/config.yaml`, §3.4), not the repo root — resolving repo root → config path is the caller's job (E3.2/E3.5). Uses `yaml.safe_load` (D11), dataclasses plus a list of `Issue(level, source, message)`, reusing `ERROR`/`WARNING`/`Issue`/`format_issues` from `aidw/config.py`. A non-mapping result (empty file, list, scalar) is an error, not an `AttributeError` (same guard `load_agent` has). A missing config file is *not* an error (§3.4: a repo with no `aidw/` folder is valid) — the loader returns an empty/defaulted `TargetConfig` with empty `.issues`.
4. Unknown keys are errors at **every** level — top-level, `repo`, `paths`, each workflow, each stage, `github`, `markers`, each `labels` entry — with the offending key's path in the message (e.g. `workflows.implement.stages[0].enabld`). Never silently ignore.
5. Wrong types and out-of-set values fail with the offending path. §3.4 fixes no literal enum field today; the only fixed value-set is `enabled` ∈ {true, false} (prompt-fixed reading of the roadmap's "bad enum values": express it as `type: boolean`, and the JSON Schema carries `enum`/`const` wherever a field's set is fixed so the mechanism is proven). Do **not** enumerate stage ids or workflow names here — that vocabulary is E4.5's, and §3.4/§3.5 disagree on id spelling, so leave `id` a free string.
6. Ship `docs/schema/aidw-config.schema.json` (replacing the `.gitkeep`), hand-written (prompt-fixed: no schema-generation dependency — `pyproject.toml`/`uv.lock` gain nothing, keeping the frozen-lock gate unchanged). It expresses the same schema: `additionalProperties: false` at every object level, required vs optional, types, `enum`/`const`. No Mythical-Forge default values baked in (E3.4's).
7. Round-trip + agreement tests (Tests) are the contract guard: YAML→dataclass→dict→YAML→dataclass is lossless and pure, and the JSON Schema's properties agree with the dataclass fields.

Traps / prior review findings:
- `aidw/config.py` already means *agent* config (`load_agent`/`load_all`, `test_config.py`) — adding target-config there overloads the module and risks breaking agent loading. Use `aidw/target_config.py`.
- Unknown-key rejection must recurse into `workflows`, every stage entry, `github`, `markers` and `labels` — a top-level-only check lets a typo'd stage key like `enabld` load silently.
- `github.labels` is an open map keyed by label *name* (§3.9 "config-with-frozen-defaults"), while `github.markers` is a fixed three-key object (`parent`/`child`/`summary`). Model the former as a map whose entries are exactly `{color, description}` (both required str — the publisher reads both unconditionally) and the latter as three fields, or a repo's extra label is rejected / a typo'd marker key is accepted.
- `max_revisions` is a real key (design.md §12) but absent from §3.4's YAML listing — omit it and the unknown-key check rejects a legitimate config; but its default-3 *merge* is E3.2's, so don't hardcode that value into the loader.
- Round-trip must reproduce the *declared* config, not a default-inflated one, and must not mutate the input dict — a round-trip that injects every default hides a missing-field bug (purity).
- `yaml.safe_load` returns `None` for an empty file and non-dict for a list/scalar — guard before attribute access.

Explicit non-goals — do NOT do these in this task:
- E3.2 layered resolution with per-value provenance (merging toolkit defaults → config) — separate; this task only loads/validates the declared config. Do not wire `repo.base_branch`/`branch_pattern` into `paths.py:TargetRepo`.
- E3.3 version/compat refusal (`schema_version` newer than understood, `requires_toolkit` unsatisfied) — separate; define/load the fields, do not compare or refuse.
- E3.4 Mythical-Forge default values (a `schema_version: 1`-only config producing the MF layout) — separate; no MF-layout defaults here.
- E3.5 `aidw doctor` config validation and exit-code wiring — separate; don't touch `aidw/doctor.py` or `cli.py`.
- E3.6 `docs/target-repo-config.md` — separate.
- E3.7 read-path existence validation — separate; load strings only, don't `Path.exists()` any field.
- E4.1/E4.5 stage registry, id vocabulary, core-vs-optional enforcement — separate (the §3.4-vs-§3.5 stage-id spelling tension is resolved there, not here).
- E4.6 stage `agent`/`model`/`thinking`/`timeout_seconds` overrides — separate; don't add those stage fields here.

Deliverables:
- aidw/target_config.py
- docs/schema/aidw-config.schema.json
- tests/test_target_config.py

Tests (what to prove, not the literal expects):
- Valid full config: a §3.4-shaped YAML (`schema_version`, `repo`, `paths`, `workflows.prompt` + `workflows.implement` with a repo-optional stage carrying `enabled`/`prompt`/`agent`, `parallel_groups`, `github.markers` + `github.labels`, `max_revisions`) loads with zero ERROR issues and every field populated.
- Near-empty config: a file containing only `schema_version: 1` loads with no error (E3.1 proves it *loads*; producing the MF layout is E3.4's test, not this one).
- Missing file / no `aidw/` folder: given a non-existent config-file path (e.g. `<target>/aidw/config.yaml` where the folder is absent), the loader returns an empty/defaulted `TargetConfig` with empty `.issues`, no error.
- Non-mapping YAML (empty file, top-level list, scalar) → ERROR, no `AttributeError`.
- Unknown keys: typo'd key at top level, inside `repo`, inside a stage entry, and inside a `github.labels` entry → ERROR naming the path (`repo.basebranch`, `workflows.implement.stages[0].enabld`, `github.labels.must-fix.colr`).
- Wrong types: `schema_version: "1"`, `repo.base_branch: 7`, `enabled: "yes"` → ERROR naming the path.
- Missing required key: a mapping config file without `schema_version`, and a `github.labels` entry missing `color` or `description` → ERROR naming the path (Requirement 1 — required whenever their container exists; a loader that treats either as optional must fail here, since E3.3's compat refusal keys off `schema_version`).
- Round-trip: load → serialize → reload → dataclasses equal; the dumped form reproduces the declared config (no injected defaults); the input dict is not mutated.
- Schema agreement: load `docs/schema/aidw-config.schema.json` and assert its top-level + nested properties match the dataclass field names and `additionalProperties: false` is present at object levels; a field added to one side but not the other fails.

Done when:
- `uv run --frozen pytest tests/test_target_config.py` is green.
- A full §3.4-shaped config loads with zero errors, and `schema_version: 1` alone (and no config file) loads without error.
- Unknown keys (top-level and nested), wrong types, out-of-set `enabled` values, and missing required keys (`schema_version`; `color`/`description` inside a `github.labels` entry) each fail with the offending path in the message — each proven by a test.
- Round-trip is lossless and pure (no input mutation, no default inflation).
- `docs/schema/aidw-config.schema.json` exists (replacing the `.gitkeep`) and a test pins dataclass ↔ JSON-Schema field agreement.
- `uv run --frozen pytest` is green from the toolkit root (the full gate — doctor, `agents validate`, `prompts check` — is recorded by `record-implementation-results.md`).
