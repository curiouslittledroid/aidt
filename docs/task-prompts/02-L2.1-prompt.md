Task: Reviewer rules for dependencies and unresolved choices (Design 8.1)

Requirements:
1. Dependency-branch inspection — in `prompts/task-review.md`, step 2 `Trace the authority chain`: when the prompt depends on a task whose code is not on the base branch, the reviewer inspects that branch (`git log <base>..origin/<id>`, `git show origin/<id>:<path>`, where `<base>` is the base branch) and states the revision it verified. Never resolve a roadmap-vs-branch conflict in favour of the roadmap summary — the roadmap entry is a planning index; the branch that implements the dependency is the authority for its shape.
2. Blocked, not a prescription — in the findings section, extending the existing "Do not disguise an unresolved design choice as a definite bug: mark it as `Blocked` when it requires an owner decision." line: when the resolution of a finding depends on another task's unmerged implementation, report a `Blocked` verdict naming the dependency — never a `Must fix`/`Should fix` with a `Suggested fix`.
3. Suggested fix is a direction — at the `Suggested fix` field definition: a `Suggested fix` is a direction, not a decision. When two readings both satisfy the cited sources, mark the finding `Blocked` and name the choice in the finding body instead of prescribing one reading.
4. Product-neutral wording — the added text ships to the target repo at cutover (EXTRACTION.md §4.2 bucket (i)): no package-manager name, no product path, no product document (no `pnpm`, no `Design 21`, no `docs/task-prompts`). The git commands and generic "base branch"/"dependent task's branch" phrasing are fine; do not bake in a product task-id example.
5. Format unchanged — the three verdict tokens stay exactly `Approve`/`Request changes`/`Blocked`; the finding labels stay exactly `Priority:`/`Confidence:`/`What I found:`/`Why it matters:`/`Trigger and effect:`/`Where:`/`Suggested fix:` with the same three priorities. `Blocked` is a *verdict*, not a fourth finding priority or a new field.
6. Blocked short-circuits — in `aidw/workflows/prompt.py`, a `Blocked` verdict ends the run blocked with **no fix stage**: record `state.status = BLOCKED`, `save`, print the review text to stderr, `return 3` — before `revisions += 1` and before the `not findings or problems` fallback fix stage, so a Blocked review (with or without parsed findings) never spawns a fixer. This holds **regardless of `approve_all`**: the short-circuit runs before any `approve_all` acceptance path can reach the gate and `_commit_reviewed_prompt` — fail closed always, matching design.md §8.3 ("If `Blocked`, the workflow stops and reports — it does not publish"). The prompt stays uncommitted (the commit runs only after the gate).

Traps / prior review findings:
- `Blocked` is a verdict, not a priority. Adding a fourth priority to the findings block would make `parse_review_findings` fail closed on `PRIORITY_MAP` (`aidw/findings.py`) and contradict "format unchanged"; report the dependency conflict as the overall `Blocked` verdict, with the finding body naming the dependency.
- Place the short-circuit immediately after the `verdict == APPROVE` break and before `revisions += 1` and the `not findings or problems` branch — otherwise a Blocked verdict with no parsed findings still runs the single fallback fix stage.
- After the short-circuit, the two `assumed_ok = verdict != VERDICT_BLOCKED` lines are unreachable for the Blocked case — leave them exactly as they are. They stay for the non-Blocked (Request changes) path, where they implement budget-exhaustion acceptance owned by L4.1 (`MAX_REVISIONS`/terminal-review semantics, an explicit non-goal here); removing, guarding, or inverting them regresses that path and breaks the three-round and fix-batching tests that must pass as-is.
- The existing terminal fails-closed check is gated on `not approve_all`, so `approve_all=True` currently lets a Blocked verdict through to the gate and commit. Requirement 6 closes this hole: place the short-circuit before any `approve_all` acceptance path can apply — do not leave the terminal guard as the only Blocked defence.
- The rendered-prompt test renders `task-review.md` with exactly one variable (the `$1` prompt path) — follow `test_l13_rendered_author_prompt_and_agent_context_state_the_contract`; rendering with zero or extra args raises `PromptError`.
- Scope the neutrality assertion to the added lines, not the whole rendered prompt: the pre-existing Scope bullet already references `Design 21 — Monorepo Layout`, and bucket (i) ships as-is (EXTRACTION.md §4.2) — L2.1 does not neutralise pre-existing text, and a whole-prompt absence assertion would fail on that reference. Assert on the added rule lines the phrase-presence checks already locate.
- The verdict-path test drives through `_fake_stages` with `approve_review=None` and asserts on the recorded stage list (no `task-review-fixes-*`) plus `state.list_runs(...)[-1].status == BLOCKED`, not on the fake stage's file contents. The stage list and run status cannot see the commit (`_commit_reviewed_prompt` is a git operation), so the no-commit criterion needs a git-level assertion: `git.status_short(repo, paths=["docs/task-prompts/03-E4.1-prompt.md"])` is still non-empty (untracked or modified) — the inverse of the empty-status proof in `test_commit_reviewed_prompt_commits_changes`. Also assert via `capsys` that the review text reached stderr, so a regression that commits before returning 3 fails the test even though stage list and status look right.
