Task: `aidw prompt` runs in the control worktree and creates the task worktree

Requirements:
1. Change the real-run preflight in `aidw/workflows/prompt.py:run` so the control-worktree guard is `git.current_branch(repo.root) == repo.base_branch` (R4: keep the literal `"main"` out of the code), not `== "main"`. Keep the clean-tree, incomplete-predecessors and `_verify_base_branch` refusals in their current order and all before any worktree or run state is created. The `--dry-run` note that "a real run requires `main`" becomes "requires the base branch `{repo.base_branch}`".
2. Derive the branch/worktree name from `repo.branch_pattern` instead of the hardcoded `f"{phase}-{task}"` in every branch-naming site (`create_run`'s `branch=`, `state.git["branch"]`, the worktree add, the final `print(f"branch: …")`, the blocked-leftover report). Reuse `derive_branch_name` from `aidw/workflows/implement.py` (prompt-fixed: import it — it is already public and carries the identical malformed-pattern contract; do not duplicate the `string.Formatter` parsing). A malformed pattern is a usage error (exit 2, design §14) before any worktree or stage. The prompt *filename* stays `{phase}-{task}-prompt.md` (task id, not branch pattern) — matches `implement.py:parse_task_id` and `default_rel`.
3. Create the task worktree as inline Python before the author stage, mirroring `aidw/workflows/implement.py`'s branch-setup: `git.add_worktree(repo.root, branch_name, base_branch=repo.base_branch)` (§3.2's per-task command; the primitive already targets `<workspace_root>/<branch>`). On `None` — branch already checked out (one branch, one worktree) or any git refusal — fail closed: actionable message, exit 4, no `run_stage` call, no run state. `--dry-run` prints the planned `worktree add -b <branch> <path> <base>` and creates nothing (design §14: a dry run performs no writes).
4. After the worktree exists, re-resolve the target and the agents against it so P1 and every review/fix stage run with `cwd` = the new worktree (§3.2): `resolved = TargetRepo.resolve(worktree)`, then `replace(resolved, base_branch=repo.base_branch, branch_pattern=repo.branch_pattern)` (the dataclass is frozen — never assign `repo.root`), then `load_all(aidt.root, target.root)` again. `create_run` receives `target.root` and `branch=branch_name`; every `run_stage` call passes `repo_root=target.root`. Keep the initial `load_all(aidt.root, repo.root)` validation before branch setup so a bad agent config refuses before creating a worktree (E2.4's order).
5. The author no longer creates the branch or commits. Edit `prompts/task-prompt.md`: remove the branch-creation/switch/verify instructions ("must be created on a dedicated branch", "if the current branch is not main", "create or switch", "verify and retain the branch name", "if `{phase}-{task}` already exists", "commit the new prompt file", "confirm the new prompt is present on the dedicated branch") and replace with a one-line pointer that AIDT has already placed the author in the task worktree on the branch AIDT created — write the prompt file and return its path; AIDT commits the reviewed prompt. The pointer names no branch: the branch is `repo.branch_pattern`-derived (`{phase}-{task}` is only the default) and P1 receives only `[phase, epic, task]` — mirror `impliment-task.md`'s shipped "Branch setup" pointer. The feasibility bullet is reworded, not kept verbatim: its check stays (read the roadmap entry and every cited spec section, verify what the task depends on exists, and when authoring cannot proceed output `blocked:` as the first line and change nothing), but its branching language goes with the removals — drop the "before branching" title, the "before creating or switching to the `{phase}-{task}` branch" body, and the blocked clause's "no branch"/"no commit" enumeration (AIDT owns the branch, worktree and commit); the check runs before writing the prompt file. Keep the separate `blocked:`-reasons bullet ("Report `blocked: <reason>` for any of these reasons…"), the roadmap-reading, conciseness-budget and prompt-fixed instructions verbatim — the reworded feasibility bullet keeps its own `blocked:` first-line contract, minus the dropped enumeration. Touch nothing else: the `Design 21`/`pnpm`/Zod/`catalog.json`/`01 - Foundation.md…09 - Frontend.md` content is bucket (iii) and E7's to mark/neutralise, not this task's.
6. Commit the reviewed prompt in the worktree: `_commit_reviewed_prompt(target.root, rel, phase, task)` becomes the single commit point (prompt-fixed: the author no longer commits, so this commits the initial or reviewed prompt; it already skips when the path is clean). It commits only the prompt path via `git.commit_paths` (design §13), on the task branch the worktree already has checked out. `rel` is `prompt_path.relative_to(target.root)` — resolved by `_resolve_prompt_path(target.root, rec1, default_rel)` against the worktree, not the control root.
7. Adapt the blocked-run leftover report (L1.3, design §8.1): the task worktree is now Python-created and deterministic, so `_probe_branch`'s before/after comparison is superseded — report the created worktree (path + branch) unconditionally and never delete it. `_uncommitted_prompt_paths` now scans `target.root` (where the author writes), not the control root (which the clean-tree preflight already guaranteed had no prompt changes).

Traps / prior review findings:
- Stale `agent.cwd`/`repo_root`: create the worktree but forget to re-resolve `TargetRepo`+`load_all`, and P1/review/fix silently run in the control worktree — the exact §3.2 failure this task removes (same trap E2.4 shipped). `TargetRepo` is `@dataclass(frozen=True)`; use `resolve`+`replace`, never assignment.
- Commit against the wrong tree: `_commit_reviewed_prompt(repo.root, …)` with the control root commits nothing or commits in the control tree — the author wrote in the worktree. Pass `target.root`.
- `git.add_worktree` returns `None` and discards git's stderr — don't parse a reason it doesn't return; fail closed with a generic actionable message (exit 4). A plain `git init` test repo has no committed base, so `add_worktree` returns `None` and every real run exits 4 — tests that reach branch setup must build the bare+control layout (mirror `tests/test_implement_workflow.py::_make_bare_with_control`); never mock `add_worktree` (Done-when forbids faked git).
- Leaving `prompts/task-prompt.md` unedited lets the author run `git checkout -b {phase}-{task}` inside the already-branched worktree and fail. Remove the branch-creation AND commit instructions — the feasibility bullet's "before branching"/"creating or switching" prose included; requirement 5 rewords that bullet rather than keeping it verbatim. Don't touch `agents/task-author/AGENTS.md`'s "branch the prompt creates" line — that reword is E7.4 (R5); it is harmless now because the author is already on the branch.
- Branch name ≠ task id: `{phase}-{task}` is the task id and prompt filename; the branch is `branch_pattern` applied. Feed `branch_name` to the worktree/`create_run`/`state.git["branch"]`/final print, but keep `default_rel` and `_resolve_prompt_path` on the phase+task filename.
- `rel` is now relative to `target.root`: `_resolve_prompt_path`/`_check_conciseness`/the review `$1` variable must all resolve against the worktree; an absolute or control-root-relative path dangles where the worktree has no file (E2.4's `prompt_rel` trap, prompt-flow edition).
