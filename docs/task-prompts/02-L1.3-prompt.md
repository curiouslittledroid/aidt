Task: give the `task-prompt` author stage a way to report that it cannot author a task, instead of inventing a workaround. `prompts/task-prompt.md` demands the prompt be written, committed on a dedicated branch, and the final message be *exclusively* the prompt path — so an author that finds a cited spec section missing, a prerequisite nowhere to be found, or an acceptance condition it cannot make executable without inventing a contract has no legal output. In E1.6 that is exactly what happened: the author knew its prerequisite was not merged and smuggled the problem into the prompt body. L1.2 now catches roadmap-visible ordering problems before any stage runs; this task covers what only the author can see.

Requirements:
1. `prompts/task-prompt.md` gains the blocked contract, in neutral wording (this file is Mythical Forge's own and moves to the target repo at cutover — E7.1 — so name no package manager, product path or product doc):
   - a feasibility step **before** any branch is created: read the roadmap entry and the spec sections it cites, and check whether what it depends on exists, before creating or switching to the `{phase}-{task}` branch;
   - when authoring cannot proceed, output `blocked: <reason>` as the first line and change nothing — no branch, no prompt file, no commit, no other edits;
   - the three reason classes the author must use it for: a cited spec section that is missing or contradicts the roadmap entry; a prerequisite the entry depends on that cannot be found (not merged and no branch carrying it); an acceptance condition that cannot be made executable without inventing a contract the cited sources do not fix.
   Extend the closing `IMPORTANT:` line so it reads "return exclusively the path to the prompt file created — or, when blocked, `blocked: <reason>` — and nothing else".
2. `agents/task-author/AGENTS.md` carries the same rule: stop and report instead of inventing, with `blocked: <reason>` as the output contract. Leave its branch line alone — E7.4 owns rewording it.
3. `aidw/workflows/prompt.py:run` handles the report: after the author stage succeeds and **before** `_resolve_prompt_path` is called (a `blocked:` first line must never be treated as a path, and must not be overridden by a prompt file the author left behind). Detect the marker on the stage output with the same "strip, then first line" convention `_resolve_prompt_path` already uses, case-insensitively, and treat the rest of the output as the reason.
4. A blocked report ends the run: `state.status = BLOCKED`, `save`, the reason written to the run log (`RunLogger.error`, which is the only log level available) and printed to stderr, and `return 3` — the same value the review-blocked paths already return. No commit, no review stage, no review-fix loop, no new exit code. The author stage's own record stays `succeeded`: it exited 0 and produced a valid report; it is the *run* that is blocked.
5. Also report, never repair, what the run can see when it is blocked (design §13: AIDT never deletes a branch and never discards work):
   - an uncommitted change under `docs/task-prompts/` (a warning naming each path, saying the run neither committed nor removed it);
   - the `{phase}-{task}` branch, but only when it appeared *during this run*: probe with `git.rev_parse(repo.root, f"refs/heads/{phase}-{task}")` before the author stage and again when blocked, and warn only on absent-then-present, so a branch that legitimately pre-existed (the author prompt reuses one based on `main`) is never reported. The probe is advisory: if either probe cannot answer, report nothing rather than guessing.
6. `blocked:` with an empty reason is still a blocked run (3), reported as having no reason; an author stage that returns no output at all keeps today's behaviour (the existing "generated task prompt not found" failure, exit 1) and is not a blocked report.
7. Docs: describe the blocked output in design.md §8.1's P1 stage, and add a row to design.md §10's condition table (`task-prompt` author reports `blocked: <reason>` → run `blocked`, exit 3, reason recorded). Traps / prior review findings:
- Detection must precede `_resolve_prompt_path`: that helper takes the first output line, tries it as a path, and falls back to `docs/task-prompts/{phase}-{task}-prompt.md` — so a `blocked:` line would otherwise be silently ignored whenever the author also left a file, and would produce the exit-1 "not found" failure when it didn't.
- Do not commit the prompt file or run `_commit_reviewed_prompt` on the blocked path, and do not delete anything the author left behind: the run reports leftovers and stops. A blocked run that leaves the tree dirty is the operator's to resolve, and hiding it would break the next run's clean-tree preflight.
- Never `git branch -D` or otherwise remove the branch. The entry's "no branch left behind" is achieved by the author doing its feasibility check *before* branching, and verified by the probe-and-warn — not by the workflow repairing it.
- Creating a branch in a fixture repo needs a commit first: a fresh `git init` has no `HEAD`, so `git branch <name>` fails there.
- The existing tests drive full runs through `_fake_stages`, whose author branch returns a path — leave that path untouched, and add the blocked cases alongside rather than changing the shared fake's default.
- `RunLogger` has `info` and `error` only (no warning level); warnings in this workflow print to stderr, as L1.1's base-branch check does.

Explicit non-goals — do NOT do these in this task:
- L1.2's predecessor gate, L1.1's base-branch check, `--no-fetch`, `--allow-incomplete-prereqs` — do not modify or reorder them.
- E2.4's branch-setup stage and E2.5's control-worktree/branch creation: do **not** remove the branch instructions from `prompts/task-prompt.md`, and do not reword `agents/task-author/AGENTS.md`'s branch line (E7.4 owns that).
- No resume path for a blocked run, no new run status or exit code, no change to `state.json`'s schema, and no auto-retry of a blocked author.
- No E7.1 bucket split: leave the rest of `prompts/task-prompt.md`'s content as it is, and add no product-specific wording.
- No change to the reviewer/fixer prompts or the review loop (L2/L3 own those).

Tests (what to prove, not the literal expects):
- Blocked path: a fake author whose output is `blocked: <reason>` and that writes no file → the run returns 3, the run state is `BLOCKED`, `run.log` and stderr carry the reason, no review stage ran, no `docs/task-prompts/**` change exists and nothing was committed.
- Ordering: the same fake author that *also* writes `docs/task-prompts/03-E4.1-prompt.md` before reporting blocked → still 3, still nothing committed, proving detection precedes path resolution.
- Leftover warning: an uncommitted prompt file left behind → the warning names it, and the file is still present afterwards (reported, never removed).
- Branch warning and its false-positive guard: a fake author that creates the real `{phase}-{task}` branch while reporting blocked → the warning names it and the branch still exists; a run where that branch already existed before the run started → no branch warning.
- Marker parsing: a leading blank line and a lower/upper-case marker are both detected, and a multi-line reason reaches the log; `blocked:` with no reason is a 3 with "no reason"; empty author output keeps today's exit-1 failure.
- Normal path unaffected: the existing full-run tests pass unchanged and still return 0.
- Rendered-contract proof: the author prompt's blocked instruction and its feasibility-before-branch ordering appear in the rendered prompt for the stage, and `agents/task-author/AGENTS.md` states the same output contract.

- The normal authoring path is unchanged — the existing prompt-workflow tests pass as they are.
