Task: `parallel_groups` — replace the hardcoded `[test, update-architecture]` pair; validate members exist and are not ordered against one another.

Requirements:
1. Effective-group resolution: in `aidw/workflows/implement.py`, read the resolved `workflows.implement.parallel_groups` entry via `config.get(...)`; when it is `None` (undeclared — the entry is *absent*, not `unset`, per `resolve_config`) fall back to the registry default `stage_registry.get_workflow("implement").parallel_groups` (`(("test", "update-architecture"),)`, E4.1's data). When `source == SOURCE_CONFIG` use its `value` verbatim, **including an explicit empty `[]`** (declared-ness, not value equality). Members are stage *names* (R11/E4.1), not ids.
2. Replace the hardcoded pair: generalize the `if parallel:` block in `implement.py` (today's `pair = [by_name["test"], by_name["update-architecture"]]` plus its hardcoded `("update-traceability", "record-implementation-results")` tail) to run the resolved groups — non-member stages serially in registry order; each group's members concurrently at the position of the group's earliest member (never empty — requirement 3's validator, run by requirement 5's preflight, rejects empty groups before the scheduler starts, so the scheduler needs no empty-group case), via the existing `ThreadPoolExecutor` + `run_stage` path (run-state writes already serialized by `_STATE_LOCK`). Preserve `should_run`/resume (already-succeeded members print `stage:  {id} {name} [skipped]` and are excluded from the pool), the failure contract (any member failure → `FAILED`, `resume={"next_stage": ...}`, return 1, no later stage runs), and the default group's exact schedule: I1 → {I2, I4} → I3 → I5 → I6 (I6 still runs via the gate path, not `execute`).
3. Validation — members exist: add a pure `validate_parallel_groups(workflow: str, groups: Sequence[Sequence[str]]) -> list[Issue]` to `aidw/stage_registry.py` (reuse `aidw.config.Issue`/`ERROR`; no I/O, no workflow import — the module already promises both). That `aidw.config` import falsifies the module docstring's "Dependency direction" bullet (its "the only import is `aidw.findings`" sentence) — rewrite that sentence to name both imports. Every member of every group must be a stage *name* in `get_workflow(workflow)`'s default `stages` (implement: `impliment-task`, `test`, `update-traceability`, `update-architecture`, `record-implementation-results`, `pr`). An unknown member produces one `ERROR` naming the workflow, the group index, and the member. An empty inner group produces one `ERROR` naming the workflow and the group index (no member to name); the empty *list of groups* `[]` stays valid — requirement 5.
4. Validation — "not ordered against one another" (prompt-fixed: §3.5 fixes the rule, not the mechanism): reject (a) a member listed more than once in one group and (b) a member appearing in more than one group. Rationale: a group declares "these run concurrently"; a duplicated or cross-listed member orders one stage against conflicting concurrency sets (or against itself), which the single-trigger scheduler cannot honor. Deliberately **not** validated (R11/§8.2): file-ownership safety (not inferable), the semantic `test`→`update-traceability` dependency, and adjacency.
5. Fail closed in preflight: run `validate_parallel_groups("implement", <effective groups>)` in `implement`'s preflight, immediately after `resolve_workflow_config` succeeds, on the effective groups (config value or registry default), before any run record/worktree and in `--dry-run`; on any `ERROR` print `format_issues(...)` to stderr and return 2 (same contract as the existing config refusal). `parallel_groups: []` — the empty *list of groups* — is valid and means "no parallel groups": `--parallel` then runs everything serially, never a fallback to the default. An empty *inner group* (` [[]]`) is not this case — it is the requirement-3 ERROR.
6. Update `implement.py`'s stale module docstring ("`--parallel` is accepted and deferred to Phase 7") and the `if parallel:` comment to describe the config-driven groups; `--parallel`'s CLI help in `aidw/cli.py` stays as-is.

Traps / prior review findings:
- The `if parallel:` block hardcodes its *tail* too (`for name in ("update-traceability", "record-implementation-results")`). Generalizing only the pair leaves non-group stages hardcoded — derive the tail from `pre_pr` in registry order, skipping group members that already ran.
- §3.4's example YAML writes `parallel_groups: - [test, architecture]` (illustrative semantic id), but R6/R11 make the retained stage **name** `update-architecture` the validation key — a config literally copied from §3.4 correctly fails "member exists" with `architecture`. `docs/target-repo-config.md`'s "stage ids" wording is the same loose usage; R11/E4.1's "stage names" wins.
- `resolve_config` omits `workflows.implement.parallel_groups` entirely when undeclared (not an `unset` entry) and carries `source=config` for an explicit `[]` — use `config.get(...) is None` vs `source == SOURCE_CONFIG`, never "non-empty value" (an explicit `[]` must mean serial, not default).
- The default group I2/I4 is non-adjacent (I3 between them) and the pair's print order is nondeterministic — `tests/test_implement_workflow.py::test_parallel_runs_test_and_architecture_concurrently` asserts the first three as a `set` and only the tail as an ordered list; don't force a member order or break the exact `[skipped]`/`prefix=entry.id` stdout shape.
- Don't validate the config's `stages:` list against `parallel_groups` (reorder/disable enforcement is E4.5's); validate group members against the *registry's* stage names only.
- `stage_registry.py` importing `aidw.config` (for `Issue`/`ERROR`) is safe (no cycle); importing `aidw.target_config` or a workflow module is not — pass the resolved group list in as an argument, like `plan_stages` takes the resolved config.
