# Workflow and stage reference

> Every stage of every workflow: what it runs, which agent and prompt it uses, which arguments
> it receives, when it runs, and what it changes.
>
> Three sources, deliberately layered: `aidw/stage_registry.py` holds the **chains** as data,
> `prompts/<stage>.md` holds each stage's **behaviour**, and `design.md` §8 holds the **contract**
> around them (gates, postconditions, exit codes). This document is the reader's index into all
> three, so it states the defaults those sources ship.
>
> It is a companion to [`target-repo-config.md`](./target-repo-config.md), not a second copy of
> it. The config contract documents the *keys*; this document documents the *defaults they
> override*. Every stage table here is asserted against `aidw.stage_registry` by
> `tests/test_workflow_stages_doc.py`, so a registry edit that this file does not follow fails
> the suite rather than a reader.

## How to read this reference

### A stage has three names

| Name | Example | Who uses it |
|---|---|---|
| **id** | `I1`, `F3`, `A1`, `P2-fix-blocking` | Stable and short. Config `workflows.<name>.stages[].id`, and `validate_stage_list`'s core/optional rules. Never rendered: an id identifies a stage, it does not name an execution. |
| **runtime name** | `impliment-task`, `iter2-code-review`, `round1-approve-review-followups`, `task-review-fixes-2-1` | The expansion of the id's template with that run's fields (`{iteration}`, `{round_index}`, `{index}`). This is what `state.json`, `run.log`, the stage block, `stages/<name>.*` and `--from <name>` all show. Each execution gets its own name, so a loop's rounds are distinguishable. |
| **prompt file** | `prompts/test.md` | The text the agent receives, resolved through the precedence documented in the companion doc (explicit `prompt:` path → target `aidw/prompts/` shadow → toolkit default → error). One prompt file may serve several stages. |

The tables below give the id and the **runtime-name template**; the actual name is that template
rendered with the run's fields.

### Columns

| Column | Meaning |
|---|---|
| **Id** | The stable stage id. |
| **Runtime name** | The `str.format` template expanded per execution. |
| **Agent** | The `agent-configs/<id>.yaml` the stage runs as. A target repo may override it per stage (`agent:`) or globally (`paths.agent_configs_dir`); `session: shared`/`fresh` comes from that agent config. |
| **Prompt** | The toolkit default prompt file. A target repo may override it (`prompt:`) or shadow it under `aidw/prompts/`. |
| **Variables** | The prompt's positional arguments, in order (`$1`, `$2`, …). `—` means the prompt takes none. |
| **Runs when** | The stage's `when=` condition. `—` means every time the workflow reaches its position. See [Conditions](#conditions). |
| **Context** | Extra text AIDW appends to the rendered prompt (not a positional argument). `—` means none. See [Context blocks](#context-blocks). |

What each kind permits in `workflows.<name>.stages`:

- **core** — replace its prompt, agent, model, thinking or timeout, and add repo-added stages
  around it (only where the workflow actually runs them — see [Declaring stages](#declaring-stages-in-a-target-repo)).
  It may **not** be removed, disabled (`enabled: false`), duplicated or reordered (D12, enforced
  by `validate_stage_list`).
- **repo-optional** — everything core allows, **plus** `enabled: false` to drop it and freedom to
  move it within the list (D13). `I3`/`I4` are the only ids in `REPO_OPTIONAL_IDS`.
- **loop-internal** — nothing: these are generated by `expand()` from the loop descriptor and are
  **refused** in a declared list, whether or not they carry `enabled: false`. The loop is core.

A stage id is classification-stable across workflows: `I7` is core in **both** workflows that run
it, so a declared `workflows.fix.stages` list must carry it — `[A1, I7, F5]` is the canonical
shape there (static ids first, post-loop ids last, in that order).

### Conditions

| Token | Meaning | Decided by |
|---|---|---|
| `findings` | The stage runs only when the preceding review reported findings (`R2` after `R1`; `F4` after `F3`). | `expand()`, from a `findings` flag the caller passes. |
| `blocking` | One stage per blocking (`must-fix`/`should-fix`) finding of the preceding review. | `expand()`, from the parsed findings. |
| `could-fix` | One **combined** stage carrying every non-blocking `could-fix` finding. | `expand()`, from the parsed findings. |
| `unparseable` | One fallback stage carrying the whole review verbatim, used when the review did not parse into findings (or a block was malformed). | `expand()`, from the parse result. |
| `evidence-green` | The stage runs only when **the workflow's own evidence** says so. The token is *carried*, never expanded away: `plan_stages`, `build_plan` and `--dry-run` plan the stage in its position, and the workflow decides before `run_stage`, so no agent can ever run a stage this condition withheld. A withheld stage is recorded as `skipped` with its reason, and the run still succeeds. | The workflow, from state no expansion can see (see `I7` in [implement](#aidw-implement--implement-a-task-prompt-and-open-the-pr) and [fix](#aidw-fix--fix-approved-review-follow-ups)). |

### Context blocks

| Context | What it carries |
|---|---|
| `stage context` | The workflow's own brief: for `I2`, the task id, branch and task-prompt path; for `F2`, the PR number and iteration, plus the instruction that this stage re-verifies a fix and does not change implementation code. Both say the change set stays uncommitted. |
| `manifest pointer` | The **absolute** path of this run's findings manifest in the run directory, which the publisher stage's script consumes. Absolute because the agent runs with the target repo as its cwd, so a run-relative path would name a file that does not exist there. |
| `delta brief` | Rounds 2+ of the prompt review loop: the previous review (re-emitted as the reviewer's own finding blocks when that is strictly smaller) plus the prompt diff since it, capped at 4000 characters. Round 1 carries **no** brief — the first sample must stay independent and must not anchor on an earlier review. |
| `reconcile brief` | The fix batch's reconcile stage: the whole review plus the batch's combined diff, with the instruction to repair cross-section contradictions rather than re-litigate findings. |

A prompt-loop fix stage receives a further runtime extra that is not listed in the tables because
it is per-finding: that finding (or the combined `could-fix` batch, or the whole review) rendered
in the reviewer's own block format.

## Cross-workflow stages

Two stages are deliberately **one definition used by two workflows**, so the behaviour cannot
drift between them:

| Id | Workflows | Why shared |
|---|---|---|
| `I7` `update-roadmap` | `implement`, `fix` | The roadmap tick. `implement` runs it in its static chain; `fix` runs it from its post-loop half once the loop converges. One id, one prompt, one agent, one name — the condition differs (see each workflow). |
| `A1` `approve-review-followups` | `approve`, `fix` | The GitHub approval step. `approve` runs it once and stops; `fix` runs it at the head of every approval round (`round{N}-…`). |

Three prompts serve more than one stage for the same reason — the behaviour *is* the same:

| Prompt | Stages | Note |
|---|---|---|
| `test.md` | `I2`, `F2` | Same proving procedure; the context block and the agent session differ. |
| `code-review.md` | `R1`, `F3` | Same read-only review procedure; `R1`'s findings become GitHub issues via `R2`, `F3`'s via `F4`. |
| `review-findings-to-github.md` | `R2`, `F4` | Same idempotent publisher; both carry the `findings` condition. |

## `aidw prompt` — author and review a task prompt

Resolves one roadmap entry to a task prompt and reviews it to a verdict, with a bounded rework
loop. The branch and worktree are created by AIDT (Python), not by a stage, and the reviewed
prompt is committed by AIDT after the loop — **neither is a stage**.

```text
preflight (control worktree on the base branch, clean tree; fetch; predecessor check)
  Python: create/reuse the task worktree for the derived branch
  → P1 task-prompt                     task-author
  → P2 task-review-1..N                task-reviewer   (verdict)
  ⟳  if Request changes:               P2-fix-* + task-review-reconcile-N  (task-fixer)
                                       then P2 again; fixes only while budget remains
  ◇  approve-task-prompt               optional, off unless --require-approval
  Python: commit the reviewed prompt in the task worktree
```

### `prompt` — stage inventory

| Id | Runtime name | Agent | Prompt | Variables | Runs when | Context |
|---|---|---|---|---|---|---|
| `P1` | `task-prompt` | `task-author` | `task-prompt.md` | `{phase}`, `{epic}`, `{task}` | — | — |
| `P2` | `task-review-{iteration}` | `task-reviewer` | `task-review.md` | `{rel}` | — | `delta brief` |
| `P2-fix-blocking` | `task-review-fixes-{iteration}-{index}` | `task-fixer` | `task-review-fixes.md` | `{rel}` | `blocking` | — |
| `P2-fix-could-fix` | `task-review-fixes-{iteration}-{index}` | `task-fixer` | `task-review-fixes.md` | `{rel}` | `could-fix` | — |
| `P2-fix-fallback` | `task-review-fixes-{iteration}` | `task-fixer` | `task-review-fixes.md` | `{rel}` | `unparseable` | — |
| `P2-reconcile` | `task-review-reconcile-{iteration}` | `task-fixer` | `task-review-fixes.md` | `{rel}` | — | `reconcile brief` |

### What each stage does

- **`P1` task-prompt** — reads the roadmap entry and the spec sections it cites, checks
  feasibility, and writes `<task_prompts_dir>/<phase>-<task>-prompt.md`. When authoring cannot
  proceed it reports `blocked: <reason>` as its first line and changes nothing; the stage itself
  still `succeeded` (it exited 0 with a valid report) and the **run** is blocked. AIDT measures
  the result against the conciseness budget (80–120 lines, <15 KB) and warns, refusing under
  `--strict`.
- **`P2` task-review-{iteration}** — read-only review of the current prompt against its own
  evidence bundle (`stages/<stage>.evidence.md`: prompt path, roadmap entry, cited headings,
  prerequisite tick state, gate commands, base revisions). Parsed verdict is `Approve`,
  `Request changes` or `Blocked`; an unparseable verdict fails closed.
- **`P2-fix-blocking`** — one stage per blocking finding, given that finding in the reviewer's
  own block format, so progress is reported per change. The fixer verifies the finding against
  the repository before editing — the reviewer's `Suggested fix` is a hypothesis, not an order.
- **`P2-fix-could-fix`** — one stage carrying **every** non-blocking finding, so the cheap
  findings cost one invocation instead of one each.
- **`P2-fix-fallback`** — the single stage used when the review did not parse into findings (or a
  block was malformed): it carries the whole review text verbatim, because findings that did not
  parse cannot be split per finding.
- **`P2-reconcile`** — one stage per fix batch, never per finding: it compares the fixed prompt
  against the full review and the batch's combined diff, repairs cross-section contradictions and
  any finding the batch left unaddressed. A round that approves runs none — unless the `Approve`
  carries blocking findings, which is a contradiction and fails closed.

Ends: `Approve` → commit and exit 0. Residual `Request changes` after the **terminal** review →
run `blocked` (exit 3), the gate recorded `denied` with mechanism `review-loop`, findings printed
for a human. `Blocked` verdict → the same exit-3 outcome with its own message.

## `aidw implement` — implement a task prompt and open the PR

```text
preflight (target config, declared stage list, worktree located, no other run active)
  → I1 impliment-task                 implementer   (shared session)
  → I2 test                           tester        (fresh)
  → I3 update-traceability            implementer   (shared)   repo-optional
  → I4 update-architecture            implementer   (shared)   repo-optional
  → I5 record-implementation-results  recorder      (fresh)    sync point
  → I8 summarize-implementation-results recorder    (fresh)
  → I9 write-integration-test-guide   recorder      (fresh)    human-run guide, runs nothing
  → I7 update-roadmap                 recorder      (fresh)    if the run's evidence is green
  ◇  approve-implementation-pr
  → I6 pr                             pr-publisher  (fresh)
  …  any repo-added stages the repo declared, in the declared position
```

### `implement` — stage inventory

| Id | Runtime name | Agent | Prompt | Variables | Runs when | Context |
|---|---|---|---|---|---|---|
| `I1` | `impliment-task` | `implementer` | `impliment-task.md` | `{prompt_rel}` | — | — |
| `I2` | `test` | `tester` | `test.md` | — | — | `stage context` |
| `I3` | `update-traceability` | `implementer` | `update-traceability.md` | `{branch}` | — | — |
| `I4` | `update-architecture` | `implementer` | `update-architecture.md` | `{branch}`, `{base_branch}` | — | — |
| `I5` | `record-implementation-results` | `recorder` | `record-implementation-results.md` | `{branch}` | — | — |
| `I8` | `summarize-implementation-results` | `recorder` | `summarize-implementation-results.md` | `{branch}` | — | — |
| `I9` | `write-integration-test-guide` | `recorder` | `write-integration-test-guide.md` | `{branch}` | — | — |
| `I7` | `update-roadmap` | `recorder` | `update-roadmap.md` | `{roadmap_file}`, `{checkbox_id}` | `evidence-green` | — |
| `I6` | `pr` | `pr-publisher` | `pr.md` | `{task_id}` | — | — |

### What each stage does

- **`I1` impliment-task** — implements the task prompt's acceptance criteria in the located task
  worktree, on the shared `implementer` session. Nothing is committed.
- **`I2` test** — proves the change against the prompt's acceptance criteria with focused checks
  (a real browser for browser-facing work), through the repo's gates (`aidw gate run`).
- **`I3` update-traceability** — updates the repo's traceability artefacts for the change. Runs
  after `I2` because traceability cites the test names `I2` may add. **Repo-optional.**
- **`I4` update-architecture** — updates the repo's architecture documents. Disjoint from `I2`'s
  file set, which is why `test` + `update-architecture` is the default `parallel_groups` pair.
  **Repo-optional.**
- **`I5` record-implementation-results** — the mandatory **sync point**: it runs the repo's full
  verification gates over the fully merged tree and writes
  `<implementation_results_dir>/<branch>/build-results.md` from the configured template,
  **failing closed** if the template is absent. Every later stage cites these gate outcomes
  instead of buying the suite again. The document names the pull request for the change at the
  top, immediately above its `## Summary`: the number a read-only lookup resolves when one
  already exists, otherwise `not yet opened`, because the PR does not exist until `I6`.
- **`I8` summarize-implementation-results** — the read-only narrative summary of `I5`'s output:
  it reads `build-results.md` and writes `summary.md` beside it, runs no gate, re-runs no
  command, edits nothing else and owns no commit. It is separate from `I5` because a summary has
  nothing to read until the record exists, and core because every repo has build results (unlike
  `I3`/`I4`).
- **`I9` write-integration-test-guide** — the human-run **guide** for the change: it reads
  `build-results.md`, the task prompt and the branch's changed files through read-only `git`,
  and writes `integration-test-guide.md` beside them — a step-by-step procedure covering the
  surfaces the change actually touches, with five fields per scenario (prerequisites, the exact
  commands or steps, the expected observable result, how to tell pass from fail, and any
  cost/permission/destructive warning) and the two closing sections (teardown, and what could
  not be exercised in this environment). It is an instruction document, never an execution: it
  runs no integration test, no gate and no cloud/browser/deployed-stack command, so design
  §1.3's non-goal still holds. Core and unconditional like `I8`, and serial between `I8` and
  `I7`.
- **`I7` update-roadmap** — the roadmap tick: flips exactly one checkbox and changes nothing
  else. AIDT resolves the entry itself and refuses (exit 2, before the stage) unless exactly one
  `(phase, task)` entry matches, so a duplicate can never be ticked by accident. After the stage,
  AIDT re-reads the file and requires that exactly the target line flipped `- [ ]` → `- [x]` with
  every other byte identical; an already-`[x]` entry is a `succeeded` no-op (`tick: already`),
  and any other edit fails the stage — an agent's exit 0 is not evidence that the write happened.
  The condition is `evidence-green` and **AIDT** evaluates it: green iff the tree's identity is
  known, at least one recorded gate outcome is for exactly that tree, and every such outcome
  `passed`. Anything else records a `skipped` stage naming the failing gates and leaves the
  roadmap byte-identical. "No evidence" is never green.
- **`I6` pr** — commits the accumulated uncommitted change set, pushes, and opens the PR. This is
  the **single owner of the commit** (design §13); no earlier stage of `implement` commits. After
  the PR exists it replaces the build results' `not yet opened` pull-request line with the number
  it printed and commits that one line, so the delivered document names its own PR.

Runtime shape: declared core order is `I1, I2, I5, I8, I9, I7, I6` (`I3`/`I4` repo-optional, free to
move), and the default `parallel_groups` is `[[test, update-architecture]]` — a `--parallel` flag
turns it on; without it every stage runs serially.

## `aidw review` — review a PR and publish findings as issues

```text
preflight (PR exists, targets the base branch, the PR head's worktree is located)
  → R1 code-review                    code-reviewer    (fresh, read-only)
  if findings:
    → R2 review-findings-to-github    review-publisher (fresh, ungated)  parent + children
  else: report Approve and stop
```

### `review` — stage inventory

| Id | Runtime name | Agent | Prompt | Variables | Runs when | Context |
|---|---|---|---|---|---|---|
| `R1` | `code-review` | `code-reviewer` | `code-review.md` | — | — | — |
| `R2` | `review-findings-to-github` | `review-publisher` | `review-findings-to-github.md` | `{pr}` | `findings` | `manifest pointer` |

### What each stage does

- **`R1` code-review** — read-only review of the PR's change set. AIDT parses the verdict
  (`Approve` / `Request changes` / `Blocked`) and the findings block, and writes the findings to
  `artifacts/findings.json` with stable `F1..Fn` labels — so `R2` does not depend on session
  memory. `Blocked` stops the workflow without publishing.
- **`R2` review-findings-to-github** — creates the review-follow-up parent issue and one child per
  finding, through the bundled publisher script driven by that manifest. It carries a **read-only
  postcondition**: after the agent exits, AIDT re-runs the publisher with `--dry-run` and fails
  the stage unless it would now *find* the parent instead of planning to create it.

Both successful exits record `pr.followups_published` in the run state (`true` only when `R2`
published), which is how `aidw run prompt-to-fix` tells "published" from "approved with nothing to
publish" without a second `gh` query. `review` has **no gate**.

## `aidw fix` — fix approved review follow-ups

```text
preflight (PR exists, targets main, the PR head's worktree is located)
  → list open children; show GitHub state
  ◇  approve-followups                 AIDT's gate, then A1
  ⟳  one approved child at a time:
       → F1 fix-next-review-followup  fixer           (fresh)
       → F2 test                      tester          (fresh)
       → F3 code-review               code-reviewer   (fresh)
       if F3 has findings:
         → F4 review-findings-to-github (new children, ungated) then ◇ approve-followups
       else:
         ◇ approve-fix-pr
     repeat until select reports no available child (or --max-iterations)
  → I7 update-roadmap                 recorder        if this run's evidence is green
  → F5 commit-and-push                pr-publisher    commits the change set and pushes the branch
```

### `fix` — stage inventory

| Id | Runtime name | Agent | Prompt | Variables | Runs when | Context |
|---|---|---|---|---|---|---|
| `A1` | `round{round_index}-approve-review-followups` | `review-approver` | `approve-review-followups.md` | `{pr}` | — | — |
| `F1` | `iter{iteration}-fix-next-review-followup` | `fixer` | `fix-next-review-followup.md` | `{pr}` | — | — |
| `F2` | `iter{iteration}-test` | `tester` | `test.md` | — | — | `stage context` |
| `F3` | `iter{iteration}-code-review` | `code-reviewer` | `code-review.md` | — | — | — |
| `F4` | `iter{iteration}-review-findings-to-github` | `review-publisher` | `review-findings-to-github.md` | `{pr}` | `findings` | `manifest pointer` |
| `I7` | `update-roadmap` | `recorder` | `update-roadmap.md` | `{roadmap_file}`, `{checkbox_id}` | `evidence-green` | — |
| `F5` | `commit-and-push` | `pr-publisher` | `fix-commit.md` | `{pr}` | — | — |

The `A1` row is the **static** half and `I7`/`F5` are the **post-loop** half: both are emitted
once per run, after the loop, and never per iteration — `I7` first, then `F5`. `F1`–`F4` are the
loop's head and body.

### What each stage does

- **`A1` approve-review-followups** — the only place AIDT writes `approve-fix` and removes
  `decision-pending` on open children (closed children are untouched), through the bundled
  `review_followup.py` script. AIDT gates this first (`approve-followups`) and verifies it after
  (`github.verify_approvals`), because an agent that reports success is not evidence the GitHub
  writes happened. `fix` runs one approval round at entry and another after every round that
  published new findings.
- **`F1` fix-next-review-followup** — fixes exactly **one** approved child issue and closes it.
  "Available" is always re-derived from `review_followup.py select`, never by counting, so the
  loop is driven by real GitHub state.
- **`F2` test** — re-verifies that one fix against its acceptance criteria. It does not fix
  implementation code: a real defect is reported `Fail` and handed back to `F1`.
- **`F3` code-review** — read-only re-review of the fix, verdict `Approve` / `Request changes` /
  `Blocked`. An ambiguous verdict or `Blocked` fails closed (exit 3).
- **`F4` review-findings-to-github** — publishes the re-review's findings as new child issues,
  ungated, from the manifest AIDT writes at `artifacts/iter{N}-review-manifest.json` (with
  `artifacts/iter{N}-findings.json` beside it). A human then approves the new children on GitHub
  and the loop continues with the next `A1` round.
- **`I7` update-roadmap** — the same definition `implement` runs, with `fix`'s own condition:
  green iff the loop ended because `select` found **no** available child (not `--max-iterations`,
  a denied gate or an ambiguous verdict), **every** `iter{N}-test` stage succeeded, and the last
  re-review verdict is `Approve`. An empty run (`latest_verdict` is `None`) is not green: a run
  that closed nothing must not claim the task done. The task id comes from the newest `implement`
  run's recorded state for this branch, falling back to reversing `repo.branch_pattern`; when
  neither yields exactly one roadmap entry the stage is **skipped with a reason and the run still
  succeeds**, because `fix` must keep working on PRs that are not AIDT tasks.
- **`F5` commit-and-push** — the one stage of `fix` that publishes the run's work, and it carries
  **no** `when=` condition: its trigger is the loop's convergence, not the tick's outcome, so a
  converged run whose tick was withheld still lands its fixes. The `pr-publisher` agent commits
  the accumulated change set (the fix edits plus the tick when it flipped) and pushes the PR-head
  branch — never the base branch, never a force-push. AIDT picks the case, then verifies the
  result: a dirty tree with at least one issue closed this run commits and pushes and records the
  verified remote head as `state.pr["head_sha"]`; a dirty tree with nothing closed, and a clean
  tree with nothing closed, are recorded **skips** with `state.pr["commit_skip_reason"]` and exit
  0 (unowned dirt is not this run's to publish, and a no-op run creates no empty commit); a clean
  tree with at least one issue closed fails closed, because issues were closed and there is
  nothing to push. A stage record alone is not evidence the push landed: AIDT re-reads `HEAD` and
  `origin/<branch>` and fails the run (naming the PR and branch) when they differ or cannot be
  resolved, when the tree is still dirty, or when the stage did not succeed.

`F5` is the only stage of `fix` that commits, and it commits everything the run accumulated —
the fix and tick edits reach the PR instead of staying in the worktree (design §8.4, §13, §17
Z9). A stopped loop still commits nothing: every stop path records both post-loop stages as
skipped with the stop as the reason.

## `aidw approve-followups` — record the approval decision only

```text
preflight (PR exists; `gh` available)
  ◇  approve-followups                 show the open children; human confirms
  →  A1 approve-review-followups       review-approver
```

### `approve` — stage inventory

| Id | Runtime name | Agent | Prompt | Variables | Runs when | Context |
|---|---|---|---|---|---|---|
| `A1` | `approve-review-followups` | `review-approver` | `approve-review-followups.md` | `{pr}` | — | — |

This is `fix`'s entry approval without the loop, for a human who wants to apply the GitHub
decision now and fix later. Declared repo-added stages in `workflows.approve.stages` run in their
declared order around `A1`; only `A1` carries the approval postcondition.

Note the asymmetry: `fix`'s approval rounds plan from **`workflows.fix.stages`** and take only its
`A1` entry, so a stage added to `workflows.approve.stages` runs in `aidw approve-followups` and
**not** inside a `fix` approval round. Extra stages around approval inside the loop must be
declared under `workflows.fix.stages`.

## Loops

### The `prompt` review loop (`P2`)

- **Head** `P2` runs every round; **body** (the fix stages) and **tail** (reconcile) run only
  while revision budget remains.
- **Budget** is `max_revisions` — CLI `--max-revisions` > target config `max_revisions` > `3`.
  Fix batches run only for the first `max_revisions - 1` rounds.
- The **last round is review-only** (`terminal_last`), so a review is always the last stage of a
  non-approving prompt and no fix is ever accepted without having been reviewed.
- Round 1 is **unprimed** (`unprimed_first`): no delta brief, because the first sample must not
  anchor on an earlier review.
- Expansion refuses a batch set larger than the budget (`RevisionBudgetError`), never silently
  shortening the plan.

### The `fix` iteration loop (`F`)

- One iteration is `F1` → `F2` → `F3` (+ `F4` when `F3` has findings, sending the loop through
  another `A1` round).
- Bounded by `--max-iterations` (default 10) and, in practice, by GitHub state: `select` reporting
  no available child ends the loop **successfully**.
- `expand("fix", …)` *is* the per-iteration expansion, which is why `I7` and `F5` live in the
  workflow's `post_loop` half and are emitted only when a caller asks
  (`include_post_loop=True`) — once each, after the loop, by `aidw fix` itself.

## Gates

Gates are human decisions recorded in `state.json` (`GateRecord`) and printed with their
mechanism: `--yes`, `--skip-gates <name>`, `--deny-gates <name>`, `human`, `human-default`,
`human-denied`, `noninteractive`, and `review-loop` for the `prompt` loop's terminal
non-approval. A gate's `detail` carries the per-round summary the operator reads.

| Workflow | Gates | Asked |
|---|---|---|
| `prompt` | `approve-task-prompt` | Between the loop and the commit; **off by default**, enabled with `--require-approval`. Also recorded `denied`/`review-loop` when the loop ends non-approving. |
| `implement` | `approve-implementation-pr` | Between `I7` and `I6`: the last chance to stop before the commit, push and PR. |
| `review` | none | `review` publishes and stops; there is no decision to make. |
| `fix` | `approve-followups`, `approve-fix-pr` | `approve-followups` at entry and after every round that published new findings; `approve-fix-pr` when a re-review approves. A denial is exit 3 (`blocked`). |
| `approve` | `approve-followups` | Before `A1`, always. |

Every gate is skippable/deniable from the CLI (`--yes`, `--skip-gates <name>`, `--deny-gates
<name>`, `--gate-default approve|deny`); `deny` wins over `skip`. `aidw run prompt-to-fix`
auto-approves exactly one gate, `approve-followups`, so the cycle is unattended — `--deny-gates
approve-followups` still refuses it.

## Runtime records and artifacts

Every stage execution is recorded, whether it succeeded, failed or was withheld:

- `state.json` — one `StageRecord` per execution: `name` (the runtime name), `agent`, `model`,
  `status` (`planned` / `running` / `succeeded` / `failed` / `skipped`), timings, `exit_code`,
  `stop_reason`, `attempts`, cost and token counters, and `artifacts`. The **run's** own status is
  separate and may additionally be `blocked`.
- `run.log` — one line per decision, including a skipped stage's reason.
- `prompts/<name>.rendered.md` — the exact prompt text Pi received.
- `stages/<name>.jsonl` — Pi's raw event stream; `<name>.out.txt` — the final message;
  `<name>.meta.json` — counters, attempts and the argv; `<name>.prompt.md` — the prompt snapshot
  for the prompt-loop fix stages; `<name>.evidence.md` — `P2`'s evidence bundle.
- `artifacts/findings.json` (`R1` → `R2`), `artifacts/iter{N}-review-manifest.json` plus
  `artifacts/iter{N}-findings.json` (`F3` → `F4`).

A finished stage prints a block naming its model, duration, cost, speed, usage and output path;
`aidw runs show <run-id>` reads the same records back, and `--dry-run` prints the plan without
invoking Pi or writing anything.

Exit codes are uniform: `0` success/approved, `1` stage failure, `2` usage or config,
`3` blocked (needs a human), `4` environment/preflight refusal.

## Declaring stages in a target repo

The config contract is [`target-repo-config.md`](./target-repo-config.md) — this section only
says how the stage vocabulary above binds to it.

```yaml
schema_version: 1

workflows:
  fix:
    stages:
      - id: A1                       # core: must be present, first
      - id: I7                       # core, post-loop half: declared last
      - id: my-extra-check           # repo-added: runs in this declared position
        prompt: my-extra-check.md
        agent: tester
  implement:
    parallel_groups:
      - [test, update-architecture]
```

- A declared `stages` list **replaces** the workflow's whole list — list values are copy-through,
  never merged element-wise, so an omitted core id is a removal `ERROR`, not an inheritance. A
  stage entry the list does not carry keeps the registry's own agent and no overrides, which is
  why the practical shape is: declare every core id, and put `prompt`/`agent`/`model`/`thinking`/
  `timeout_seconds` on the entries you want to change.
- `parallel_groups` members are stage **runtime names** of that workflow's static chain, not ids.
- Unknown ids are refused; a malformed list is a refusal (exit 2) before any run state exists.
- **Repo-added stages run in `implement`, `review` and `approve`, not in `prompt` or `fix`.**
  Those two resolve their stages by runtime name, so a repo-added entry is planned (the plan and
  the dry run reflect the declaration) but never executed, and the run warns about it — a
  declared stage that silently did not run would be worse than the warning.

## Chains (`aidw run`)

Chains are code, not configuration (`aidw/workflows/run.py`): each composes whole workflows, and
each workflow keeps its own preflight, gates, state and resumability. The chain stops at the first
non-zero exit.

| Chain | Runs | Note |
|---|---|---|
| `task-to-pr <phase> <epic> <task>` | `prompt` → `implement` | Uses the branch the prompt workflow created. |
| `review-and-fix --pr <n>` | `review` → `fix` | Ends gracefully (exit 0) when the review published no follow-ups. |
| `prompt-to-fix <phase> <epic> <task> [--pr <n>]` | `prompt` → `implement` → `review` → `fix` | The PR number comes from the `implement` run's state; `approve-followups` is auto-approved. |

## Keeping this document true

`tests/test_workflow_stages_doc.py` parses the tables above and asserts them against
`aidw.stage_registry`:

- the workflow set is exactly `stage_registry.DEFAULTS`;
- each workflow's inventory rows — id, runtime-name template, agent, prompt, variables, `when=`
  and context — match its definition **in order** (static, then loop head/body/tail, then
  post-loop), so added, renamed, reordered or re-agented stages fail here;
- the id vocabulary is exactly `STAGE_IDS` plus the loop-internal labels, with each id's
  core/repo-optional/loop-internal classification and the workflows it appears in;
- the condition and context tables name exactly the tokens the registry can emit;
- the gates table matches each workflow module's gate constants;
- every prompt file named here is in `inventory.REQUIRED_PROMPTS`, so a prompt rename cannot
  leave a stale reference.

The same test pins the `aidw implement` stage list in `README.md`, which had drifted from the
registry.
