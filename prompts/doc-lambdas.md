# Regenerate Lambda Reference Document

Regenerate `docs/architecture/Lambdas.md` — the canonical reference for every Lambda in the Mythical Forge project. This prompt discovers all Lambdas from the CDK infrastructure, inspects their source code and shared-types schemas, and produces a structured document with trigger sources, database access patterns, summaries, and input/output JSON schemas.

## Source-of-truth locations

- CDK infrastructure (Lambda definitions): `infra/lib/compute-stack.ts`, `infra/lib/api-stack.ts`, `infra/lib/identity-stack.ts`, `infra/lib/data-stack.ts`, `infra/lib/srd-data-stack.ts`
- Lambda source code: `services/*/src/`
- Shared type schemas: `packages/shared-types/src/schemas/`
- Infrastructure custom resources: `infra/lib/custom-resources/`
- Seed Lambda: `infra/lib/seed-srd-data.ts`
- Project rules: `AGENTS.md`

## Document format

The output document at `docs/architecture/Lambdas.md` must follow this exact structure:

1. **Header** — title, auto-generation notice citing this prompt path (`aidt/prompts/doc-lambdas.md`)
2. **Table of Contents** — 2-level, linked, covering all sections
3. **Summary Table** — 22+ rows with Lambda name (linked), trigger source, reads, writes, status
4. **Per-Lambda sections** — grouped by subsystem, each containing:
   - Attribute table (Trigger, Source, Reads, Writes, Code, Concurrency if applicable)
   - One-paragraph summary
   - Collapsible `<details>` block with exact input/output JSON/TypeScript schemas

## Discovery instructions

### Step 1: Find every Lambda

Scan all CDK stack files under `infra/lib/` for Lambda definitions. Look for:
- `new lambda.Function(...)` — placeholder/stub Lambdas
- `new lambdaNodejs.NodejsFunction(...)` — real Lambdas with entry points
- Custom resource `Provider` on-event handlers

Record for each: the CDK construct ID, the Lambda's logical name, its source code entry path, reserved concurrency, environment variables, IAM grants, and VPC/subnet/security-group placement.

### Step 2: Read each Lambda's source code

For every Lambda with a real entry point (not inline placeholders), read:
- The handler file to understand the event shape and processing logic
- Any service-level modules it imports (moderation, intent parser, etc.)
- The Zod schemas or TypeScript interfaces for its input and output

For inline placeholder Lambdas, note the stub code and what the Lambda is planned to do (from comments and design spec references).

### Step 3: Extract input/output schemas

For each Lambda, determine:
- **Input schema** — the exact event shape the Lambda receives. For Cognito triggers this is the AWS trigger event type. For API Gateway this is `APIGatewayProxyEvent` or `APIGatewayProxyWebsocketEventV2`. For CloudFormation custom resources this is the CFN event. Include the Zod validation schema where applicable.
- **Output schema** — the exact response shape. For API Gateway Lambdas this is `APIGatewayProxyResult`. For WebSocket Lambdas, include the frames sent via `PostToConnection`. For Cognito triggers, note the mutation of the event object. For CFN custom resources, note the `PhysicalResourceId` response.

Source these from:
- `packages/shared-types/src/schemas/` — Zod schemas for API contracts
- `services/*/src/` — handler code and local types
- AWS Lambda type definitions (`@types/aws-lambda`)

### Step 4: Group and write

Organize Lambdas into these groups (matching the CDK stack structure):
1. **Identity Triggers (Cognito)** — from `identity-stack.ts`
2. **Player API — REST** — from `api-stack.ts`
3. **Player API — WebSocket** — from `api-stack.ts`
4. **Rules Engine** — from `compute-stack.ts`
5. **Background Workers** — from `compute-stack.ts`
6. **Data Infrastructure** — from `data-stack.ts` and `srd-data-stack.ts` (custom resources + seed)

For each Lambda write:
- An attribute table with: Trigger, Source, Reads, Writes, Code, Concurrency (if set)
- A one-paragraph plain-English summary of what the Lambda does
- A collapsible `<details>` block with TypeScript interfaces, Zod schemas, and JSON examples for both input and output

### Step 5: Build summary table and TOC

Build a summary table at the top with every Lambda, each name linked to its section anchor. Include columns: #, Lambda, Trigger Source, Reads, Writes, Status (✅ Active / 🔶 Placeholder / 🔶 Stub).

Build a 2-level table of contents above the summary table with links to every section and subsection.

## Content rules

- Every Lambda that exists in CDK must appear in the document, including placeholders and stubs. If a Lambda is removed from CDK, remove it from the document.
- The document must state it is auto-generated at the top: `> Auto-generated by [aidt/prompts/doc-lambdas.md](../../aidt/prompts/doc-lambdas.md). Regenerate with this prompt to keep it in sync with the codebase.`
- Use exact code identifiers, environment variable names, table names, IAM role names, and file paths from the source. Do not invent, approximate, or paraphrase.
- Schema examples must match the actual Zod schemas and TypeScript types. Do not simplify or omit fields.
- If a schema is defined in `@mythical-forge/shared-types`, reference the package and schema name.
- The document should be comprehensive enough that a developer can understand every Lambda's contract without reading the source code.
